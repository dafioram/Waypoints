Python virtual environments

A virtual environment is a folder that gives one project its own Python packages, so what you install for one project cannot break another. This guide covers the everyday commands, how to keep several Python versions side by side, and what to do when something goes wrong.

Quick start

These are the commands you will run most often, from creating an environment to throwing it away. The rest of the guide explains each step and what to do when one fails.

Quick start (Linux, macOS)
$ cd myproject$ python3 -m venv .venv # create it, once per project$ source .venv/bin/activate # switch it on, in every new terminal(.venv) $ pip install requests # installs into .venv only(.venv) $ pip list # what is installed here(.venv) $ pip freeze > requirements.txt # save the exact versions(.venv) $ pip install -r requirements.txt # restore them somewhere else(.venv) $ deactivate # switch it off$ rm -rf .venv # delete it; you can always recreate it
Quick start (Windows, PowerShell)
PS> cd myprojectPS> py -m venv .venv # create it, once per projectPS> .venv\Scripts\Activate.ps1 # switch it on, in every new terminal(.venv) PS> pip install requests # installs into .venv only(.venv) PS> pip list # what is installed here(.venv) PS> pip freeze | Out-File -Encoding utf8 requirements.txt # save the exact versions(.venv) PS> pip install -r requirements.txt # restore them somewhere else(.venv) PS> deactivate # switch it offPS> Remove-Item -Recurse -Force .venv # delete it; you can always recreate it

The Windows examples use PowerShell. The pip and uv commands are identical in cmd.exe; only activating and deleting differ, and the activation section lists those.

The prompt shows (.venv) while an environment is switched on, and the examples show it the same way. Two habits are worth keeping from day one: write python -m pip when you are not sure which pip you will get, and commit requirements.txt but never .venv.

What a virtual environment is

A virtual environment is an ordinary folder, usually named .venv, inside your project. It holds a python that points back at the Python which created it, its own empty site-packages folder where pip install puts packages, and a few activation scripts. It is quick to create because nothing is downloaded and Python's standard library is not copied.

.venv/The whole environment. Safe to delete.
├─ bin/Commands and activation scripts.
│ ├─ pythonA link to the Python that created it.
│ ├─ pippip for this environment only.
│ └─ activateAlso activate.fish, activate.csh and Activate.ps1.
├─ include/Headers, for packages that compile code.
├─ lib/python3.12/Named for the Python version.
│ └─ site-packages/Every package you install lands here.
├─ lib64A link to lib, on 64-bit Linux.
└─ pyvenv.cfgRecords which Python made it.
.venv\The whole environment. Safe to delete.
├─ Scripts\Commands and activation scripts.
│ ├─ python.exeThe environment's Python.
│ ├─ pip.exepip for this environment only.
│ └─ Activate.ps1Also activate.bat and activate.
├─ Include\Headers, for packages that compile code.
├─ Lib\Python's library folder.
│ └─ site-packages\Every package you install lands here.
└─ pyvenv.cfgRecords which Python made it.

The last file is why an environment stays on one Python version. This is the real pyvenv.cfg of an environment created with Python 3.12:

pyvenv.cfg
home = /usr/bininclude-system-site-packages = falseversion = 3.12.3executable = /usr/bin/python3.12command = /usr/bin/python3.12 -m venv /home/ada/myproject/.venv

What activating does

Activation changes three things in your current terminal: it puts the environment's binScripts folder first on PATH, sets a VIRTUAL_ENV variable, and adds (.venv) to your prompt. Typing python then finds the environment's copy before the system one. deactivate undoes exactly those three changes. The panel at the top of this page lets you try it.

What follows from that

  • You do not have to activate. .venv/bin/python app.py.venv\Scripts\python app.py runs with the environment's packages. Use this form in cron jobs, services and scripts, where nobody is there to activate.
  • An environment belongs to its path. The scripts inside it contain the absolute path of the folder they were created in. Moving or renaming .venv breaks it; recreate it instead.
  • An environment belongs to one Python version. To change version you build a new environment, as the versions section shows.
  • An environment is disposable. Delete it whenever it gets confusing. The requirements file is the record, and the environment is only the result.

To check from inside Python whether an environment is active, compare two values. They differ only inside an environment:

Is an environment active?
python -c "import sys; print(sys.prefix != sys.base_prefix)"False(.venv) python -c "import sys; print(sys.prefix != sys.base_prefix)"True

Create an environment

Run this from your project folder. -m venv means “run the venv module of this Python”, and .venv is the folder to create.

Create (Linux, macOS)
$ python3 -m venv .venv
Create (Windows, PowerShell)
PS> py -m venv .venv

The new environment uses the Python that ran the command, at that version. To use a different version, run that version instead, as in Several Python versions. On Windows py starts the Python install manager's default Python; python -m venv .venv works too when python is on your PATH.On Debian and Ubuntu you may first need sudo apt install python3-venv; the exact message is below.

Name and location

Call it .venv and keep it in the project root. The leading dot hides it from casual listings, uv uses that name by default, and because it is the same in every project, commands and docs can be copied between them. Names like venv or env work the same but need their own line in .gitignore and are not what uv looks for.

Prompt named after the folder, pip up to date (Linux, macOS)

Prompt named after the folder, pip up to date (Windows, PowerShell)
PS> py -m venv --prompt . --upgrade-deps .venv

Activation applies to one terminal window. Do it again whenever you open a new terminal in the project.

“Running scripts is disabled on this system.” PowerShell blocks Activate.ps1 until you allow local scripts for your own account. Run this once:

Allow local scripts for your user (Windows, PowerShell)
PS> Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

Deactivate and delete

Switch off, then delete (Linux, macOS)
(.venv) $ deactivate$ rm -rf .venv
Switch off, then delete (Windows, PowerShell)
(.venv) PS> deactivatePS> Remove-Item -Recurse -Force .venv

In cmd.exe the delete command is rmdir /s /q .venv.

deactivate is a function that the activate script defines, so it exists only while an environment is active. Typed with nothing active, it answers “command not found”. Leave the environment before deleting it, so your PATH does not keep pointing at a folder that no longer exists.

Install and inspect packages

With the environment active, pip installs into it and nowhere else. This is the session behind the numbers in this guide:

Install, then look
(.venv) pip install requestsSuccessfully installed certifi-2026.10.23 charset-normalizer-3.5.2 idna-3.20 requests-2.34.2 urllib3-2.8.0(.venv) pip listPackage            Version------------------ ----------certifi            2026.10.23charset-normalizer 3.5.2idna               3.20pip                24.0requests           2.34.2urllib3            2.8.0

Installing one package pulled in four, because requests depends on them. That matters again in Requirements files.

The pip commands you will use most
CommandWhat it does
pip install requestsInstall the newest version.
pip install requests==2.34.2Install exactly that version.
pip install "requests>=2.31,<3"Install a version within a range. The quotes stop the shell treating > and < as redirects.
pip install --upgrade requestsMove to the newest version.
pip uninstall requestsRemove it. Asks first; -y skips the question. Its dependencies stay.
pip list --outdatedShow installed packages that have newer releases.
pip show requestsVersion, install location, and which packages it needs.
pip checkReport installed packages whose requirements are not met.
pip install -e .Install your own project in editable mode, so code changes take effect without reinstalling. Needs a pyproject.toml.

python -m pip is the safe spelling. pip and python -m pip both use the environment's pip when it is active. The longer form always uses the pip that belongs to the Python you named, so it cannot pick up another pip by accident. It is also the only form that works when you call the environment's Python by path, as in .venv/bin/python -m pip install requests.venv\Scripts\python -m pip install requests.

Do not use sudo pip install. Recent Debian and Ubuntu releases refuse global installs with externally-managed-environment (see Troubleshooting). The refusal is the system telling you to use an environment.

Requirements files

A requirements file is a text file with one package per line. It is how you rebuild an environment after a fresh clone, on another machine, or after deleting .venv.

Freeze and restore

pip freeze prints every installed package with its exact version, and -r installs from such a file.

Save and restore (Linux, macOS)
(.venv) $ pip freeze > requirements.txt(.venv) $ pip install -r requirements.txt
Save and restore (Windows, PowerShell)
(.venv) PS> pip freeze | Out-File -Encoding utf8 requirements.txt(.venv) PS> pip install -r requirements.txt

After installing only requests, the file contains five lines:

requirements.txt
certifi==2026.10.23charset-normalizer==3.5.2idna==3.20requests==2.34.2urllib3==2.8.0

That reproduces the environment exactly, which is the point. The cost is that the file no longer shows which line you chose and which came along with it. pip freeze also leaves out pip itself.

PowerShell 5.1 writes > output as UTF-16. Microsoft documents that Windows PowerShell’s redirection operators and Out-File default to UTF-16LE, while PowerShell 7 defaults to UTF-8. pip can still read a UTF-16 file that has a byte-order mark (tested), but git, grep and many editors will treat it as garbled or binary. The Out-File -Encoding utf8 form above avoids that on both versions.

Keep two files: what you asked for and what you got

For anything beyond a script, keep the packages you chose in a short requirements.in and generate the long pinned requirements.txt from it. pip-tools does this on any system, and works in an ordinary environment.

requirements.in
requests
Compile and sync with pip-tools
(.venv) pip install pip-tools(.venv) pip-compile requirements.in # writes requirements.txt with every dependency pinned(.venv) pip-sync requirements.txt # make the environment match that file exactly

The generated file records why each package is there:

requirements.txt
## This file is autogenerated by pip-compile with Python 3.12# by the following command:##    pip-compile requirements.in#certifi==2026.10.23    # via requestscharset-normalizer==3.5.2    # via requestsidna==3.20    # via requestsrequests==2.34.2    # via -r requirements.inurllib3==2.8.0    # via requests

pip-sync also uninstalls anything the file does not list, which is why it is better than pip install -r for keeping an environment honest. (pip-compile 7 prints a warning about --strip-extras; add that flag to silence it.)

With uv, the same two steps are uv pip compile requirements.in -o requirements.txt and uv pip sync requirements.txt.

Separate development tools from what runs in production

A second input file can include the first with -r and add test tools on top.

requirements-dev.in
-r requirements.inpytest
Two environments from two files
(.venv) pip-compile requirements-dev.in # writes requirements-dev.txt(.venv) pip-sync requirements-dev.txt # development: requests and pytest(.venv) pip-sync requirements.txt # production: requests only, pytest is removed

Limit versions without installing anything

A constraints file caps versions but never asks for a package. It only applies to packages that something else installs. Use it to hold back one release you know is broken for you.

constraints.txt
urllib3<2
Install with a constraint
(.venv) pip install -r requirements.in -c constraints.txt(.venv) pip listrequests           2.34.2urllib3            1.26.20

Without the constraint, urllib3 would install as 2.8.0.

Check what you ended up with

pip check reads the installed packages and reports any whose requirements are not met. It prints one line and exits 0 when all is well, and exits 1 with a message when not:

pip check
(.venv) pip checkNo broken requirements found.(.venv) pip install --no-deps idna==2.0(.venv) pip checkrequests 2.34.2 has requirement idna<4,>=2.5, but you have idna 2.0.

The file syntax in one table

LineMeaning
# noteA comment.

-c constraints.txtApply the version limits in that file.

Pin hashes so a changed download is refused

A hash is a fingerprint of the exact file pip downloads. If a package on the index is tampered with or silently replaced, the fingerprint no longer matches and pip stops. Generate them when compiling:

Compile with hashes, install with checking
(.venv) uv pip compile --generate-hashes requirements.in -o requirements.txt(.venv) pip install --require-hashes -r requirements.txt

(pip-compile --generate-hashes does the same for pip-tools.) Each package then carries one --hash=sha256:… line per downloadable file, and a download that matches any one of them is accepted. Two things to expect:

  • Pip turns hash checking on automatically as soon as one line has a hash, and then requires hashes and exact versions for every line. A line without one fails with Hashes are required in --require-hashes mode, but they are missing from some requirements. and prints the hash you could add.
  • A mismatch fails with THESE PACKAGES DO NOT MATCH THE HASHES FROM THE REQUIREMENTS FILE, followed by the expected and the actual hash.

What to commit. Commit the requirements files (requirements.in and requirements.txt, or just requirements.txt if you use plain freeze). Never commit .venv.

Several Python versions

This is the part venv cannot do by itself. python -m venv builds the environment from whichever Python runs it, and it cannot download one. So “which version does this project use?” turns into three smaller questions: where do I get that Python, how do I pick it for this project, and where do I write the choice down?

See what you already have

Installed versions (Linux, macOS)
$ ls /usr/bin/python3.*[0-9]/usr/bin/python3.11/usr/bin/python3.12/usr/bin/python3.13$ uv python list --only-installed # if you have uv; also lists versions uv downloaded
Installed versions (Windows, PowerShell)
PS> py list # Python install manager; older launchers use: py -0

Pick a version by naming its interpreter

The simplest method needs no extra tools. Run the environment-creating command with the Python you want, and the environment gets that version.

Create with a specific version (Linux, macOS)
$ python3.12 -m venv .venv$ .venv/bin/python --versionPython 3.12.3
Create with a specific version (Windows, PowerShell)
PS> py -V:3.12 -m venv .venvPS> .venv\Scripts\python --version

Older tutorials write py -3.12. That form still works, but -V:3.12 is the one the current Python docs use.

This only works for versions your system has. Debian and Ubuntu install extra ones as packages, such as sudo apt install python3.12 python3.12-venv, but only the versions your release carries. For anything else, use one of the tools below.

Three ways to get and choose versions

Recommendation: use uv to choose versions, and keep the environment itself plain. The commands are the same on Linux and Windows, it downloads a Python in seconds without touching the system one, and it still produces an ordinary .venv that every other tool in this guide understands. Use explicit interpreters instead when you cannot install tools on the machine, and stay with pyenv when your team already runs on it.

The convention, step by step

Pick the version once for the project, write it down in a file that is committed, and create .venv from it.

Choose 3.12 for this project
uv python install 3.12 # download it, once per machineInstalled Python 3.12.13 in 1.86suv python pin 3.12 # writes .python-version in this folderPinned `.python-version` to `3.12`uv venv # creates .venv using the pinned versionUsing CPython 3.12.13Creating virtual environment at: .venv
.python-version
3.12

Anyone who clones the project and runs uv venv gets the same Python line. uv looks for .python-version in the current folder and its parents, and pyenv reads the same file, so the pin works for either tool. 3.12 means “any 3.12.x”. uv checks the Pythons it has installed first, then the ones on your PATH, and downloads a matching one only when it finds none, so the first command is optional; it just makes the download explicit. After installing a Python, uv may warn that its executable folder is not on your PATH. You can ignore that here, because uv finds the Pythons it installed by itself.

Then activate as before. uv creates environments without pip, so either use uv's own pip-compatible commands, which find .venv in the current folder even when nothing is active, or ask for pip when you create it:

Two ways to install into a uv environment
uv pip install -r requirements.txt # uv's installer; needs no pip insideuv venv --seed --clear # or: recreate with pip included, so every pip command here works as written

One environment per version, for testing

When code must work on several versions, keep the everyday environment as .venv and add one more per version, named after it: .venv-3.11, .venv-3.13. The name tells you the version at a glance, and a .venv*/ line in .gitignore covers them all.

Create one per version, then use them without activating (Linux, macOS)
$ for v in 3.11 3.12 3.13; do python$v -m venv .venv-$v; done$ for v in 3.11 3.12 3.13; do .venv-$v/bin/python -m pip install -q -r requirements.txt; done$ for v in 3.11 3.12 3.13; do .venv-$v/bin/python -c "import sys, requests; print(sys.version.split()[0], requests.__version__)"; done3.11.17 2.34.23.12.3 2.34.23.13.16 2.34.2
Create one per version, then use them without activating (Windows, PowerShell)
PS> foreach ($v in "3.11","3.12","3.13") { py "-V:$v" -m venv ".venv-$v" }PS> foreach ($v in "3.11","3.12","3.13") { & ".venv-$v\Scripts\python" -m pip install -q -r requirements.txt }

With uv, uv venv .venv-3.13 --python 3.13 creates one, and the version is downloaded first if it is missing. Calling each environment's Python by path, rather than activating it, is what makes loops like these work: there is no state to switch.

Move a project to another version

Do not try to convert an environment. Delete it and create a new one, then reinstall from the requirements file.

Switch the project to Python 3.13 (Linux, macOS)
(.venv) $ deactivate$ rm -rf .venv$ python3.13 -m venv .venv$ source .venv/bin/activate(.venv) $ pip install -r requirements.txt(.venv) $ python --versionPython 3.13.16
Switch the project to Python 3.13 (Windows, PowerShell)
(.venv) PS> deactivatePS> Remove-Item -Recurse -Force .venvPS> py -V:3.13 -m venv .venvPS> .venv\Scripts\Activate.ps1(.venv) PS> pip install -r requirements.txt

With uv: uv python pin 3.13, then uv venv --clear. Without --clear uv refuses to overwrite an existing .venv and tells you to add it. Exact pins can fail on a new Python version, for example when a pinned release has no build for it. If so, regenerate the pins from requirements.in rather than editing them by hand.

pyenv on Linux and macOS

pyenv installs Python versions side by side under your home folder and uses small wrapper programs called shims to decide which one python means. It builds each version from source, so install your system's build dependencies first (the pyenv wiki lists them per distribution).

pyenv, then a plain venv (Linux, macOS)
$ pyenv install --list # every version that can be built$ pyenv install 3.12.3 # compile and install one$ pyenv local 3.12.3 # writes .python-version in this folder$ python -m venv .venv # python now resolves to 3.12.3

pyenv picks a version in this order: the PYENV_VERSION variable (set per terminal with pyenv shell), then the nearest .python-version file in the current folder or a parent, then the global default from pyenv global. pyenv versions lists what is installed and marks the active one. pyenv does not manage environments; a separate plugin, pyenv-virtualenv, does, and plain python -m venv as above is enough for this guide’s conventions.

These pyenv commands come from its README and were not run for this guide.

The Windows Python install manager

Current Python releases for Windows are installed with the Python install manager, which provides the py and python commands. It replaces the older “py launcher” that came with the full installer.

Install manager commands (Windows, PowerShell)
PS> py install 3.12 # download and install a versionPS> py list # what is installedPS> py uninstall 3.12 # remove onePS> py -V:3.12 -m venv .venv # use a specific one

If you installed the older launcher as well, it can take over the py command and produce errors such as “can't open file”; the Python docs cover the fix. With an environment active, py runs that environment's Python. These commands come from the official Windows documentation and were not run for this guide.

Project conventions

These rules keep every project predictable. They are the ones the rest of the guide already follows.

myproject/The project.
├─ .venv/Local only, never committed.
├─ .python-versionCommitted. Contains 3.12.
├─ .gitignoreContains .venv*/
├─ requirements.inCommitted. What you asked for.
├─ requirements.txtCommitted. Every package, pinned.
├─ requirements-dev.inCommitted. Adds test tools.
├─ requirements-dev.txtCommitted. The same, pinned.
└─ README.mdSetup steps for the next person.
  1. One environment per project, inside the project. Never install a project's packages into the system Python.
  2. Use the same name everywhere. .venv for the everyday one, .venv-3.13 style for extra versions.
  3. Commit the recipe, not the result. Requirements files and .python-version go in git; the environment does not. A line in .gitignore keeps it out:
    .gitignore
    .venv*/
    Python 3.13 and later, and uv, also write a .gitignore containing * inside the environment, which hides it from git. Python 3.12 and earlier do not, so keep your own line.
  4. Recreate rather than repair. If an environment behaves strangely, delete it and rebuild from the requirements file. It takes seconds.
  5. Call the environment's Python by path in anything unattended. Cron jobs, services and CI should run .venv/bin/python.venv\Scripts\python rather than rely on a shell that activated something.
  6. Make pip refuse to run outside an environment. This turns the classic mistake of installing globally into an immediate error:
    Require an environment for pip
    pip config set global.require-virtualenv trueWriting to /home/ada/.config/pip/pip.confpip install requests # outside any environmentERROR: Could not find an activated virtualenv (required).
    It also blocks the rare deliberate global install. Set PIP_REQUIRE_VIRTUALENV=false for a single command to override it.
  7. Write the setup steps in the README so the next person, or you in six months, can start without asking.

$ git clone <your-repo-url> myproject$ cd myproject$ python3 -m venv .venv$ source .venv/bin/activate(.venv) $ pip install -r requirements.txt
First run on a new machine (Windows, PowerShell)

Troubleshooting

Each heading is the message you will see. The Linux messages below were produced for this guide, and the Windows ones come from the official documentation.

error: externally-managed-environment

You ran pip install against a system Python that its distribution manages (the check is called PEP 668). Recent Debian and Ubuntu releases mark their system Python this way. The message itself says what to do: use an environment.

Fix (Linux, macOS)
$ python3 -m venv .venv$ source .venv/bin/activate(.venv) $ pip install requests

pip also offers --break-system-packages. It exists for the rare case you really want to change the system Python, and it can break tools your system relies on.

ensurepip is not available

Debian and Ubuntu split the venv module into its own package. Without it, creating an environment fails with this text:

Message
The virtual environment was not created successfully because ensurepip is notavailable.  On Debian/Ubuntu systems, you need to install the python3-venvpackage using the following command.    apt install python3.12-venv

Install the package for the version you are using (the number in the message is the version), then run the create command again. sudo apt install python3.12-venv is the full form.

Permission denied when activating (Linux)

You ran the script instead of sourcing it. Compare the two forms:

Wrong, then right (Linux, macOS)
$ ./.venv/bin/activatebash: ./.venv/bin/activate: Permission denied$ source .venv/bin/activate

No such file or directory when activating

The path does not exist from where you are: you are in the wrong folder, the environment was never created, or the folder is named something else. Run ls -aGet-ChildItem -Force and check that .venv is there. On Windows the activation scripts live in Scripts, not bin, and a command copied from a Linux guide fails on the first line.

deactivate: command not found

Nothing is active in this terminal, or you activated in a different window. deactivate only exists while an environment is on. There is nothing to undo, so carry on.

Running scripts is disabled on this system (Windows)

PowerShell's execution policy is blocking Activate.ps1. Allow local scripts for your account once with Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser, or activate with .venv\Scripts\activate.bat from cmd.exe instead.

The package installed, but Python cannot import it

Almost always pip and python belong to different environments. Ask both where they live:

Find out which Python and pip you are using (Linux, macOS)
(.venv) $ which python(.venv) $ python -m pip --version
Find out which Python and pip you are using (Windows, PowerShell)
(.venv) PS> (Get-Command python).Source(.venv) PS> python -m pip --version

Both paths should be inside .venv. If not, activate the environment or call its Python by path, then install again with python -m pip install. If an editor shows import errors even though the terminal works, point the editor's Python interpreter setting at .venv/bin/python.venv\Scripts\python.exe.

cannot execute: required file not found after moving a folder

Scripts such as pip start with the absolute path of the Python they were created for. Move or rename the environment, or the project that holds it, and that path goes stale:

What a moved environment does (Linux, macOS)
$ mv old-project/.venv new-project/.venv$ cd new-project$ .venv/bin/pip --versionbash: .venv/bin/pip: cannot execute: required file not found$ source .venv/bin/activate(.venv) $ which python/usr/bin/python

The last two lines are the dangerous part. Activation did not fail, but it kept the old VIRTUAL_ENV path, so python quietly became the system Python and anything you install goes to the wrong place. python -m pip may still appear to work for the same reason. (If the folder path is very long, over roughly 120 characters, pip prints pip: 2: exec: …/python3.12: not found instead. It is the same problem with the same fix.) Delete the moved folder and create a new one; there is nothing worth rescuing.

python or pip says “No such file or directory” in a working-looking environment

The environment's python is a link to the Python that created it. If that Python was upgraded to a new version, uninstalled, or moved, the link points at nothing:

A dangling link (Linux, macOS)
$ .venv/bin/python --versionbash: .venv/bin/python: No such file or directory$ .venv/bin/pip --versionbash: .venv/bin/pip: cannot execute: required file not found

Check the home = line of pyvenv.cfg to see which Python it expected, then recreate the environment from your requirements file. This commonly follows a system upgrade that replaces one Python version with the next.

pip or python fails after moving the folder or upgrading Python (Windows)

The causes are the same as on Linux. The programs in Scripts carry the absolute path of the folder they were created in, and python.exe depends on the Python that created it. Rename or move .venv, or uninstall or replace that Python, and the environment stops working. The exact error text on Windows was not captured for this guide. The fix does not depend on it: check the home = line of pyvenv.cfg, then delete the environment and recreate it from your requirements file.

No module named pip in a uv environment

uv leaves pip out of environments it creates, so python -m pip fails there:

The error, and two fixes
.venv/bin/python -m pip --version.venv/bin/python: No module named pipuv pip install requests # fix 1: use uv's installeruv venv --seed --clear # fix 2: recreate the environment with pip inside

The new environment has the wrong Python version

The environment copies whichever Python ran -m venv, and plain python3python is whatever your PATH finds first. Check what you got and rebuild with the interpreter named explicitly:

Check, then rebuild (Linux, macOS)
$ .venv/bin/python --version$ grep version .venv/pyvenv.cfg$ rm -rf .venv && python3.12 -m venv .venv
Check, then rebuild (Windows, PowerShell)
PS> .venv\Scripts\python --versionPS> Select-String version .venv\pyvenv.cfgPS> Remove-Item -Recurse -Force .venv; py -V:3.12 -m venv .venv

If you use pyenv and a .python-version file seems to be ignored, pyenv is probably not set up in this shell, so python still resolves to the system one. pyenv version prints what it thinks is selected.

py starts the wrong Python or says “can't open file” (Windows)

When both the older py launcher and the Python install manager are installed, the older one can take over the py command. Remove the older launcher, or use python directly. The current Python docs for Windows describe the conflict.

requirements.txt is unreadable in git or an editor (Windows)

You created it with > in Windows PowerShell 5.1, which writes UTF-16. Recreate it with pip freeze | Out-File -Encoding utf8 requirements.txt.

How this was checked

Every Linux command in this guide was run on a Debian-based system with Python 3.11, 3.12 and 3.13, pip 24.0, uv 0.11.32 and pip-tools 7.6.2, and the outputs shown are what they printed. Folder paths are shortened to /home/ada/myproject. Package versions are the ones that installed on 28 October 2026.

The Windows commands, the Python install manager, and the pyenv commands were taken from their official documentation and were not run, because none of them can run on the system this guide was written on. The PowerShell encoding behaviour comes from Microsoft's documentation, and pip's reading of UTF-16 and UTF-8 files with a byte-order mark was tested. macOS uses the Linux commands for everything here, and was not tested separately.
