01The operating model

Know what Btrfs owns, what a snapshot protects, and where the boundaries are.

Btrfs combines a Linux filesystem with its own multi-device allocator. It checksums metadata and, by default, file data; copy-on-write updates point to newly written extents. Subvolumes provide independently managed file trees within one filesystem. Snapshots initially share extents with their source and diverge as either tree changes.

LayerIdentityWhat you administer
Physical storageDrive serial, WWN, partition pathHardware health, cables, partitions, encryption mapping
Btrfs filesystemFilesystem UUID (FSID)Device membership, allocation profiles, free space, scrub
Member devicedevid inside that filesystemReplace a particular member; IDs are not Linux sdX letters
SubvolumeSubvolume ID and UUIDSnapshot, mount, delete, send/receive
Mounted viewPath such as /srv/dataThe part of the file tree a process can see
Three different protections: RAID copies help survive a device failure. Snapshots help recover an earlier file-tree state. Backups on another failure domain help survive losing the filesystem itself. Use all three when the data warrants it.

What a root snapshot does not promise

A root snapshot does not automatically include separate subvolumes, other filesystems, an EFI System Partition, or application state held only in memory. It also does not repair a dying disk. Plan recovery around the actual boundaries rather than the directory names visible under /.

Record the actual environment

Keep a Debian live/rescue USB that can mount the filesystem features you use. For root filesystems, compatibility includes GRUB and initramfs as well as Linux. 05Profiles, redundancy, and usable capacity

Choose data and metadata policies deliberately.

ProfileCopies / minimum devicesPractical meaning
singleOne copy / 1No device-failure tolerance for extents stored on a lost device.
DUPTwo copies / 1Two copies on the same device; useful for metadata, not protection against losing that device.
RAID1Two copies / 2A healthy all-RAID1 filesystem can lose one entire device while retaining at least one copy of every allocated block.
RAID1C3 / RAID1C4Three / four copies; 3 / 4 devicesMore redundancy at higher capacity cost; an advanced choice, not the default here.
RAID10Mirrored stripes / 4Performance-oriented multi-device layout; do not assume arbitrary multiple-device failures are survivable.
RAID0Striped, no redundancy / 2Losing a member can lose the filesystem.
RAID5 / RAID6Parity layoutsOverview only: upstream still flags RAID56 limitations. No parity setup recipes in this guide.

For a two-drive home-server filesystem, the worked examples use data=raid1 and metadata=raid1. With two 4 TB disks, roughly one disk’s capacity is available before filesystem overhead and decimal/TiB differences. Two unequal drives are limited by the smaller member for two-copy storage; with three or more devices, allocation is more flexible but depends on the distribution of free space.

Check Data, Metadata, and System profiles after conversions or degraded operation. A filesystem may contain more than one profile at once. A RAID1 label in one line does not prove every extent has redundancy.
Inspect all allocation profiles
sudo btrfs filesystem usage -T /srv/data
sudo btrfs filesystem df /srv/data

06Create a filesystem on prepared devices

Choose one format recipe. Both destroy existing contents on the selected partitions.

Prerequisites: backed-up disks, already-created empty partitions, and reviewed device identity. Partitioning the disk is outside these format commands. The data examples use one partition per disk and do not modify an installed operating system’s boot disk.

Inspect the proposed targets
D1=/dev/disk/by-id/REPLACE_ME_DISK_A-part1
D2=/dev/disk/by-id/REPLACE_ME_DISK_B-part1
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS "$D1" "$D2"
sudo wipefs --no-act "$D1" "$D2"
swapon --show

Stop: both targets must be the intended expendable partitions, unused by mounts, swap, or another storage stack. No force flag is included. Choose exactly one format option below.

Format one data disk
sudo mkfs.btrfs -L archive -d single -m dup "$D1"
Format a two-disk mirrored filesystem
sudo mkfs.btrfs -L archive -d raid1 -m raid1 "$D1" "$D2"

After the chosen format completes, mount the administrative top level and record its UUID:

Mount and verify
FS_UUID=$(sudo blkid -s UUID -o value "$D1")
sudo mkdir -p /mnt/btrfs-top
sudo mount -t btrfs -o subvolid=5,compress=zstd:3 "UUID=$FS_UUID" /mnt/btrfs-top
sudo btrfs filesystem show /mnt/btrfs-top
sudo btrfs filesystem usage -T /mnt/btrfs-top
What to expect · illustrative
For the mirror recipe: two devices; Data, RAID1 and Metadata, RAID1.
The filesystem UUID is the same when read from either member.

If the profiles or members are unexpected, correct the design before storing real data. Do not repeatedly reformat while troubleshooting a filesystem containing files you want.

07Create the data subvolume layout

Choose snapshot boundaries based on recovery needs.

Create and mount the working tree
sudo btrfs subvolume create /mnt/btrfs-top/@data
sudo btrfs subvolume create /mnt/btrfs-top/@snapshots
sudo mkdir -p /mnt/btrfs-top/@snapshots/data
sudo mkdir -p /srv/data
sudo mount -t btrfs -o subvol=@data,compress=zstd:3 "UUID=$FS_UUID" /srv/data
sudo btrfs subvolume list -p /mnt/btrfs-top

Use ordinary directories within @data unless you need a separate snapshot, send, quota, or retention boundary. A separate subvolume is not a security boundary by itself and does not reserve space. Use normal ownership and permissions for application access. Newly created subvolumes are normally root-owned; grant access to a specific working directory rather than making the filesystem top level writable to everyone.

Create a personal working directory from your normal user shell
sudo install -d -m 0750 -o "$(id -un)" -g "$(id -gn)" /srv/data/documents
Verify the mounted subvolume
findmnt -T /srv/data -o TARGET,SOURCE,FSROOT,OPTIONS
sudo btrfs subvolume show /srv/data
Snapshots do not recurse into nested subvolumes. A snapshot of a parent leaves a placeholder where a nested child subvolume lived; it does not capture that child’s contents. Explicitly snapshot/replicate each child you need.

Keeping snapshots as siblings outside the live tree makes their purpose obvious. Do not put a backup destination inside the source tree and then let a recursive file-backup tool chase its own output.

Create & mount

08Persistent mounts and mount-option scope

Make the normal boot predictable before relying on snapshots.

Add these entries to /etc/fstab with the actual filesystem UUID. These are data-volume examples, not root-migration instructions. Keep the filesystem-wide options consistent on both mounts.

fstab data-volume example
UUID=REPLACE_ME_FS_UUID /srv/data btrfs defaults,subvol=@data,compress=zstd:3 0 0
UUID=REPLACE_ME_FS_UUID /mnt/btrfs-top btrfs defaults,subvolid=5,compress=zstd:3 0 0
Validate configuration
sudo findmnt --verify --verbose
sudo systemctl daemon-reload
findmnt -t btrfs -o TARGET,SOURCE,FSROOT,OPTIONS

If these paths are already mounted, editing fstab does not retest a fresh mount. During a maintenance window stop dependent services, unmount the relevant data mounts, then mount by fstab target and verify. Keep a rescue shell open when changing boot-critical entries.

Mount previously unmounted data targets
sudo mount /mnt/btrfs-top
sudo mount /srv/data

Most Btrfs mount options, including compression policy, apply filesystem-wide; the first mount matters. Use per-file or per-directory properties for exceptions. Retain normal atime behavior unless you understand the application tradeoff; noatime is optional, not mandatory tuning.

Avoid nofail for storage a service requires unless that service also verifies the mount. Otherwise it may start writing to an empty directory on the root filesystem when the data disk is absent. Add explicit systemd mount dependencies to the service.

09Inspect filesystems, subvolumes, and errors

Read the right view before changing anything.

Inspection kit
findmnt -t btrfs -o TARGET,SOURCE,FSROOT,OPTIONS
sudo btrfs filesystem show /srv/data
sudo btrfs filesystem usage -T /srv/data
sudo btrfs device usage /srv/data
sudo btrfs device stats /srv/data
sudo btrfs subvolume list -p -u -q /mnt/btrfs-top
sudo btrfs subvolume get-default /mnt/btrfs-top

A mount’s FSROOT identifies its subvolume view. The default subvolume is used when a mount omits an explicit subvol/subvolid; it is not necessarily the root your bootloader selects. Device counters record I/O/checksum/generation errors; a nonzero value is evidence to investigate, not an automatic diagnosis of bad media.

Correlate filesystem and hardware evidence
sudo journalctl -k -b --no-pager
sudo smartctl -x /dev/disk/by-id/REPLACE_ME_DISK_A

Check drive health on the whole physical drive, not its Btrfs partition. Controller resets, power loss, cables, USB bridges, and memory errors can resemble filesystem trouble. Save counters and kernel logs before clearing anything.

10Space accounting and ENOSPC

Free space has several meanings on a copy-on-write filesystem.

ReadingMeaningHow to use it
Device size / allocated / unallocatedPhysical capacity assigned to block groups or still availableInspect per-device headroom, especially during conversions.
Data / Metadata total vs usedLogical capacity of allocated block groups and occupancyAllocated-but-unused is not the same as device-unallocated.
Estimated free spaceEstimate based on current profiles and allocationUseful for planning, not a guarantee every future write fits.
du / apparent file sizeDirectory/file view; sharing may be counted differentlyCannot alone explain snapshot-pinned space.
Global reserveInternal metadata emergency reserveNot an administrator’s spare disk space to consume.
Compare the layers
df -h /srv/data
sudo btrfs filesystem usage -T /srv/data
sudo btrfs device usage /srv/data
sudo btrfs filesystem du -s /srv/data /mnt/btrfs-top/@snapshots/data

Plan headroom; a starting operational target is keeping roughly 15–20% free, adjusted for snapshot churn, large rewrites, and device topology. This is a planning convention, not a Btrfs guarantee. A large VM rewrite can consume shared space quickly even if the visible file size barely changes.

When a write says “No space left on device”

  • Pause heavy writers. Inspect data and metadata allocation on every device; also check quota limits.
  • Delete only identified disposable files or snapshots whose backups and incremental-base requirements are understood. Deleting snapshots frees extents asynchronously.
  • Wait for completed snapshot deletion with btrfs subvolume sync, then recheck usage.
  • If unused block groups are consuming allocation, the usage=0 balance in the balance chapter can reclaim them.
  • If workspace is genuinely exhausted, add planned capacity or restore elsewhere. Do not start an unfiltered balance or a repair command as a reflex.

A file removed from the live tree may still be held by snapshots, reflinks, or an open process. Truncating a shared large file is not a dependable emergency-space remedy.

Snapshots & backups

11Create and inspect snapshots

Make a named checkpoint you can explain and restore.

A snapshot is fast because it starts by sharing extents; it is not a full copy and does not stop applications. Stop or quiesce applications when you require a consistent database/application state. Snapshot each independent subvolume explicitly.

Create a read-only data checkpoint
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
SNAP=/mnt/btrfs-top/@snapshots/data/data-$STAMP
sudo btrfs subvolume snapshot -r /srv/data "$SNAP"
sudo btrfs subvolume show "$SNAP"
sudo btrfs property get -ts "$SNAP" ro
What to expect · illustrative
ro=true
Subvolume show identifies the new UUID and its relationship to the source.

The read-only flag protects the snapshot tree, not the whole filesystem or the hardware. Keep replication bases read-only for their entire lifetime. Do not toggle a received snapshot writable for experiments; make a separate writable snapshot instead.

Create an independent writable test tree
sudo btrfs subvolume snapshot "$SNAP" /mnt/btrfs-top/@data-test

Changes in @data-test do not modify the preserved snapshot or live data, although all three still share the same filesystem and physical failure domain. There is no need to “promote” the writable snapshot as in a ZFS clone workflow.

12Restore a file or directory

Recover into a staging location first, then replace deliberately.

Choose a known checkpoint, inspect its contents, and compare the destination. The examples use an ordinary directory named documents; no nested subvolume is implied. Preserve ownership, ACLs, and xattrs when those matter.

Preview a recovery copy
SNAP=/mnt/btrfs-top/@snapshots/data/REPLACE_ME_SNAPSHOT
sudo ls -la "$SNAP/documents"
sudo mkdir -p /srv/data/recovered-documents
sudo rsync -aHAX --numeric-ids --dry-run -- "$SNAP/documents/" /srv/data/recovered-documents/

After reviewing the preview, copy into that recovery directory. There is no delete flag.

Recover the selected directory
sudo rsync -aHAX --numeric-ids -- "$SNAP/documents/" /srv/data/recovered-documents/

Open representative files and run application validation before putting recovered data back into service. A trailing slash on the source means copy its contents. For a single file, copying to a new name first is an easy way to preserve the current version.

For a database, restore the complete database recovery unit with its application stopped and its required version available. Copying one live database file from a filesystem snapshot can make matters worse. See application consistency.

13Retention and safe deletion

A snapshot policy includes how you stop keeping snapshots.

A useful starting policy is short-term hourly snapshots, a week or two of daily snapshots, and a small set of explicit pre-maintenance checkpoints. Choose counts from measured churn and recovery needs. Do not keep every snapshot forever merely because creation was cheap.

  • Name snapshots with a UTC timestamp and log the reason separately.
  • Keep the newest successfully replicated base on both sender and receiver until its successor is confirmed.
  • Keep at least one tested root checkpoint covering the current maintenance window.
  • Prune according to successful backups and available headroom, not just age.
  • Exclude mounted snapshots, active boot environments, and anything a send operation is currently using.
Inspect one deletion candidate
sudo btrfs subvolume list -r /mnt/btrfs-top
sudo btrfs subvolume show /mnt/btrfs-top/@snapshots/data/REPLACE_ME_OLD_SNAPSHOT

Once that exact snapshot is confirmed expendable and is not needed as an incremental base:

Delete one selected snapshot
sudo btrfs subvolume delete /mnt/btrfs-top/@snapshots/data/REPLACE_ME_OLD_SNAPSHOT
Wait for reclamation and recheck space
sudo btrfs subvolume sync /mnt/btrfs-top
sudo btrfs filesystem usage -T /srv/data

Deletion removes a tree reference; only extents no longer referenced elsewhere can be reclaimed. Avoid piping broad filename matches into deletion. Keep cleanup scripts narrowly scoped and give them a dry-run mode.

14Full send/receive to a separate filesystem

Create a backup copy whose failure domain is actually different.

Assume the source uses the data layout above and a separate Btrfs filesystem is mounted at /mnt/btrfs-backup with subvolid=5. A second directory on the source is not this backup. Confirm UUIDs and physical devices before sending.

Inspect and prepare the receiver
findmnt -T /srv/data -o SOURCE,FSROOT
findmnt -T /mnt/btrfs-backup -o SOURCE,FSROOT
sudo btrfs filesystem show /mnt/btrfs-backup
sudo mkdir -p /mnt/btrfs-backup/host-a-data

Create a read-only source checkpoint and then stream it. The example snapshot name is illustrative and must not already exist.

Create the first replication base
S1=/mnt/btrfs-top/@snapshots/data/data-20261029T180000Z
sudo btrfs subvolume snapshot -r /srv/data "$S1"
Bash: send the complete snapshot
set -o pipefail
sudo btrfs send "$S1" | sudo btrfs receive /mnt/btrfs-backup/host-a-data

A pipeline failure is a failed backup. Do not prune the source or call the destination complete merely because a directory appeared. The receiver turns the destination read-only only after successful completion.

Verify successful receive identity
sudo btrfs subvolume show "$S1"
sudo btrfs subvolume show /mnt/btrfs-backup/host-a-data/data-20261029T180000Z
sudo btrfs property get -ts /mnt/btrfs-backup/host-a-data/data-20261029T180000Z ro

The receiver has its own UUID and a received UUID tied to the sent snapshot. Inspect files and perform an actual restoration test. Send/receive transfers one subvolume per source argument; it does not silently include every nested subvolume. Restrict write access to the receiver directory while receiving and accept streams only from trusted sources.

Snapshots & backups

15Incremental sends, SSH, and interrupted transfers

The last successful immutable base is part of your backup protocol.

After the full backup above succeeds, create the next read-only snapshot. Keep S1 and its received counterpart unchanged; the incremental stream describes the changes needed to construct S2 from that base.

Create the next daily checkpoint
S1=/mnt/btrfs-top/@snapshots/data/data-20261029T180000Z
S2=/mnt/btrfs-top/@snapshots/data/data-20261030T180000Z
sudo btrfs subvolume snapshot -r /srv/data "$S2"
Bash: transmit only the delta
set -o pipefail
sudo btrfs send -p "$S1" "$S2" | sudo btrfs receive /mnt/btrfs-backup/host-a-data

Verify S2’s received identity, read-only flag, and restoration before retiring older checkpoints. A future S3 can use S2 as its base, so S1 need not be retained forever once it has no remaining policy or transfer role.

Send to another Debian machine

On the receiver, prepare the Btrfs mount and destination directory first. The remote destination must already hold a successfully received, unchanged read-only S1; a base received only on your local backup disk does not satisfy this. For the first remote transfer, use btrfs send "$S1" with the SSH receive pipeline below, verify it, and only then send S2 incrementally. Establish SSH host-key trust and a narrowly designed privileged receive path. The following assumes the remote account is already permitted to run this exact receive operation non-interactively; it does not configure that privilege.

Bash: remote incremental transfer
set -o pipefail
sudo btrfs send -p "$S1" "$S2" | ssh backup-host 'sudo -n btrfs receive /mnt/btrfs-backup/host-a-data'

Do not grant unrestricted passwordless root or generic Btrfs access just to make a pipeline work. The remote receive operation has filesystem-changing power. A dedicated backup service or reviewed restricted wrapper can enforce the intended destination.

Recover from an interrupted receive

Stop the transfer and inspect the receiver. A partially received destination may remain writable and must not be treated as a valid incremental base. Preserve the last successful base. After confirming the exact failed destination, delete only that incomplete subvolume, then resend S2 using the same verified S1. Native send/receive is not an rsync-style byte-offset resume operation.

For a stream file instead of a live pipe, store it on a different filesystem, check the send exit status, and checksum the file. Protect its contents as backup data; it is not inherently encrypted.

Snapshots & backups

16Restore from another Btrfs filesystem

A backup is proven when you can turn it back into a working tree.

Assume a healthy destination filesystem has the administrative top-level mount at /mnt/btrfs-top. The source is a verified read-only snapshot on the backup filesystem. You cannot create a Btrfs snapshot directly across filesystems; receive it first.

Bash: receive the backup into the destination
sudo mkdir -p /mnt/btrfs-top/restore-inbox
set -o pipefail
sudo btrfs send /mnt/btrfs-backup/host-a-data/data-20261029T180000Z | sudo btrfs receive /mnt/btrfs-top/restore-inbox
Create and mount a writable recovery tree
FS_UUID=REPLACE_ME_DESTINATION_FS_UUID
sudo btrfs subvolume snapshot /mnt/btrfs-top/restore-inbox/data-20261029T180000Z /mnt/btrfs-top/@data-restored
sudo mkdir -p /mnt/data-restored
sudo mount -t btrfs -o subvol=@data-restored "UUID=$FS_UUID" /mnt/data-restored

Verify ownership, ACLs, representative file hashes, and the application’s integrity checks. Stop the application before changing its mount or moving recovered files into production. For a full swap, change the data mount’s fstab subvolume path to the tested recovery tree during downtime, unmount the old view, mount the new view, and confirm findmnt before starting the service.

This is also a disaster-recovery drill: receive onto a spare disk or VM, restore a writable tree, and start a test copy of the application. A successful scrub of the backup alone does not test the restoration procedure.

Keep the original read-only received snapshot until recovery is accepted. Retain an independent offline or off-site copy if both source and backup are normally accessible to the same administrator or ransomware event.

Operate & inspect

17Compression that is easy to reason about

Start with a moderate policy and measure actual workloads.

compress=zstd:3 is a practical starting convention for these examples. It is not an optimum for every CPU or workload. Compression normally affects newly written extents; enabling it does not automatically rewrite old files. Already compressed media often has little left to gain.

Inspect mount policy and an inode override
findmnt -T /srv/data -o OPTIONS
sudo btrfs property get /srv/data compression

A missing compression property does not mean the mount policy is disabled. The inode property is an override and accepts an algorithm, not a level. Use it on a directory before creating files when a specific subtree needs a policy.

Set a directory compression policy
sudo btrfs property set /srv/data/documents compression zstd

To recompress a selected existing file, defragmentation can rewrite it, but may break extent sharing with snapshots/reflinks and substantially increase space use. Keep headroom and test one file before considering bulk work.

Rewrite one selected file with compression
sudo btrfs filesystem defragment -czstd /srv/data/documents/REPLACE_ME_FILE

Do not schedule recursive defragmentation across snapshot-heavy trees as routine maintenance. Balance relocates block groups and is not a compression pass. A writable snapshot is a cheap place to test changes, but its growth still consumes the same underlying filesystem.

18Reflinks, NOCOW, and defragmentation

Know what you give up when optimizing write-heavy files.

Create a sharing-based file copy
cp --reflink=always -- /srv/data/source.img /srv/data/test-copy.img

Within the same Btrfs filesystem, reflinks initially share file extents. Later writes diverge. The copy is not independent protection against losing the disk. --reflink=always fails if the requested sharing operation cannot be performed instead of silently making a full copy.

NOCOW is an explicit exception

For selected VM/database workloads, an empty directory with +C makes new files inherit NOCOW. This also removes ordinary file-data checksums and compression for those files. Metadata remains checksummed. On a mirror, Btrfs cannot use a missing data checksum to decide which of two silently divergent NOCOW copies is correct.

Set NOCOW before files are created
sudo mkdir /srv/data/vm-nocow
sudo chattr +C /srv/data/vm-nocow
lsattr -d /srv/data/vm-nocow

Setting the attribute on a populated directory does not convert all existing file contents. Migration requires stopped applications and deliberate copying into newly created files, without reflink sharing; validate both bytes and resulting attributes. Keep the old data until accepted.

Snapshots can still force copy-on-write when otherwise NOCOW extents are shared. Benchmark with your actual snapshot cadence. Prefer the default checksummed COW path unless a measured problem and the workload’s own integrity/backup mechanisms justify the exception. Autodefrag is likewise workload-specific; leave it off in the baseline here.

19Scrub and health monitoring

Validate stored copies, then investigate what changed.

Start and monitor a normal scrub
sudo btrfs scrub start /srv/data
sudo btrfs scrub status -d /srv/data

The first command normally backgrounds the scrub. For a supervised maintenance run, use the foreground alternative instead:

Run a foreground scrub
sudo btrfs scrub start -B -d /srv/data

Do not run both as if they were consecutive steps. The foreground exit status matters; read the final counts and kernel log, not just the process return. A normal read-write scrub can repair a damaged checksummed copy using a verified redundant copy. On single-copy data it can detect corruption without being able to reconstruct the file.

Inspect evidence after a scrub
sudo btrfs device stats /srv/data
sudo journalctl -k --since "2 hours ago" --no-pager

A practical starting cadence is monthly scrubs plus alerts for failures and new device errors. Adjust to workload and acceptable detection delay. Scrub is not a full hardware burn-in, a backup, or the offline structural checker.

Cancel or resume an interrupted scrub

Cancel the current scrub
sudo btrfs scrub cancel /srv/data
Resume using saved scrub state
sudo btrfs scrub resume /srv/data

These are alternatives for a known running/interrupted job. For evidence preservation, note that scrub -r on a read-write mount may still cause writes through implementation details; use a read-only mount and an appropriate recovery procedure if avoiding writes is essential.

Maintenance

20Balance: relocation, not a healing button

Use a reason, a filter, and a completion check.

Balance rewrites selected block groups to satisfy allocation constraints or change profiles. It does not replace a failed drive, scrub file contents, defragment files, or recompress extents. A full unfiltered balance can be expensive and requires working space. It is not a default monthly chore.

Inspect before balancing
sudo btrfs balance status /srv/data
sudo btrfs filesystem usage -T /srv/data

Reclaim entirely empty block groups

Reclaim unused allocations
sudo btrfs balance start -dusage=0 -musage=0 /srv/data

This filter handles empty groups and normally avoids needing relocation workspace. For lightly occupied data groups, start with a limited batch, then inspect rather than repeatedly raising the threshold blindly:

Relocate at most ten sparsely used data groups
sudo btrfs balance start -dusage=5,limit=10 /srv/data
Check the result
sudo btrfs filesystem usage -T /srv/data
sudo btrfs balance status /srv/data

Control a known active balance

Pause
sudo btrfs balance pause /srv/data
Resume a paused balance
sudo btrfs balance resume /srv/data
Cancel
sudo btrfs balance cancel /srv/data

Those are separate choices. An interrupted balance may resume when mounted; skip_balance is a recovery-time way to prevent automatic resumption while investigating. Profile conversion can temporarily leave mixed profiles, so completion and a post-conversion profile check are required.

Devices & recovery

21Add a device and convert profiles

Adding space alone does not create redundancy for existing extents.

Starting state: a healthy single-device filesystem using single data and DUP metadata, with a tested backup and enough conversion workspace. The new partition is empty, unmounted, and at least large enough for the planned mirrored allocation. Adding an undersized disk may make full conversion impossible.

Verify the addition
NEW=/dev/disk/by-id/REPLACE_ME_NEW_DISK-part1
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS "$NEW"
sudo wipefs --no-act "$NEW"
sudo btrfs filesystem usage -T /srv/data
Add the reviewed empty partition
sudo btrfs device add "$NEW" /srv/data

The filesystem now has another member, but old single-copy data is still single-copy. Convert both data and metadata when the healthy device set and available space support it:

Convert the filesystem to two-copy allocation
sudo btrfs balance start -dconvert=raid1 -mconvert=raid1 /srv/data
Verify completed conversion
sudo btrfs balance status /srv/data
sudo btrfs filesystem usage -T /srv/data
sudo btrfs filesystem df /srv/data

Do not declare one-drive failure tolerance until every relevant data and metadata block group has converted and the system profile is appropriate. If the operation stops for lack of space, inspect the mixed state and capacity constraints; do not remove a device or force a lower-redundancy profile to hide the problem. Keep the tested backup.

Devices & recovery

22Grow, shrink, and remove healthy devices

Distinguish filesystem space from partition and encryption layers.

Grow after a larger device or underlying partition is ready

Btrfs can grow to the capacity already exposed by its block device. For a multi-device filesystem specify the member ID; the example expands devid 2. Resize any outer partition/LUKS layer first using its own supported procedure.

Grow a selected member to its exposed maximum
sudo btrfs filesystem show /srv/data
sudo btrfs filesystem resize 2:max /srv/data
sudo btrfs device usage /srv/data

One larger disk in a two-disk RAID1 filesystem does not by itself provide a matching second copy for all of its extra capacity. Replace or expand the other member too if the goal is to use that extra space with two-copy allocation.

Shrink from the inside out

Back up first, inspect devid and byte sizes, and choose an explicit target safely above allocated requirements. Shrinking relocates extents and can fail if they cannot fit. The following number is an example, not a recommendation for your device:

Example: shrink member 1 to 800 GiB
sudo btrfs filesystem resize 1:800G /srv/data

Only after successful filesystem shrink and verification may an underlying partition/container be shortened, with a size that still contains the complete Btrfs device. Preserve partition start sectors. Exact partition/LUKS edits are intentionally not combined with this example; unit mistakes can destroy the filesystem.

Remove a healthy member from a larger filesystem

Example: three healthy devices with all relevant profiles RAID1, and enough remaining capacity on the two survivors. Choose the intended member by its confirmed ID:

Evacuate and remove healthy devid 3
sudo btrfs device remove 3 /srv/data

The operation relocates its allocations. It is not “forget the disk.” Inspect profiles and device membership afterwards. Do not use this recipe on a failing drive, and do not reduce a two-device RAID1 filesystem to one device as a substitute for replacement. Use the failure walkthrough next.

Devices & recovery

23Worked incident: a failed RAID1 drive

Replace a missing member and rebuild redundancy—the Btrfs counterpart to replacement and resilvering.

Scenario: a two-device data filesystem, both Data and Metadata RAID1, one completely failed drive, one readable surviving drive, and a blank replacement partition at least as large in bytes as the missing Btrfs member. The filesystem is not mounted at the start of this rescue procedure. For an already mounted but unstable system, stop writers and assess it before following the unmounted path.

A surviving RAID1 copy is a recovery opportunity, not a guarantee: if it also has unreadable extents, replacement may fail. Prioritize irreplaceable data and a backup. Do not schedule a stress-test scrub of the only remaining copy before deciding whether the disk needs imaging or specialist recovery.

1. Identify the filesystem, survivor, and missing devid

Inspect; replace all example identities
SURVIVOR=/dev/disk/by-id/REPLACE_ME_SURVIVING_DISK-part1
NEW=/dev/disk/by-id/REPLACE_ME_REPLACEMENT_DISK-part1
FAILED_DEVID=2
lsblk -e7 -o NAME,PATH,SIZE,MODEL,SERIAL,FSTYPE,UUID,MOUNTPOINTS
sudo btrfs filesystem show "$SURVIVOR"
sudo journalctl -k -b --no-pager

FAILED_DEVID=2 is true only in this scenario. Obtain your actual missing member ID from filesystem metadata and your saved inventory; never infer it from sdb. Save kernel errors, serials, old member size, FSID, and device counters on another device. Power down before replacing hardware unless the enclosure and procedure support hot-swap.

What to expect · illustrative
Scenario record: devid 1 = surviving disk; devid 2 = missing disk.
The replacement has a different physical serial and no mounted filesystem.

2. Try a controlled read-only inspection

Inspect without tree-log replay
sudo mkdir -p /mnt/recovery
sudo mount -t btrfs -o ro,degraded,nologreplay,subvolid=5 "$SURVIVOR" /mnt/recovery
sudo btrfs filesystem usage -T /mnt/recovery
sudo btrfs device stats /mnt/recovery
sudo ls /mnt/recovery/@data

Use nologreplay because an ordinary read-only Btrfs mount may replay the log. If this mount fails, or reads produce uncorrectable errors, stop and take the salvage path in the emergency chapter. Do not escalate directly to btrfs check --repair. Readable urgent files can be copied now to a verified separate healthy destination, with copy failures checked.

3. Review the blank replacement and size

Verify target and compare bytes with the old member record
lsblk -o NAME,PATH,SIZE,FSTYPE,MOUNTPOINTS "$NEW"
sudo wipefs --no-act "$NEW"
sudo blockdev --getsize64 "$NEW"
swapon --show

The selected replacement partition must have no data you intend to preserve and must not be in use by any other stack. If it contains signatures, investigate them instead of adding -f. Do not run mkfs on the replacement and do not add it first: replace itself initializes the target.

4. Mount for replacement and start reconstruction

After deciding the surviving copy is usable and protecting the data you can, unmount the inspection view. Mount the same filesystem read-write in degraded mode for the replacement operation. Stop ordinary application writers; this is a temporary maintenance state.

Enter the replacement maintenance state
sudo umount /mnt/recovery
sudo mount -t btrfs -o rw,degraded,subvolid=5 "$SURVIVOR" /mnt/recovery

Keep power stable and prevent suspend. In the same terminal with the reviewed variables:

Rebuild missing devid onto the replacement
sudo btrfs replace start -B -r "$FAILED_DEVID" "$NEW" /mnt/recovery

-B keeps the command in the foreground. -r favors a healthy mirror over reading a damaged source; a wholly absent source is reconstructed from available redundancy. The missing member is selected by ID. There is no separate “start resilver” command. Keep this command’s failure status and logs if it does not complete.

5. Inspect progress and final state

From another terminal, or after completion
sudo btrfs replace status /mnt/recovery
sudo btrfs filesystem show /mnt/recovery
sudo btrfs filesystem usage -T /mnt/recovery
sudo btrfs device stats /mnt/recovery

Expect a completed replacement, two present members, and the replacement associated with the old member ID. Confirm no missing device remains. Device error counters can retain historical values; success is not inferred merely from counters being zero. Verify the operation result and current kernel messages.

6. Confirm redundant profiles, then verify contents

Check every Data, Metadata, and System profile. Degraded writes or an interrupted conversion can leave unwanted profiles depending on kernel/state. If any single-copy data or metadata groups remain, and the replacement is healthy with enough workspace, convert those groups back:

Only if profile verification shows conversion is needed
sudo btrfs balance start -dconvert=raid1,soft -mconvert=raid1,soft /mnt/recovery

The soft filter skips groups already using the target profile. Do not run this before replacement as a substitute for reconstruction. After it completes, inspect profiles again; do not accept unexpected system allocation.

Verify the rebuilt redundant filesystem
sudo btrfs scrub start -B -d /mnt/recovery
sudo btrfs filesystem usage -T /mnt/recovery
sudo btrfs device stats /mnt/recovery

Investigate uncorrectable errors and validate important files/applications. Scrub cannot validate ordinary NOCOW file data through Btrfs checksums. Once accepted, unmount the maintenance view and mount the normal fstab targets without degraded. Confirm mounts before restarting services.

Return to normal data mounts
sudo umount /mnt/recovery
sudo mount /mnt/btrfs-top
sudo mount /srv/data
findmnt -t btrfs -o TARGET,SOURCE,FSROOT,OPTIONS

Stop conditions and the boot-disk exception

If replacement aborts, record status and logs, reassess the surviving copy, and verify what happened to the target before retrying. Do not run concurrent replace, remove, or balance operations. Do not permanently add degraded to fstab. Keep the old failed disk disconnected until its disposition is deliberate; reconnecting stale copies complicates recovery.

For a root mirror, this Btrfs operation restores only the Btrfs member. It does not create an EFI System Partition, install GRUB on the new disk, copy an external /boot, or establish firmware boot entries. Restore those separately and test booting from each disk independently in a planned maintenance window. A mirrored root filesystem with one bootable ESP still has a boot-availability weakness.

24Replace a readable drive or upgrade capacity

A healthy migration uses the same replace primitive.

When the old member is still readable, keep both old and new devices attached if feasible. Verify the new target and run replacement using the source devid or its stable path. Example: replace devid 1 on a healthy mounted data filesystem.

Review the live replacement

If the source is failing or very slow, the -r preference from the incident recipe can favor redundant good copies. Keep the target at least as large as the source member. Finish and verify one replacement before starting another.

sudo btrfs replace status /srv/data
sudo btrfs filesystem resize 1:max /srv/data
sudo btrfs device usage /srv/data

The same procedure does not promise that the enlarged filesystem can later fit back on the old smaller disks.

26Take a pre-maintenance root checkpoint

Capture a coherent state before apt or configuration work.

Confirm the root’s actual filesystem UUID and use the top-level mount of that filesystem—not the unrelated data volume from earlier chapters. This example starts a new shell context with explicit root variables.

Mount the root filesystem top level
ROOT_UUID=REPLACE_ME_ROOT_FS_UUID
sudo mkdir -p /mnt/root-top
sudo mount -t btrfs -o subvolid=5 "UUID=$ROOT_UUID" /mnt/root-top
sudo btrfs subvolume show /mnt/root-top/@rootfs

One-time setup, only if the sibling container does not already exist:

Create the root checkpoint container
sudo btrfs subvolume create /mnt/root-top/@rootsnaps

Wait for all apt/dpkg operations to finish normally. Stop or quiesce stateful applications included in root if consistency matters. Do not freeze the root filesystem and then try to create a snapshot on it: the snapshot operation itself needs writes. A filesystem sync does not make a running database application-consistent.

Create and record the root checkpoint
ROOT_SNAP=root-pre-upgrade-$(date -u +%Y%m%dT%H%M%SZ)
sudo btrfs filesystem sync /
sudo btrfs subvolume snapshot -r /mnt/root-top/@rootfs "/mnt/root-top/@rootsnaps/$ROOT_SNAP"
sudo btrfs property get -ts "/mnt/root-top/@rootsnaps/$ROOT_SNAP" ro
printf "%s
" "$ROOT_SNAP"

Record the snapshot name off-machine with the maintenance reason, installed kernel versions, mount layout, and recovery instructions. Verify that the snapshot contains the expected kernel/initramfs and modules before beginning a risky upgrade.

Check the boot and package state
sudo ls "/mnt/root-top/@rootsnaps/$ROOT_SNAP/boot"
sudo ls "/mnt/root-top/@rootsnaps/$ROOT_SNAP/lib/modules"
sudo test -s "/mnt/root-top/@rootsnaps/$ROOT_SNAP/var/lib/dpkg/status"

Proceed with the intended maintenance only after the checkpoint is verified. Package updates are deliberately not bundled into the same copy button. Replicate important checkpoints separately if they must survive loss of this filesystem.

27Boot a writable snapshot clone from GRUB

The practical analogue of choosing a previous boot environment.

Starting state: the root layout from the previous chapters, a working GRUB menu, and a verified read-only checkpoint. The goal is a temporary test boot of an older root without altering the preserved checkpoint or selecting it as the permanent default. This procedure is for the unencrypted, /boot-inside-root layout described above.

1. Make a writable test environment

Clone and adjust its mount configuration
ROOT_SNAP=REPLACE_ME_ROOT_CHECKPOINT_NAME
sudo btrfs subvolume snapshot "/mnt/root-top/@rootsnaps/$ROOT_SNAP" /mnt/root-top/@boot-test
sudoedit /mnt/root-top/@boot-test/etc/fstab

In the clone’s fstab, change the root line only from subvol=@rootfs to subvol=@boot-test; use the same root FSID and remove any contradictory numeric subvolid. For this isolated test, make shared application-data and home mounts noauto or otherwise keep them out of the test environment. Preserve a copy of the original fstab before editing.

Check the clone’s /etc/default/grub for hardcoded rootflags, but do not regenerate its bootloader during this temporary test. The installed EFI/GRUB loader may still load configuration from the normal root. Boot-menu ownership matters when moving from testing to permanent activation.

2. Add a host-specific menu entry in the normal running system

Select the clone’s actual kernel and edit custom entries
sudo ls /mnt/root-top/@boot-test/boot
sudo ls /mnt/root-top/@boot-test/lib/modules
sudoedit /etc/grub.d/40_custom

Keep the existing executable header of 40_custom; append the entry. Replace both UUID placeholders and both kernel-version placeholders. Use the kernel version inside the clone, not uname -r from the current system. Preserve necessary hardware/console parameters from your working Debian menu entry.

GRUB template: unencrypted root, /boot inside clone
menuentry 'Debian Btrfs test environment' {
    insmod part_gpt
    insmod btrfs
    search --no-floppy --fs-uuid --set=root REPLACE_ME_ROOT_FS_UUID
    linux /@boot-test/boot/vmlinuz-REPLACE_ME_KERNEL_VERSION root=UUID=REPLACE_ME_ROOT_FS_UUID rootflags=subvol=@boot-test ro systemd.unit=rescue.target
    initrd /@boot-test/boot/initrd.img-REPLACE_ME_KERNEL_VERSION
}

This loads kernel files from the clone and tells the initramfs which root subvolume to mount. The kernel’s initial ro flag is normal; the writable clone can later be remounted read-write according to its own fstab. It is not the Btrfs read-only property of the preserved snapshot. GPT is assumed; keep your working partition module on other layouts.

Generate and syntax-check the normal boot menu
sudo update-grub
sudo grub-script-check /boot/grub/grub.cfg

Ensure the menu is visible during boot using your normal GRUB timeout settings. Keep the existing Debian entry and choose the test entry manually for one boot; do not make it the default yet. A syntax check cannot prove disk discovery, firmware behavior, decryption, or driver compatibility.

3. Verify you actually booted the clone

Inspect from the test environment
findmnt -no SOURCE,FSROOT,OPTIONS /
cat /proc/cmdline
uname -r
sudo btrfs subvolume show /

4. Clean up after a successful normal boot

28Recover an unbootable root from live media

Restore the stable root path while retaining the broken state for inspection.

Scenario: a package/configuration change broke boot, but the Btrfs filesystem and hardware are healthy. You have the coherent root checkpoint described above. Use live/rescue media booted in the same firmware mode. This is not the disk-failure procedure.

1. Mount only the top level and inspect the checkpoint

Inspect from live media
ROOT_UUID=REPLACE_ME_ROOT_FS_UUID
ROOT_SNAP=REPLACE_ME_ROOT_CHECKPOINT_NAME
sudo mkdir -p /mnt/root-top
sudo mount -t btrfs -o subvolid=5 "UUID=$ROOT_UUID" /mnt/root-top
sudo btrfs subvolume show "/mnt/root-top/@rootsnaps/$ROOT_SNAP"
sudo ls "/mnt/root-top/@rootsnaps/$ROOT_SNAP/boot"
findmnt -t btrfs -o TARGET,SOURCE,FSROOT

Make sure the installed root is not running and no other mounted view of its active subvolume is being used. Preserve files changed since the checkpoint, particularly anything stored under root. Independently snapshot/backup separate application data if it must remain compatible. If the candidate lacks matching kernel/modules or package state, choose another checkpoint or repair using a matching kernel set.

2. Create the replacement root before changing names

Prepare a writable restored root
sudo btrfs subvolume snapshot "/mnt/root-top/@rootsnaps/$ROOT_SNAP" /mnt/root-top/@rootfs-next
sudoedit /mnt/root-top/@rootfs-next/etc/fstab

Verify the restored fstab uses subvol=@rootfs for /, not the temporary name or a stale numeric subvolume ID. Verify any hardcoded GRUB rootflags likewise select @rootfs. The clone becomes @rootfs in the next step. This recipe uses explicit subvolume paths, not the filesystem’s default-subvolume selector.

Preserve the old root under a new name
BROKEN=@rootfs-broken-$(date -u +%Y%m%dT%H%M%SZ)
sudo mv -- /mnt/root-top/@rootfs "/mnt/root-top/$BROKEN"
Activate the restored root path
sudo mv -- /mnt/root-top/@rootfs-next /mnt/root-top/@rootfs
sudo btrfs subvolume show /mnt/root-top/@rootfs

These two renames are not one atomic transaction. If the second fails, restore the old name before leaving rescue. Keep the broken tree; it can contain files not present in the checkpoint. Never perform this name switch from the root being replaced.

3. Mount the restored root and rebuild its boot metadata

Prepare the chroot
sudo mkdir -p /mnt/sysroot
sudo mount -t btrfs -o subvol=@rootfs "UUID=$ROOT_UUID" /mnt/sysroot
sudo mount --rbind /dev /mnt/sysroot/dev
sudo mount --make-rslave /mnt/sysroot/dev
sudo mount -t proc proc /mnt/sysroot/proc
sudo mount --rbind /sys /mnt/sysroot/sys
sudo mount --make-rslave /mnt/sysroot/sys
sudo mount --rbind /run /mnt/sysroot/run
sudo mount --make-rslave /mnt/sysroot/run

For the assumed UEFI layout, mount the machine’s existing ESP at the restored root’s /boot/efi if it is needed by its installed boot tooling. Verify that partition by UUID; do not format it. If /boot is separate, stop here until it contains a kernel/initramfs matching the restored modules and package state—the example’s self-contained boot assumption no longer holds.

UEFI only: mount the existing ESP
sudo mkdir -p /mnt/sysroot/boot/efi
sudo mount /dev/disk/by-uuid/REPLACE_ME_ESP_UUID /mnt/sysroot/boot/efi
Enter the restored Debian installation
sudo chroot /mnt/sysroot /bin/bash

Inside the chroot, inspect available kernels, regenerate existing initramfs images, and generate the restored GRUB configuration. Do not use the live medium’s uname -r as the installed kernel version.

Inside the chroot: rebuild and verify
ls /lib/modules
ls /boot/vmlinuz-*
update-initramfs -u -k all
update-grub
grub-script-check /boot/grub/grub.cfg

Resolve any reported error before rebooting. Existing initramfs images are updated by -u -k all; if a needed image is absent, identify that exact installed kernel and create its image with update-initramfs -c -k VERSION. This does not reinstall GRUB’s EFI/core binaries. If those were damaged or updated incompatibly, use Debian’s bootloader rescue procedure too.

Leave the chroot
exit
Unmount cleanly from the live shell
sudo umount -R /mnt/sysroot
sudo umount /mnt/root-top

If unmounting fails, inspect what is still using the mounts; do not force a reboot with unexamined errors. Reboot into the normal Debian entry, then verify findmnt /, kernel/modules, package status, services, and application data before deleting any preserved root tree.

If the restored root still fails

Return to live media. Preserve the attempted root under another unused name and restore the original @rootfs name from the broken tree if appropriate. Use the saved logs and known boot configuration to diagnose. Keep both candidates until you know which files and package state must survive.

30Applications, databases, VMs, and containers

Filesystem consistency is only one layer of a useful checkpoint.

WorkloadRecommended checkpoint approachCommon mistake

DatabaseUse database-native backup, or stop/quiesce it before the filesystem snapshotTreating a live file copy as a guaranteed consistent database backup.

For a self-hosted service, define a restore set: application version, configuration, database, uploaded files, and credentials needed to decrypt or access them. A root rollback may reintroduce an older application that cannot read its still-newer data schema.

A simple stopped-service snapshot

Example: a dedicated systemd service called example-app.service owns all data in /srv/data. Substitute the actual service and ensure no independent worker keeps writing. This block stops only the named service; examine its real dependencies.

Stop and confirm the application is inactive
sudo systemctl stop example-app.service
sudo systemctl is-active example-app.service

Once confirmed inactive, create the snapshot. An “inactive” check typically has a nonzero exit code; interpret it rather than assuming all nonzero commands here mean the stop failed.

Checkpoint the quiesced data
APP_SNAP=/mnt/btrfs-top/@snapshots/data/app-$(date -u +%Y%m%dT%H%M%SZ)
sudo btrfs subvolume snapshot -r /srv/data "$APP_SNAP"

Restart the application even if snapshot creation failed, after checking what happened and whether it is safe to resume service. In production automation, implement explicit error handling and restart cleanup rather than pasting these steps into an unattended script.

Resume and verify the service
sudo systemctl start example-app.service
sudo systemctl status example-app.service --no-pager

Replicate the snapshot and separately retain required configuration and application-native backups. A snapshot of one subvolume is not an atomic multi-subvolume snapshot transaction.

31Swapfiles and hibernation boundaries

Use the supported helper and keep swap out of your snapshot roots.

For this recipe use a single-device filesystem with single data profile, not the two-device RAID1 example. A separate swap partition or zram is often simpler for a mirrored root. Active Btrfs swapfiles have allocation constraints and prevent snapshotting their containing subvolume.

Single-device example: create and activate swap
sudo btrfs subvolume create /mnt/root-top/@swap
sudo mkdir -p /swap
sudo mount -t btrfs -o subvol=@swap "UUID=$ROOT_UUID" /swap
sudo btrfs filesystem mkswapfile --size 8G /swap/swapfile
sudo swapon /swap/swapfile
swapon --show

The helper creates a preallocated NOCOW swapfile with the required setup. Do not substitute an ordinary sparse truncate file. For persistence add both the subvolume mount and the file entry to fstab, then validate them. Root filesystem-wide mount options still apply; the swapfile’s own attributes enforce its constraints.

fstab example
UUID=REPLACE_ME_ROOT_FS_UUID /swap btrfs defaults,subvol=@swap 0 0
/swap/swapfile none swap defaults 0 0

Hibernation additionally needs a suitable resume device and a Btrfs-specific resume offset, sufficient space, and working Debian resume configuration. It is not enabled just by creating swap. Inspect with the supported mapping command instead of copying a generic filefrag offset:

Inspect the hibernation resume offset
sudo btrfs inspect-internal map-swapfile -r /swap/swapfile

Recreating or relocating swap can invalidate a saved resume offset. This guide does not configure hibernation automatically. Before swapoff, ensure enough memory; then account for swap restrictions before resize, balance, or device operations.

32Quotas and snapshot accounting

Enable them for an actual requirement, not just for a pretty space number.

Btrfs qgroups account for referenced and exclusive extents across subvolumes. They are not traditional per-user quotas. Shared space complicates both interpretation and performance; snapshot-heavy workloads can pay substantial accounting costs. The default in this guide leaves quotas disabled unless limits are needed.

TermMeaning
ReferencedExtent space referenced by the qgroup, including shared extents.
ExclusiveExtent space not referenced outside the qgroup.
0/subvolume-IDLeaf qgroup associated with one subvolume.
LimitA constraint, not preallocated or reserved capacity.
RescanRebuild accounting when required; may take time and consume resources.

For a filesystem where you have chosen traditional qgroups, enable and let accounting settle, then inspect the real subvolume ID before setting a limit:

Enable and inspect qgroups deliberately
sudo btrfs quota enable /srv/data
sudo btrfs quota rescan -w /srv/data
sudo btrfs qgroup show -reF /srv/data
sudo btrfs subvolume show /srv/data

Example: only if the intended subvolume has ID 256, apply a 200 GiB referenced-space limit. Snapshots and other qgroups need their own considered policy; this is not an entire filesystem capacity reservation.

Set a limit on the verified qgroup
sudo btrfs qgroup limit 200G 0/256 /srv/data
Remove that limit
sudo btrfs qgroup limit none 0/256 /srv/data

The second box is an alternative policy change, not the next step of setting a limit. Investigate inconsistent-accounting messages and rescan status before trusting enforcement. Simple quotas (“squotas”) use different accounting semantics and version requirements; they are acknowledged here but excluded from the baseline workflow.

Maintenance

33Automate inspection, not surprise mutations

A small scheduled task with an observable result is better than a silent maintenance bundle.

Start with monthly scrubs, frequent backup checks, and alerts for new device errors. Keep balance, profile conversions, broad defragmentation, and device removal out of routine unattended jobs. Avoid overlapping heavy maintenance. Check for existing Debian/local timers first so the same filesystem is not scrubbed twice.

Inspect existing automation and the executable path
systemctl list-timers --all
systemctl list-unit-files | grep -E "btrfs|snapper|fstrim"
command -v btrfs

A monthly scrub with systemd

Create /etc/systemd/system/btrfs-data-scrub.service. Confirm the executable path on your Debian installation. This unit requires the actual data mount and keeps systemd attached until the scrub finishes.

btrfs-data-scrub.service
[Unit]
Description=Scrub the Btrfs data filesystem
RequiresMountsFor=/srv/data
ConditionPathIsMountPoint=/srv/data

[Service]
Type=oneshot
ExecStart=/usr/bin/btrfs scrub start -B /srv/data
TimeoutStartSec=infinity
Nice=10

Create /etc/systemd/system/btrfs-data-scrub.timer:

btrfs-data-scrub.timer
[Unit]
Description=Monthly Btrfs data scrub

[Timer]
OnCalendar=monthly
RandomizedDelaySec=6h
Persistent=true

[Install]
WantedBy=timers.target
Enable the schedule
sudo systemctl daemon-reload
sudo systemctl enable --now btrfs-data-scrub.timer
systemctl list-timers btrfs-data-scrub.timer

Test the service once during a suitable maintenance window, and inspect its final result. Persistent timers can run a missed job after boot; the random delay avoids every machine starting together. These times use the system timezone.

Test and inspect the scheduled job
sudo systemctl start btrfs-data-scrub.service
systemctl status btrfs-data-scrub.service --no-pager
journalctl -u btrfs-data-scrub.service --no-pager

A failed unit in the journal is not an alert delivered to you. Integrate it with your monitoring system and test a notification path. Check SMART/device-error trends separately; retain prior counter values. Alert on failures, unexpected missing mounts, and low headroom.

Requirements for snapshot/backup scripts

  • Verify the source and destination are mounted Btrfs filesystems with the expected FSIDs and subvolume roots.
  • Take a lock so runs do not overlap; use distinct timestamped names and stop on failures.
  • Quiesce applications with guaranteed restart cleanup when needed.
  • For pipelines use Bash pipefail or explicitly inspect every process status.
  • Mark success only after receive/verification; retain the previous base until then.
  • Give retention a preview mode, a protected-snapshot list, and a narrowly bounded path.
  • Log enough to restore: source snapshot UUID, received UUID, destination, timestamps, and verification outcome.

TRIM is a separate SSD maintenance concern. Debian kernels can support async discard and fstrim; inspect the actual mount and storage stack, particularly LUKS or thin provisioning. Do not add multiple discard mechanisms blindly.

34When the filesystem will not mount

Preserve evidence and salvage readable data before trying invasive repairs.

SymptomFirst responseAvoid
One RAID1 member missingFollow the controlled degraded inspection/replacement recipeFormatting the survivor or removing the missing member as the first fix.
Filesystem remounted read-onlyStop writers; save kernel logs and device statsRepeated rw remounts without understanding the error.
Checksum / uncorrectable errorsIdentify affected files and available redundant/backup copiesAssuming scrub can invent data when every copy is bad.
ENOSPC with free-looking dfInspect allocation, snapshots, open files, and quotasA full unfiltered balance.
Package update broke bootUse the known root checkpoint and live-media procedureFilesystem repair for an otherwise healthy filesystem.
Mechanical failure or repeated disconnectsStabilize hardware and consider imaging/recovery helpRepeated exhaustive scans of the only fragile remaining copy.

A non-replaying read-only mount attempt

On an unmounted filesystem with devices correctly discovered, a read-only, no-log-replay mount is a cautious inspection step. Add degraded only for an understood missing-device case; do not treat every mount failure as a degraded-array problem.

Inspect an unmounted filesystem
sudo mkdir -p /mnt/salvage
sudo mount -t btrfs -o ro,nologreplay,subvolid=5 /dev/disk/by-id/REPLACE_ME_MEMBER-part1 /mnt/salvage

If readable, recover essential files to a different healthy filesystem and check copy errors. If not mountable, btrfs restore can attempt salvage without modifying the source. Its output can be incomplete or older than expected; validate recovered files.

List roots and dry-run salvage
sudo btrfs restore -l /dev/disk/by-id/REPLACE_ME_MEMBER-part1
sudo btrfs restore -D -v /dev/disk/by-id/REPLACE_ME_MEMBER-part1 /mnt/healthy-recovery

Verify that /mnt/healthy-recovery is actually mounted on a separate healthy filesystem with sufficient space, then make a real salvage attempt if appropriate:

Salvage readable files and metadata
sudo btrfs restore -v -m -x -S /dev/disk/by-id/REPLACE_ME_MEMBER-part1 /mnt/healthy-recovery

Here -m requests metadata, -x xattrs, and -S symlinks. This is a recovery attempt, not a complete transactional backup restore. Keep original media or images until the result has been inspected.

Structural checking is a different operation

On an unmounted, stable source or working copy
sudo btrfs check --readonly /dev/disk/by-id/REPLACE_ME_MEMBER-part1

Read-only checking can still impose a heavy read load on bad hardware. Choose it when structural diagnosis is useful, ideally after preserving the source. Do not run it on an active read-write mount. btrfs check --repair, rescue tree rebuilding, log clearing, and superblock manipulation are intentionally not provided as copyable fixes. Use case-specific expert guidance with verified backups/images.

35Practice in a disposable Debian VM

Rehearse the commands before the incident is real.

Use a disposable Debian VM with its OS disk clearly separate from three expendable virtual data disks. A VM provides real mounts, initramfs, and bootloader behavior without risking a host filesystem. Two disks form the data RAID1 filesystem; the third is the replacement. Add a separate backup disk if you want to rehearse send/receive as well.

  • Create the two-disk filesystem, mount @data, and populate a small test dataset with recorded hashes.
  • Take a read-only snapshot. Change a file in the live tree; confirm the old bytes remain in the snapshot.
  • Create a writable snapshot and confirm edits are isolated.
  • Send full and incremental snapshots to the backup filesystem; compare source UUIDs with received UUIDs.
  • Power off the VM and detach one data disk. Boot with only the survivor and blank replacement attached.
  • Perform the complete failed-drive replacement procedure. Confirm normal mounts without degraded, profiles, scrub, and hashes.
  • On a separate root-snapshot VM, test the GRUB writable environment and live-media rename rollback. Do not combine first-time root and data experiments.
  • Record actual output and the recovery time. Repeat after material kernel, tool, or boot-layout changes.
Write and hash a disposable test file
sudo mkdir -p /srv/data/lab
printf "known-good-v1\n" | sudo tee /srv/data/lab/check.txt
sha256sum /srv/data/lab/check.txt

Store the hash record outside the filesystem under test. Do not simulate a production drive failure by pulling a random cable or overwriting a member’s superblock. The VM disk-removal exercise should be a powered-off, controlled action.
