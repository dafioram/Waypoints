Read this first

This guide covers OpenZFS on Linux from the command line, in the order you meet things: how a pool is built, how to prepare and partition disks, how to create a pool and what the options mean, then datasets and snapshots, health checks, replacing a failed disk, backups with send and receive, performance, and booting from a ZFS root. It ends with a practice lab you can run on plain files, a table of error messages, and a note on how the content was checked.

It targets OpenZFS 2.4.4. Features that need a newer release than 2.1 carry a version pill such as 2.3+. Run zfs version to see which release you have, as distributions often ship an older one.

  • The prompt # means the command runs as root. Use sudo in front of it, or sudo -i first. A $ prompt marks the few commands that run as an ordinary user.

Where to begin

If ZFS is new to you, read how ZFS is organized first. It is short, and every later command uses its words: pool, vdev, dataset. After that, read the disk and pool sections in order before you create anything. If a disk has just failed, go straight to the replacement steps. Read the safety check before you start.

Whatever you do, ZFS is not a backup. A snapshot, a mirror or RAIDZ protects against different failures, and none of them helps if the whole machine is lost, stolen or deleted by a mistake that was snapshotted. Keep at least one copy on another machine, and test restoring it.

How ZFS fits together

ZFS has two layers and you manage them with two commands. zpool builds and looks after the pool: the disks and how they are arranged. zfs works inside a pool on datasets: the filesystems, volumes and snapshots that hold your files. Nothing in the pool is formatted in advance. You create datasets as you need them, and they all share the pool's free space.

The pool: disks arranged into vdevs

A vdev (virtual device) is a group of disks that ZFS treats as one unit. Disks sit inside top-level vdevs, and the pool spreads data across all of its top-level vdevs. Redundancy lives inside each top-level vdev, not in the pool.

tankThe pool. One name for all the space below it.
├─ mirror-0A top-level vdev: two disks holding identical data.
│ ├─ DISK1A leaf vdev: a whole disk, a partition or a file.
│ └─ DISK2
├─ mirror-1A second top-level vdev. The pool stripes data across both.
│ ├─ DISK3
│ └─ DISK4
├─ specialOptional helper: fast storage for metadata and small files.
│ └─ mirror-2
├─ logsOptional helper: a separate intent log for synchronous writes.
├─ cacheOptional helper: a second-level read cache on fast storage.
└─ sparesOptional helper: idle disks that take over when one fails.

Five rules that follow from this

  • Vdevs cannot be nested. A mirror or raidz can only contain disks or files. A mirror of mirrors is not allowed. To get "RAID 10", list several mirror vdevs, as the example above does.
  • Losing one top-level vdev loses the pool. Two mirrors do not protect each other. A pool made of one mirror and one single disk is only as safe as that single disk.
  • You can add vdevs later, but you cannot freely remove them. zpool remove works for mirrors, single disks and helper devices, but not when the pool contains a raidz or draid vdev. Plan raidz widths before you build.
  • Different sizes in one vdev waste space. A mirror or raidz vdev is limited by its smallest disk.
  • Everything is checksummed. When a read fails its checksum, ZFS repairs it from a good copy if the vdev has one. That is why redundancy matters even if the disks look healthy.

Datasets: what you actually use

Inside a pool you create datasets. A filesystem is mounted like a normal directory. A volume (zvol) is a block device, used for virtual machine disks and iSCSI. Each dataset has its own properties, such as compression and quota, and children inherit them from their parent.

├─ homeA filesystem. Children inherit its properties.
│ ├─ adaMounted at /tank/home/ada.
│ └─ ben
├─ vmA filesystem used only as a folder for volumes.
│ └─ win11A volume. Appears as /dev/zvol/tank/vm/win11.
└─ home/ada@mondayA snapshot. A read-only picture of ada at one moment.

Health states

A pool is ONLINE when every device works, DEGRADED when a device has failed but the redundant layout still holds all data, and FAULTED when too much is missing to carry on. A single device can also be OFFLINE (you took it offline), UNAVAIL (it could not be opened) or REMOVED (it was unplugged while running). The builder at the top of the page shows these states as you fail disks.

Name disks after their slot with vdev_id.conf

On a server with many bays, serial numbers are hard to match to a physical slot. ZFS ships a udev helper, vdev_id, that creates names such as /dev/disk/by-vdev/A1 from a mapping you write in /etc/zfs/vdev_id.conf. The file format is documented in man vdev_id.conf. After editing it, run udevadm trigger and the new names appear.

A second option needs no setup. Once a pool exists, ZPOOL_SCRIPTS_AS_ROOT=1 zpool status -c upath,serial adds the device path and serial number to every vdev line. The health section explains this and lists more columns.

Sector size and ashift

ZFS stores data in blocks that are a multiple of the disk's sector size. The ashift pool property is that size as a power of two: 9 means 512 bytes, 12 means 4096 bytes, 13 means 8192 bytes. It is fixed for each vdev when the vdev is created and cannot be changed later.

Report the logical and physical sector sizes in bytes
# blockdev --getss --getpbsz /dev/disk/by-id/DISK15124096# lsblk -t /dev/disk/by-id/DISK1

The first number is the logical sector size and the second is the physical one. ZFS asks the disk and picks an ashift to match, but some drives report 512 bytes when the hardware is really 4096. If a vdev is built with ashift=9 on such a disk, every write is a slow read-modify-write, and a later replacement with a true 4K disk is refused with "new device has a different optimal sector size". Set ashift=12 yourself when you create a pool. A larger value than the disk needs costs a little space and nothing else. SSDs often use 12 or 13; 12 is a safe choice for all of them.

Partition and wipe disks

ZFS is happy to take a whole disk. You partition by hand only when a disk has to do more than one job, for example a boot disk with an EFI system partition, or when you want a replacement-friendly margin. This section shows both paths. The partitioning commands in it destroy the existing contents of the disk.

Whole disk or partitions

If you give zpool create a whole disk (/dev/disk/by-id/DISK1), ZFS writes a GPT partition table itself on Linux. It makes partition 1 for data and partition 9, about 8 MiB, as a reserved area at the end. That small reserve is why a replacement disk that is a few sectors smaller than the original can still be used.

Choose a layout

The layout decides how many disk failures you survive and how much space you keep, and it is the hardest thing to change later. Decide it before you create the pool. The builder at the top of this page shows the space and failure tolerance for each choice.

How to choose

  • Two to four disks, or you expect to add disks over time: mirrors. You can add another pair whenever you like.
  • Many disks holding big, mostly-read files such as media, backups or archives: RAIDZ2. The manual recommends 3 to 9 disks per raidz vdev. For more disks, use more than one vdev.
  • Virtual machines, databases or anything with many small random reads and writes: several mirrors.
  • Large disks (many terabytes): prefer two-parity layouts. Rebuilding one takes many hours, and a second failure during that window is the case that RAIDZ1 and 2-way mirrors cannot survive.
  • A boot disk: a 2-way mirror.

RAID of any kind is not a backup. It protects against a dead disk, not against deleting a file, ransomware or a flooded server room. Send snapshots to another machine as well.

Space is never exactly the formula

  • ZFS refuses to let the last 3.2 percent of a pool be used, so it cannot run out of space completely (the spa_slop_shift setting).
  • RAIDZ rounds each allocation up, so small blocks use more space than the formula suggests. Volumes with a small block size suffer most.
  • Disk makers count in powers of ten. A "4 TB" disk is about 3.64 TiB, which is what ZFS tools show.

Features, compatibility and upgrades

OpenZFS adds new on-disk features over time. A new pool turns on every feature the running version knows, and a system with an older ZFS then cannot import it. If you may move the pool to an older system, or boot it with a boot loader such as GRUB, limit the features when you create it.

See the feature sets this installation ships
# ls /usr/share/zfs/compatibility.d/
Create a pool that OpenZFS 2.2 can also importDestroys data on the disks listed
# zpool create -o ashift=12 -o compatibility=openzfs-2.2 tank mirror /dev/disk/by-id/DISK1 /dev/disk/by-id/DISK2

Files named openzfs-2.2, openzfs-2.3 and openzfs-2.4 exist in 2.4.4. Older ones such as openzfs-2.1-linux and grub2 exist too. The names with a -linux suffix are the same sets listed for Linux only.

Check which pools lack features, and enable them
# zpool upgrade # lists pools that do not have every supported feature enabled# zpool upgrade tank # enables the features; with a compatibility list set, only those

Upgrading is one-way. After zpool upgrade the pool cannot be imported by software that lacks the new features. Do not run zpool upgrade -a on a pool you boot with an older boot loader until you have checked its feature support.

A volume is a block device backed by the pool, which you format with another filesystem or hand to a virtual machine. It supports snapshots and clones like a filesystem.

Create and use a volume
# zfs create -V 50G tank/vm/win11 # appears as /dev/zvol/tank/vm/win11# zfs create -s -V 1T tank/vm/thin # -s makes it sparse (no space reserved up front)# zfs create -V 20G -b 16k tank/vm/db # -b sets the volume block size, fixed at creation# zfs set volsize=100G tank/vm/win11 # grow it later# mkfs.ext4 /dev/zvol/tank/vm/win11

A normal volume reserves its full size, so you see the space leave the pool as soon as you create it. The manual advises against putting swap on a ZFS volume. Use a partition instead.

Your own properties, and delegating

Attach notes to a dataset
# zfs set backup:policy=daily tank/home # the name needs a colon; the part before it is yours# zfs get -r backup:policy tank

User properties are stored with the dataset, inherited by children and sent with it by zfs send -p and -R. Scripts can read them to decide what to back up.

Let an ordinary user take snapshots and send backups of their own dataset
# zfs allow -u ada snapshot,hold,send tank/home/ada# zfs allow tank/home/ada # show what has been delegated# zfs unallow -u ada send tank/home/ada # take one permission away again

The manual says Linux cannot delegate mount, unmount, mountpoint, canmount, rename and share, because only root may change the system's mount table. It also lists mount as a requirement for snapshot, destroy, rollback and create. I could not test how those interact, so try the delegation as the actual user before relying on it. Running snapshot jobs as root from cron, as the script below does, avoids the question.

Encrypt a dataset

Native encryption is chosen when a dataset is created and cannot be added later. ZFS encrypts file contents, file attributes and directory listings. It does not encrypt dataset and snapshot names, properties or file sizes.

Create an encrypted dataset, lock it and unlock itLose the passphrase, lose the data
# zfs create -o encryption=on -o keyformat=passphrase tank/private # prompts for a passphrase; on means aes-256-gcm# zfs unmount tank/private# zfs unload-key tank/private # now the data is unreadable# zfs load-key tank/private # prompts again# zfs mount tank/private# zfs get encryption,keystatus,encryptionroot tank/private

Children of an encrypted dataset share its key. To back it up without ever unlocking it on the backup machine, send it raw: zfs send -w. For an encrypted root pool, the boot section shows the extra options.

Snapshots, clones and rollback

A snapshot is a frozen, read-only view of a dataset. It takes no time to make and takes up no space until the live data changes, because ZFS never overwrites blocks in place. Snapshots are the everyday protection against deleting the wrong thing, and they are the raw material for backups.

Roll back

Rollback returns the whole dataset to the snapshot and throws away every change made since. It is quick and it is permanent.

Roll back to the newest snapshotDiscards later changes
# zfs rollback tank/home/ada@before-upgrade

By default ZFS only rolls back to the most recent snapshot. To go further back you must also agree to lose the snapshots in between: zfs rollback -r tank/home/ada@older. -R additionally destroys clones of those snapshots. Both apply to the dataset you name, not to its children.

If you only need one file or folder, copy it out of .zfs/snapshot instead. Rolling back a whole dataset to recover one file loses everything else you did since.

Clones: try a change on a copy

A clone is a writable dataset that starts as a snapshot and shares its blocks, so it costs almost nothing until you change it.

Test something on a clone, then keep or discard it
# zfs snapshot tank/vm/db@golden# zfs clone tank/vm/db@golden tank/vm/db-test # a writable copy, ready at once# zfs promote tank/vm/db-test # optional: make the clone the original and the old one its dependent# zfs destroy tank/vm/db-test # or just discard it

A snapshot with clones cannot be destroyed. ZFS says "has dependent clones" and lists them. Either destroy the clones first, or promote one, which reverses the dependency so the old dataset can be removed.

Protect snapshots from deletion

Place, list and release a hold
# zfs hold keep tank/home/ada@before-upgrade # "keep" is a tag you choose# zfs holds tank/home/ada@before-upgrade# zfs release keep tank/home/ada@before-upgrade

While a snapshot has a hold, zfs destroy fails on it. Backup scripts use holds so that the snapshot they are sending cannot be pruned halfway.

Bookmarks

A bookmark remembers when a snapshot was taken but holds no data, so it costs nothing. It is enough to send an incremental stream later, which means you can destroy the snapshot and still replicate onward.

Snapshot on a schedule

Distribution packages such as sanoid, zfs-auto-snapshot and zrepl do this well. If you would rather have something small and readable, this script takes a recursive snapshot and keeps only the newest ones it made.

/usr/local/sbin/zfs-snap.sh
#!/bin/bash# Usage: zfs-snap.sh DATASET KEEP# Takes a recursive snapshot named auto-YYYY-MM-DD_HHMM and then deletes# all but the newest KEEP snapshots of DATASET whose names start with auto-.set -euo pipefailDATASET=${1:?usage: zfs-snap.sh DATASET KEEP}KEEP=${2:?usage: zfs-snap.sh DATASET KEEP}[ "$KEEP" -ge 1 ] || { echo "KEEP must be at least 1" >&2; exit 2; }zfs snapshot -r "$DATASET@auto-$(date +%Y-%m-%d_%H%M)"# Oldest first, only this dataset's own snapshots, only ours, all but the newest KEEP.zfs list -H -t snapshot -o name -s creation -d 1 "$DATASET" \  | grep "@auto-" \  | head -n "-$KEEP" \  | xargs -r -n 1 zfs destroy -r
Make it executable and run it every hour from cron
# chmod 755 /usr/local/sbin/zfs-snap.sh# echo '0 * * * * root /usr/local/sbin/zfs-snap.sh tank/home 48' > /etc/cron.d/zfs-snap

The listing uses -H, which prints plain lines with no header, so the script can read it safely. head -n -48 (GNU head, standard on Linux) drops the newest 48 lines from the list, so what remains is the old snapshots to destroy.

Scrub

A scrub reads every block in the pool, checks it against its checksum, and repairs any bad copy from the good one. It finds damage on parts of the disk nobody has read in months, which is exactly when you want to find out, because a second failure on top of undetected damage is how pools are lost. It works while the pool is in use. Scrub once a month, or weekly for important data.

Start, watch, pause and stop a scrub
# zpool scrub tank# zpool status tank # progress and estimated time# zpool scrub -p tank # pause (the progress is remembered across reboots)# zpool scrub tank # running it again resumes a paused scrub# zpool scrub -s tank # stop it for good# zpool scrub -w tank # start it and wait here until it finishes
Scrub in progress, from the zpool-scrub manual pageExample output
# zpool status...  scan: scrub in progress since Sun Jul 25 16:07:49 2021        403M / 405M scanned at 100M/s, 68.4M / 405M issued at 10.0M/s        0B repaired, 16.91% done, 00:00:04 to go...

"Scanned" is metadata ZFS has walked through. "Issued" is data actually read and checked. The percentage and time left follow the issued figure. A scrub that finds a bad block on a redundant pool repairs it and reports the amount in "repaired". It also bumps the CKSUM count of the disk that held the bad copy.

Schedule it

On systemd machines, ZFS ships timers for each pool. This is the recommended way:

Scrub every week or every month, automatically
# systemctl enable --now zfs-scrub-weekly@tank.timer# systemctl enable --now zfs-scrub-monthly@backup.timer# systemctl list-timers 'zfs-*'

Enable one timer per pool, weekly or monthly, not both. Without systemd, use cron: 0 2 1 * * root /usr/sbin/zpool scrub tank. Some distributions already schedule a scrub, for example with a cron file shipped in the ZFS package. Look at ls /etc/cron.d and systemctl list-timers before adding a second schedule.

TRIM and initialize

On SSDs, TRIM tells the drive which blocks are free so it can keep writing quickly. You either set autotrim=on on the pool, or run TRIM on demand. The manual notes that automatic trimming can stress cheaper drives, and that a periodic manual TRIM gets most of the benefit.

Trim a pool and watch it
# zpool trim tank# zpool status -t tank # shows per-disk trim progress# zpool trim -w tank # trim and wait# zpool trim -s tank # suspend; run zpool trim again to resume# zpool trim -c tank # cancel# systemctl enable --now zfs-trim-weekly@tank.timer # or schedule it

zpool initialize tank writes a pattern over all the free space of every disk. It is used to find bad areas on new drives or to pre-allocate thin-provisioned storage. It is not needed for ordinary disks.

Watch the traffic

Per-disk throughput and operations, refreshed every 5 seconds

Replace a failed disk and resilver

This is the job ZFS earns its keep on. You swap the bad disk, tell ZFS about the new one with zpool replace, and ZFS copies the data it needs onto it. That copying is called resilvering. The pool stays online and usable the whole time.

The example pool is tank, a two-way mirror of DISK1 and DISK2, and DISK2 has died. The commands are the same for RAIDZ and for pools with several vdevs. Differences for RAIDZ are noted below.

Replace the disk, step by step

  1. Find out which disk failed

    Start with the report. It names the disk and shows the state:

    See what is wrong
    # zpool status -x# zpool status -g tank # the same, but with each disk's GUID in place of its name

    The status in the health section showed this case: DISK2 is UNAVAIL and the pool is DEGRADED. A disk can also show FAULTED ("too many errors") or REMOVED. If its name has been replaced by a long number, ZFS lost the path. That number is the GUID, and you can use it anywhere a disk name is accepted.

    Next, find the physical drive. Compare serial numbers:

    Match names to serial numbers
    # export ZPOOL_SCRIPTS_AS_ROOT=1# zpool status -c serial,model tank# smartctl -i /dev/disk/by-id/DISK1 | grep -i serial # check the healthy disk too, then remove the other one

    Do not pull a disk by guesswork. In a degraded 2-way mirror or RAIDZ1 the healthy disks hold the only copy. Removing the wrong one takes the pool offline. If your enclosure has locate LEDs, use them: ledctl locate=/dev/sdb (from the ledmon package) lights a drive's bay. With ZED_USE_ENCLOSURE_LEDS=1 the daemon may already have lit the fault LED.

  2. Check you are safe to proceed

    Make sure no data is already damaged
    # zpool status -v tank

    errors: No known data errors means the surviving disks hold everything. Any file listed there is already damaged beyond what ZFS can repair. Restore it from a backup afterwards. If you have not sent a recent snapshot to another machine, do that now, because during the resilver the remaining disk carries all the risk.

  3. Take the old disk offline, if it is still listed

    If the failed disk still answers at all, tell ZFS to stop using it before you pull it. If it is already UNAVAIL or REMOVED, skip this step.

    Stop ZFS from using the disk
    # zpool offline tank /dev/disk/by-id/DISK2

    The state becomes OFFLINE, and the pool DEGRADED. -t makes the offline last only until the next reboot. On Linux, --power also switches off the drive's slot in enclosures that support it.

  4. Fit the new disk and prepare it

    The new disk must be at least as large as the smallest disk in the vdev. If it is smaller, ZFS says "device is too small". Once it is installed, find its by-id name and make sure it is blank:

    Find the new disk and check it is empty
    # ls -l /dev/disk/by-id/ | grep -v -- -part # the new serial number is the one you did not have before# wipefs -n /dev/disk/by-id/NEWDISK # no output means no signatures# zdb -l /dev/disk/by-id/NEWDISK # "failed to unpack label" four times is good

    If it carries an old filesystem or pool, wipe it first.

    If the pool was built on partitions (for example DISK2-part1, as on a boot pool) copy the partition layout from a healthy disk before replacing, and use the new disk's partition in the next step:

    Copy a partition table from the healthy diskOverwrites the new disk's table
    # sgdisk --replicate=/dev/disk/by-id/NEWDISK /dev/disk/by-id/DISK1 # target first, source last# sgdisk -G /dev/disk/by-id/NEWDISK # new unique IDs# partprobe /dev/disk/by-id/NEWDISK

  5. Replace the disk

    Name the old disk exactly as zpool status does, then the new one:

    Replace and start the resilver
    # zpool replace tank /dev/disk/by-id/DISK2 /dev/disk/by-id/NEWDISK

    The command returns quickly and the resilver runs in the background. A few variations:

    Other ways to give the same command
    # zpool replace -w tank /dev/disk/by-id/DISK2 /dev/disk/by-id/NEWDISK # -w: do not return until it is finished# zpool replace tank 1234567890123456789 /dev/disk/by-id/NEWDISK # old disk named by its GUID, when the path is gone# zpool replace -s tank /dev/disk/by-id/DISK2 /dev/disk/by-id/NEWDISK # sequential: faster on mirrors, scrubs afterwards# zpool replace tank /dev/disk/by-id/DISK2 # no new disk named: the new disk sits at the old one's path

    If the replacement disk appears at the same device path as the dead one, you can leave out the new name. This is useful with slot-based names such as /dev/disk/by-vdev/A2 from vdev_id.conf, or plain sdb. ZFS notices that the disk behind the path is a different disk. With by-id names the path changes, so you will normally give both names.

  6. Watch the resilver

    The pool shows a temporary vdev called replacing-1, holding the old disk and the new one. The new one is marked (resilvering).

    Check progress
    # zpool status tank
    Example output, partway throughExample output
    # zpool status tank  pool: tank state: DEGRADEDstatus: One or more devices is currently being resilvered.     • The two numbers on the scanned line are the rates at which ZFS is walking the pool's block pointers and at which it is issuing real reads. The time remaining is calculated from the issue rate, and it is only an estimate. ZFS prints "no estimated completion time" while the rate is too low to say.
    • The percentage and "resilvered" figure count the data written to the new disk.
    • The pool is usable. Applications keep working, a little slower.
    Other ways to follow it
    # zpool wait -t resilver tank # returns when the resilver finishes; good in a script# zpool iostat -v tank 5 # watch reads on the old disk and writes on the new one# watch -n 30 zpool status tank

    How long it takes depends on how much data the pool holds, not on how big the disks are. Hours is normal for a few terabytes on spinning disks, and large RAIDZ vdevs on a busy pool can take days. Rebooting during a resilver is safe: the pool imports as usual and the resilver carries on.

  7. Confirm it is finished

    Check the result
    # zpool status tank
    Example output, finishedExample output
    # zpool status tank  pool: tank state: ONLINE  scan: resilvered 3.10T in 05:38:36 with 0 errors on Thu Oct 29 14:40:47 2026config:        NAME         STATE     READ WRITE CKSUM        tank         ONLINE       0     0     0          mirror-0   ONLINE       0     0     0            DISK1    ONLINE       0     0     0            NEWDISK  ONLINE       0     0     0errors: No known data errors

    The replacing-1 group is gone and the old disk has been detached automatically. The pool is ONLINE. Then do these three things:

    • Scrub. A normal resilver verifies checksums as it goes, but a scrub of the whole pool is the best proof that everything is intact. It is required after a sequential resilver, because those skip the checksum checks. ZFS tells you so: "One or more devices have been sequentially resilvered, scrubbing the pool is recommended." Run zpool scrub tank.
    • Clear old error counts once you understand their cause: zpool clear tank.
    • Write it down. Note the new disk's serial number and slot, and send the old disk for disposal or warranty. Wipe it first if it holds anything private (wipe commands).

    To get the scrub started automatically after every resilver, set ZED_SCRUB_AFTER_RESILVER=1 in zed.rc.

Replace a disk that has not failed yet

To swap a disk for a bigger or newer one, or because SMART warns about it, do not offline it first. Connect the new disk beside it and run the same replace command. The old disk stays in the vdev, and keeps serving reads and holding a copy, until the new one is fully resilvered. The pool never loses redundancy.

Replace a healthy disk without ever losing redundancy
# zpool replace tank /dev/disk/by-id/DISK2 /dev/disk/by-id/NEWDISK

This needs a spare bay or port to hold both disks at once. If you have none, use the offline method from the steps above. In a 2-way mirror you can also attach, then detach, which ends up in the same place.

Hot spares

A hot spare is an idle disk in the pool. When a disk fails, the ZFS event daemon (zed) puts the spare in its place automatically and starts a resilver, so the pool regains redundancy while you are asleep. It does not replace the need to swap the dead disk later.

Add, use and remove spares
# zpool add tank spare /dev/disk/by-id/DISK9 # add a spare to a running pool# zpool replace tank /dev/disk/by-id/DISK2 /dev/disk/by-id/DISK9 # put the spare in place by hand# zpool replace tank /dev/disk/by-id/DISK2 /dev/disk/by-id/NEWDISK # later: the real replacement; the spare goes back to idle# zpool detach tank /dev/disk/by-id/DISK2 # alternative: make the spare permanent by removing the failed disk# zpool remove tank /dev/disk/by-id/DISK9 # take a spare out of the pool

While a spare is in use, zpool status shows a group named spare-N containing the failed disk and the spare, with the spare marked INUSE. A spare can be shared by several pools on one machine, and while a shared spare is in use, its pool cannot be exported. Hot spares need the event daemon running (see ZED).

What differs for RAIDZ and dRAID

  • The commands are the same. The vdev is called raidz2-0 instead of mirror-0.
  • A RAIDZ resilver rebuilds the new disk from parity, so it reads from all the surviving disks in the vdev. It is slower than a mirror copy and loads the whole vdev.
  • -s (sequential) is not supported for RAIDZ. ZFS says "only mirror and dRAID vdevs support sequential reconstruction".
  • RAIDZ1 has no redundancy left while it resilvers. A single read error on any surviving disk during that time is permanent data loss for the affected blocks, and a second failed disk loses the vdev. That is why double parity is advised for large disks.
  • dRAID has distributed spares built in. A failed disk can be rebuilt onto spare space spread across all the other disks, which is much faster than writing to one new disk. A later zpool replace with a physical disk copies the data back.

Replace with larger disks to grow a vdev

You can grow a mirror or RAIDZ vdev without adding disks by replacing every disk in it with a bigger one, one at a time. The extra space appears only after the last disk has been replaced.

Grow a mirror by replacing its disks with bigger ones
# zpool set autoexpand=on tank # so the pool grows by itself at the end# zpool replace -w tank /dev/disk/by-id/DISK1 /dev/disk/by-id/BIG1 # wait for each resilver before the next# zpool replace -w tank /dev/disk/by-id/DISK2 /dev/disk/by-id/BIG2# zpool list -v tank # EXPANDSZ shows space waiting to be claimed, if autoexpand was off# zpool online -e tank /dev/disk/by-id/BIG1 /dev/disk/by-id/BIG2 # claim it by hand

Replace one disk at a time and never start the next until the pool is back to ONLINE. If the pool was created with a smaller ashift, the larger disks still work, but the vdev keeps its original sector size.

Mirror: attach, then detach

A mirror is the one layout where you can add a copy first and drop the old one afterwards. The result is the same as zpool replace.

Turn a 2-way mirror into a 3-way mirror, then remove the bad disk
# zpool attach tank /dev/disk/by-id/DISK1 /dev/disk/by-id/NEWDISK # DISK1 is any disk that is in the mirror now# zpool wait -t resilver tank# zpool detach tank /dev/disk/by-id/DISK2 # drop the failed or old disk

The same attach command also turns a single-disk pool into a mirror: zpool attach tank DISK1 DISK2 makes a two-way mirror, and the new disk begins resilvering at once. zpool detach only works on mirrors, and it refuses if no other valid copy remains.

Grow, shrink and reshape

ZFS lets you add capacity easily and remove it only in some cases. Check each of these against your layout before you rely on it.

Add a vdev

New data is spread over all top-level vdevs. Existing data stays where it is, so a new vdev starts empty and takes most of the new writes. Match the redundancy of what is already there.

Preview, then add another mirrorCannot be undone for RAIDZ pools
# zpool add -n tank mirror /dev/disk/by-id/DISK5 /dev/disk/by-id/DISK6 # dry run: prints the resulting layout# zpool add tank mirror /dev/disk/by-id/DISK5 /dev/disk/by-id/DISK6

ZFS stops you with "mismatched replication level" if you try to add a single disk to a pool of mirrors, unless you force it with -f. Do not force it: the pool would then depend on that one disk. On a pool that contains RAIDZ vdevs, anything you add can never be removed again. Run the dry run every time.

The same zpool add command adds helper devices:

Add log, cache, special and spare devices
# zpool add tank log mirror /dev/disk/by-id/SSD1 /dev/disk/by-id/SSD2# zpool add tank cache /dev/disk/by-id/SSD3# zpool add tank special mirror /dev/disk/by-id/SSD4 /dev/disk/by-id/SSD5# zpool add tank spare /dev/disk/by-id/DISK9

Expand a RAIDZ vdev 2.3+

OpenZFS 2.3 can add one disk at a time to an existing RAIDZ vdev. You use attach with the vdev's name as shown in zpool status.

Add a disk to a RAIDZ2 vdevNeeds the raidz_expansion feature
# zpool attach tank raidz2-0 /dev/disk/by-id/NEWDISK# zpool status tank # shows expansion progress# zpool wait -t raidz_expand tank
  • The redundancy does not change. A RAIDZ2 stays a RAIDZ2.
  • Old data keeps its old ratio of data to parity. Only data written afterwards uses the wider stripe, so the free space reported can be slightly lower than you expect. Rewriting old data (for example by sending it to a new dataset) brings it up to date.
  • A scrub of the whole pool starts when the expansion finishes.
  • If a disk fails during the expansion, the expansion pauses until you have replaced it.

Remove a vdev

zpool remove copies a vdev's data onto the rest of the pool and then drops the vdev. It works for mirrors, single disks, and the helper devices. It does not work if any top-level vdev is RAIDZ or dRAID, or if the vdevs have different sector sizes.

Remove a mirror, a spare, a log or a cache
# zpool remove -n tank mirror-1 # estimate only; changes nothing# zpool remove tank mirror-1 # starts evacuating mirror-1 in the background# zpool status tank # shows evacuation progress# zpool remove -s tank # cancel an evacuation in progress# zpool remove tank /dev/disk/by-id/SSD3 # cache and spare devices go immediately

Split a mirror into a second pool

If every vdev is a mirror, you can split off one disk from each to make a new, identical pool. It is a quick way to make a clone of a pool for another machine.

Split and then import the new pool
# zpool split -n tank tank2 # dry run: shows what the new pool would contain# zpool split tank tank2 # takes the last disk of every mirror# zpool import -d /dev/disk/by-id tank2 # the new pool is exported; import it here or elsewhere

Checkpoint before something risky

A checkpoint remembers the whole state of the pool. If an upgrade or layout change goes wrong, you can rewind to the moment before it. While a checkpoint exists, ZFS refuses zpool remove, attach, detach, split and reguid, and the checkpoint holds on to space, so discard it as soon as you are happy.

Create, use and discard a checkpoint
# zpool checkpoint tank# zpool export tank# zpool import --rewind-to-checkpoint tank # go back to the checkpoint, losing everything since# zpool checkpoint -d tank # or: discard it, once everything works

Rename, relabel and re-ID

Small housekeeping jobs
# zpool export tank# zpool import -d /dev/disk/by-id tank newname # rename a pool by importing it under a new name# zpool reguid newname # give the pool a new GUID, e.g. after cloning disks# zpool reopen newname # make ZFS re-check all its disks# zpool set comment="rack 3, bay 4 to 7" newname

Send, receive and backups

A snapshot on the same pool protects you from mistakes. It does not protect you from a dead pool, a fire or a stolen server. For that you need a copy on another pool, preferably on another machine. zfs send turns a snapshot into a stream of bytes on standard output. zfs receive reads that stream and rebuilds the snapshot. ZFS knows which blocks changed between two snapshots, so an incremental send moves only those, however big the dataset is.

Every example here sends from tank to a machine called backup-host that has a pool named backup. Change the names to yours. All of it also works with both pools on one machine: leave out the ssh backup-host part.

Send a snapshot to another pool or machine

Make a snapshot, then copy it
# zfs snapshot tank/home@mon-1# zfs send tank/home@mon-1 | zfs receive backup/home # another pool on this machine# zfs send tank/home@mon-1 | ssh backup-host zfs receive -u backup/home # a pool on another machine

The first send is full: it carries every block the snapshot references. The target backup/home is created by the receive and must not exist yet (see the error table), but its parent backup must. -u stops the new dataset from mounting on the backup machine, which is what you want for a copy that nothing should open or modify.

Add -v to both ends to watch it work. The sender prints to standard error while the receiver prints to standard output:

Verbose full sendExample output
# zfs send -v tank/home@mon-1 | ssh backup-host zfs receive -v -u backup/homefull send of tank/home@mon-1 estimated size is 210Gtotal estimated size is 210Greceiving full stream of tank/home@mon-1 into backup/home@mon-114:02:11   1.02G   tank/home@mon-114:02:12   2.11G   tank/home@mon-1...received 210G stream in 1283.40 seconds (168M/sec)

The stream is not compressed or encrypted by zfs send itself. ssh encrypts the connection. Use zfs send -c (below) so blocks that are compressed on disk cross the wire compressed. There is little point in turning on ssh compression as well.

Estimate the size first

-n (dry run) with -v prints what a send would do and sends nothing. It is the quickest way to learn whether an incremental is small or whether something unexpected changed.

Dry runExample output
# zfs send -nv -i @mon-1 tank/home@tue-1send from @mon-1 to tank/home@tue-1 estimated size is 4.20Gtotal estimated size is 4.20G

The real command is the same without -n. -P prints the same facts in a form scripts can parse.

Incremental sends

After the first full copy, send only what changed. You name the snapshot both sides already have, and the new one.

Send the changes since @mon-1
# zfs snapshot tank/home@tue-1# zfs send -v -i @mon-1 tank/home@tue-1 | ssh backup-host zfs receive -u backup/home

Two rules decide whether this works. The starting snapshot (@mon-1) must exist on both sides, and on the destination it must be the newest snapshot. Nothing may have written to the destination since then. If either is false, receive stops with an error that says which.

Choosing the form
You writeWhat arrives on the destination
send -i @a fs@dOne step: the difference between @a and @d. Snapshots taken between them (@b, @c) are not created there.
send -I @a fs@dEvery snapshot from @a to @d, each kept as its own snapshot. Use this to keep the history on the backup identical.
send -i #mark fs@dOne step, starting from a bookmark instead of a snapshot. The sender may have destroyed the old snapshot.
send -R fs@dA whole tree with its properties, descendants and snapshots. See below.

To make the destination refuse stray writes, receive the first copy with -o readonly=on. That is enough to prevent most of the “has been modified” errors, and it does not affect the receive itself.

First copy, read-only on the backup side
# zfs send tank/home@mon-1 | ssh backup-host zfs receive -u -o readonly=on backup/home

Copy a whole tree with -R

-R sends a dataset and all its children with their properties, their snapshots and their clone relationships. The snapshot must exist on every dataset in the tree, so take it with zfs snapshot -r.

Replicate tank/home and everything below it
# zfs create backup/tank # a container on the backup pool; -e and -d need their target to exist# zfs snapshot -r tank/home@2026-10-29# zfs send -R tank/home@2026-10-29 | ssh backup-host zfs receive -u -e backup/tank

The result is backup/tank/home, backup/tank/home/ada and so on. The options that pick the target name:

  • -e keeps the last part of the source name (home) and puts it under the target you give.
  • -d drops the first part (the pool name tank) and keeps the rest of the path under the target. For tank/home/ada into backup/tank that gives backup/tank/home/ada.
  • With neither, you name the exact destination dataset, as in the earlier examples.

With -d or -e the target must already exist, or receive says “specified fs (…) does not exist”. Add -n -v to a receive to see the names it would use without writing anything.

The next day, send an incremental replication stream:

Incremental replication of the tree
# zfs snapshot -r tank/home@2026-10-30# zfs send -R -I @2026-10-29 tank/home@2026-10-30 | ssh backup-host zfs receive -u -e backup/tank

Be careful with -F on a replication receive. When the stream is an incremental -R stream, zfs receive -F destroys snapshots and datasets on the destination that no longer exist on the sender. That is how a replica stays an exact mirror, and it is also how a snapshot you deleted on purpose, or a dataset you renamed, silently removes the only copy on the backup. Leave -F off unless you want a mirror, and keep the backup's own retention separate.

Related send flags for trees: -X tank/home/tmp,tank/home/cache leaves some descendants out of a -R stream, and -s carries on past a dataset that is missing the snapshot (it warns and skips that dataset and its children) instead of aborting.

Encrypted datasets: raw sends

If you send an encrypted dataset without -w, ZFS decrypts it on the sender and the stream carries plain data. The receiver then stores it however its own settings say (unencrypted, or re-encrypted with a different key). With -w the stream carries the blocks exactly as they sit on disk, still encrypted.

Back up an encrypted dataset without unlocking it anywhere
# zfs snapshot tank/secure@2026-10-29# zfs send -w tank/secure@2026-10-29 | ssh backup-host zfs receive -u backup/secure# zfs send -w -i @2026-10-29 tank/secure@2026-10-30 | ssh backup-host zfs receive -u backup/secure

The sender does not need the key loaded to send. The backup machine never sees the key, so it can store and scrub the data but cannot read it. When you need the data back, load the key there or send it home raw. Three rules apply:

  • Do not mix raw and non-raw receives into the same dataset. After one non-raw receive, later raw incrementals fail. Choose one style per backup.
  • With -R or -p on an encrypted dataset, -w is required. Otherwise the send stops with “encrypted dataset … may not be sent with properties without the raw flag”.
  • The received copy has keylocation=prompt unless you override it. Change it after the receive finishes (zfs set keylocation=…). You cannot use -o keylocation=prompt during the receive because the stream is already using standard input.

There is more on keys in the dataset section.

Resume an interrupted transfer

A multi-terabyte send over an unreliable link will break sooner or later. Receive with -s and ZFS keeps what has already arrived. Without -s the partial dataset is thrown away and you start again from the beginning.

Send so that it can be resumed
# zfs send -v tank/home@mon-1 | ssh backup-host zfs receive -s -u backup/home

If the connection drops, the receive ends with an error that includes a token. The same token is stored as a property of the half-received dataset:

A replication script

This script does one dataset per run: it takes a snapshot, finds the newest repl- snapshot that the backup already has, sends the difference, and removes older repl- snapshots from the source. It resumes a broken transfer first, and it stops instead of guessing when anything looks wrong. It needs to run as a user who can run zfs on both machines (in practice root, with a key-based ssh login to the backup host).

/usr/local/sbin/zfs-replicate.sh
#!/bin/sh# Usage: zfs-replicate.sh SOURCE_DATASET BACKUP_HOST DEST_DATASET# Example: zfs-replicate.sh tank/home backup-host backup/home# Optional: SENDOPTS="-w" for encrypted datasets, SENDOPTS="-c -L" for compressed/large blocksset -euSRC=${1:?usage: zfs-replicate.sh SOURCE_DATASET BACKUP_HOST DEST_DATASET}HOST=${2:?usage: zfs-replicate.sh SOURCE_DATASET BACKUP_HOST DEST_DATASET}DEST=${3:?usage: zfs-replicate.sh SOURCE_DATASET BACKUP_HOST DEST_DATASET}SENDOPTS=${SENDOPTS:-}NOW="repl-$(date +%Y-%m-%d_%H%M%S)"zfs list -H -o name "$SRC" > /dev/null# 1. Notes on how it behaves:

  • It never uses -F. If the backup has been changed, the receive fails with the message in the error table, and nothing is deleted on either side.
  • Step 4 only runs if the receive succeeded. set -e stops the script at the first failed command, and a send that dies leaves the receive with an incomplete stream, which fails. Step 4 destroys every older repl- snapshot on the source, so the next run starts from the snapshot just sent.
  • The backup keeps every repl- snapshot it receives. Prune those there with a similar zfs destroy loop that keeps the number you want. Do not delete the newest one, because it is the next run's starting point.
  • To schedule it, use cron (17 3 * * * /usr/local/sbin/zfs-replicate.sh tank/home backup-host backup/home) or a systemd timer, and make sure a mail or log line shows you when it exits non-zero.
  • For a tree with children, change the script to use zfs snapshot -r and zfs send -R, and consider what -F would do first (see the warning above).

ZFS could not run where this guide was written, so the script was tested against stand-in zfs and ssh commands that model snapshot lists. The tests covered the first full send, an incremental, resuming, the refusal cases and a failed receive. That shows the script's logic and error handling, not how real pools behave. Run it once on a scratch dataset before you trust it with your data.

Check that the copy is good

Every snapshot has a guid that a send/receive preserves. If the two sides agree, the destination holds that same snapshot. A scrub on the backup pool then confirms the blocks still match their checksums.

Compare and scrub
# zfs get -H -o value guid tank/home@repl-2026-10-29_0300# ssh backup-host zfs get -H -o value guid backup/home@repl-2026-10-29_0300 # the same number means the same snapshot# ssh backup-host zpool scrub backup# ssh backup-host zfs list -t snapshot -o name,used,creation -s creation -r backup/home

The only real proof that a backup works is restoring from it. Once a quarter, receive a recent snapshot into a scratch dataset and open some files.

Test restore to a scratch dataset
# ssh backup-host zfs send backup/home@repl-2026-10-29_0300 | zfs receive tank/restore-test# ls /tank/restore-test# zfs destroy -r tank/restore-test # when you are satisfied

Restore

For a single file, you do not need to send anything. Mount the backup dataset on the backup machine and copy the file out of its .zfs/snapshot/ directory (see reading a snapshot), or use scp from there.

For a whole dataset that was damaged but still has a snapshot the backup also has, roll back to that snapshot and bring it up to date with an incremental send from the backup. This moves only the difference. The script above always leaves the last snapshot it sent on the source, which is exactly the common snapshot you need here.

Bring tank/home up to the newest backupRolls back, losing newer local changes
# zfs rollback -r tank/home@repl-2026-10-29_0300 # destroys any snapshots after it; check with zfs list -t snapshot first# ssh backup-host zfs send -i @repl-2026-10-29_0300 backup/home@repl-2026-10-30_0300 | zfs receive tank/home

If the local pool is lost, create a new pool (the create section), then send the whole backup in full: ssh backup-host zfs send backup/home@repl-2026-10-29_0300 | zfs receive tank/home. For a tree, use send -R from the backup with receive -u -e tank or -d.

Repair damaged blocks from a backup 2.2+

If zpool status -v reports files with permanent errors, and you have the same snapshot on a backup, a corrective receive can rewrite just the bad blocks from it. Send the snapshot that the damaged blocks belong to, and receive it with -c into the same snapshot name.

Heal tank/home@repl-2026-10-29_0300 from the backup
# zpool status -v tank # lists the damaged files# ssh backup-host zfs send backup/home@repl-2026-10-29_0300 | zfs receive -c -v tank/home@repl-2026-10-29_0300# zpool scrub tank # check that everything is clean now# zpool clear tank

It repairs data blocks only. Damaged metadata cannot be healed this way, and if the stream does not match what the pool holds, it stops with “stream is not compatible with the data in the pool”. The manual also points out that repeated healing of a drive that keeps corrupting data is a sign to replace the drive, not a fix.

Streams as files

A stream can be written to a file and received later: zfs send tank/home@snap | zstd > /mnt/usb/home.zfs.zst, then zstd -dc /mnt/usb/home.zfs.zst | zfs receive tank/home-restored. It works, but a file has none of the protection a pool gives. One damaged byte can make the stream unreceivable, and nothing repairs it. You also cannot look inside it or restore a single file without receiving everything. If you want an offline copy, keep a second pool on a removable disk and send to that instead.

Performance and special devices

ZFS performs well with its defaults, and the OpenZFS manual says as much: most of what follows is for particular workloads, not for every pool. The order below is the order to try things in. Measure first, adjust a dataset property, give the machine more RAM, and only then add special-purpose devices. Every helper device is another thing that can fail, and some of them can take the pool with them.

Measure before you change anything

You need to know whether the disks, the CPU, memory or the network is the limit. These show what ZFS itself is doing:

Watch the pool, the cache and the log
# zpool iostat -v tank 2 # per-vdev operations and bandwidth every 2 seconds (first line is the average since boot)# zpool iostat -l tank 2 # adds average wait times per disk# zpool iostat -q tank 2 # adds queue depths# zarcstat 2 # ARC and L2ARC hit rates every 2 seconds (named arcstat before OpenZFS 2.4)# zarcsummary | less # a long report on ARC size, hit ratios and tunables (named arc_summary before 2.4)# zilstat -p tank -i 2 # synchronous write activity on the pool's intent log

For a repeatable test use fio against a scratch dataset, with a block size and read/write mix that look like your real workload. A file-copy benchmark mostly measures the ARC and the write cache. Look at the iostat section for how to read the columns. Also remember that a pool gets slower as it fills up. As a rule of thumb, plan to keep it below roughly 80% full, and look at FRAG and CAP in zpool list.

Memory: the ARC

The ARC is ZFS's read cache in RAM. It grows to use free memory and gives it back when programs ask. That is why free shows little free memory on a ZFS machine, and it is normal. In 2.4.4 the default ceiling is the larger of all memory minus 1 GiB and 5/8 of memory. Releases before 2.3 used half of memory on Linux. To make room for virtual machines or a database, cap it:

Limit the ARC to 8 GiB
# awk '$1 ~ /^(size|c|c_max|hits|misses)$/ {print $1, $3}' /proc/spl/kstat/zfs/arcstats # current size, target, ceiling and hit counters# echo 8589934592 > /sys/module/zfs/parameters/zfs_arc_max # takes effect now, lost at reboot# echo "options zfs zfs_arc_max=8589934592" >> /etc/modprobe.d/zfs.conf # makes it permanent# update-initramfs -u -k all # Debian and Ubuntu, needed when the root or boot pool is ZFS# dracut --force --regenerate-all # Fedora, RHEL and similar, the same step

Lowering the value does not shrink the ARC by itself. The manual says the ARC only shrinks below its old size when memory pressure forces it to. The limit must be at least 64 MiB, and it cannot be set back to 0 on a running system. The permanent line is appended with >>, so if zfs.conf already has a zfs_arc_max line, edit that line instead.

A second-level read cache (L2ARC)

L2ARC is a read cache on a fast SSD that sits between the ARC and the disks. It only helps when your working set is bigger than RAM and mostly read repeatedly. The manual says it helps most with random reads of mostly static content. It costs ARC memory for the index of what it holds, so on a machine with little RAM it can slow things down. More RAM is almost always the better first step.

Add and remove a cache device
# zpool add tank cache /dev/disk/by-id/SSD3 # no redundancy needed, a cache device holds only copies# zpool iostat -v tank 2 # the cache device appears in its own group# zpool remove tank /dev/disk/by-id/SSD3 # takes effect immediately

The cache survives a reboot and is reloaded in the background when the pool is imported. This is the persistent L2ARC, controlled by l2arc_rebuild_enabled. A cache device smaller than 1 GiB gets no rebuild metadata. A device added with zpool add starts empty even if it used to be part of the pool, while one brought back with zpool online has its contents restored. Writes to the cache are throttled to 32 MiB per interval (l2arc_write_max), and prefetched but unused data is skipped by default (l2arc_noprefetch=1). A read error on the cache device is retried against the pool's disks, so a failing cache device does not endanger data.

A separate log for synchronous writes (SLOG)

Programs that call fsync, such as databases and NFS servers, ask ZFS to put data on stable storage before continuing. ZFS first writes it to its intent log. By default that log lives on the pool's own disks. A separate log device on a fast SSD with power-loss protection makes those writes faster. It does nothing for ordinary asynchronous writes such as copying files, and it is never a write cache for them.

First check that you have synchronous writes at all. Run zilstat -p tank -i 2 while the real workload runs. If the numbers stay at zero, a log device will not help.

Add a mirrored log, remove it again
# zpool add tank log mirror /dev/disk/by-id/SSD1 /dev/disk/by-id/SSD2# zpool iostat -v tank 2# zpool remove tank mirror-1 # use the name zpool status shows for the log mirror

The log is small. It holds writes only until the next transaction group commits, which by default happens every 5 seconds (zfs_txg_timeout). A few gigabytes are plenty, and the device's latency and power-loss safety matter far more than its size. Mirror it: with a single log device, losing that device together with a crash or power failure costs you the last few seconds of synchronous writes. RAIDZ is not allowed for logs. A dataset with logbias=throughput skips the log device and optimises for pool throughput instead.

A special vdev for metadata and small files

A special vdev holds the pool's metadata, and optionally small files, on fast storage while bulk data stays on the big disks. It speeds up directory listings, find, scrubs and small-file workloads on pools of hard disks.

Add a mirrored special vdev and send small files to itA special vdev is permanent for RAIDZ pools
# zpool add tank special mirror /dev/disk/by-id/SSD4 /dev/disk/by-id/SSD5# zfs set special_small_blocks=32K tank/home # blocks of 32K or less, after compression, go to the special vdev# zpool list -v tank # the special vdev has its own size and allocation

A special vdev is part of the pool, not a cache. It holds the only copy of the metadata. If it is lost, the pool is lost. Give it at least the redundancy of the rest of the pool: a two-way mirror for a mirrored or RAIDZ1 pool, a three-way mirror for RAIDZ2. Also, zpool remove only works on a pool whose main storage has no RAIDZ or dRAID top-level vdev, so on such a pool treat the addition as permanent.

  • special_small_blocks takes values from 0 (the default, no small files) up to 16 MiB. A value at or above the dataset's recordsize would send all of its data to the special vdev and fill it.
  • When free space on the special vdev drops below 25% (zfs_special_class_metadata_reserve_pct), small file blocks are written to the normal disks again so there is always room for metadata. If the special vdev fills completely, allocations spill over to the normal disks.
  • Only new writes use it. Existing metadata and files stay where they are until they are rewritten. Copying data into a new dataset does this. OpenZFS 2.4 also adds zfs rewrite -r /tank/home to rewrite files in place. The manual lists checksum, compression, dedup and copies as properties it applies, and does not mention special placement, so confirm the result with zpool list -v.
  • The deduplication tables also go to the special class unless the zfs_ddt_data_is_special module parameter is turned off.

Deduplication

Deduplication stores identical blocks once. It sounds attractive and it is the most expensive feature in ZFS. The manual advises at least 1.25 GiB of RAM per TiB of storage, and warns that a badly sized system can become slow and may even fail to import the pool because memory runs out. Compression is the less costly way to save space, and it covers most cases where people expect deduplication to help.

Before turning it on, ask ZFS what it would save on your actual data. This builds the table in memory and reads the whole pool, so run it at a quiet time:

Simulate deduplication
# zdb -S tank
The last line of the reportExample output
dedup = 1.04, compress = 1.52, copies = 1.00, dedup * compress / copies = 1.58

A dedup figure close to 1.00 means nearly nothing would be saved. Here it would save 4%, which is nowhere near worth the cost. If the figure is well above 2 and you have the memory, turn it on for the one dataset that benefits:

Enable on one dataset and watch the table
# zfs set dedup=on tank/vm-images # applies to new writes only# zpool status -D tank # the table's size and a histogram by reference count# zpool list tank # the DEDUP column shows the pool-wide ratio
  • Existing data is not deduplicated retroactively, and turning dedup off later does not remove the table. Entries disappear as the blocks they describe are freed.
  • A dedicated dedup vdev (zpool add tank dedup mirror …) keeps the tables off the main disks. Give it the same redundancy as the pool.
  • 2.3+ The fast_dedup feature turns on more advanced deduplication features for newly created tables. The pool property dedup_table_quota stops the table from growing past a size (in automatic mode, the size of a dedicated dedup vdev). zpool ddtprune -d 30 tank removes entries for blocks that are still unique and older than 30 days, to make room for newer duplicates. zpool prefetch -t ddt tank loads the table into the ARC, for instance after a reboot.

Block cloning 2.2+

Block cloning lets a file copy share the original's blocks until one of them changes. It has little overhead, unlike deduplication, and the program doing the copy has to ask for it. Newer versions of cp try it on their own, and cp --reflink=always insists on it.

Copy by sharing blocks, then see the savings
# cat /sys/module/zfs/parameters/zfs_bclone_enabled # 1 means enabled; the default differs between releases# cp --reflink=always /tank/vm/base.img /tank/vm/clone1.img# zpool get bcloneused,bclonesaved,bcloneratio tank

Only whole blocks of data that has reached the disk can be cloned. Encrypted data cannot be cloned, the source and destination must have the same recordsize, and the manual notes that most versions of Linux do not allow cloning across datasets. This is a different feature from zfs clone, which makes a writable copy of a whole snapshot.

Direct I/O 2.3+

Programs that open files with O_DIRECT ask to skip the page cache. With the direct property on standard (the default in 2.4.4), ZFS bypasses the ARC for those requests when they are properly aligned. This suits very fast NVMe pools and applications that do their own caching. In 2.2 and earlier, O_DIRECT was silently ignored, which is what direct=disabled still does.

Choose how direct requests are handled
# zfs get direct tank/db# zfs set direct=disabled tank/db # ignore O_DIRECT, serve everything through the ARC# zfs set direct=always tank/db # treat every properly aligned request as direct

For writes to bypass the ARC, the offset and size must be multiples of the dataset's recordsize. Any unaligned part goes through the ARC. Buffers must be page-aligned, and the request size must be a multiple of the page size, or the program gets an error.

Make scrubs and resilvers faster, or gentler

A scrub or resilver is a background job that shares the disks with your normal reads and writes. These module parameters set the balance. They can be changed on a running system by writing to /sys/module/zfs/parameters/, and the change lasts until reboot. Put the lasting value into /etc/modprobe.d/zfs.conf as options zfs name=value.

Where a pool serves users during the day, go the other way: leave the defaults, and start scrubs from a timer at night. The manual's own rule is that smaller max_active values favour the latency of normal I/O and larger ones favour throughput. Changing the numbers is a trade between the two, not a free gain.

Rewrite existing files 2.4+

After changing compression, checksum, dedup or copies, old data still has the old settings. zfs rewrite reads each file's blocks and writes them back to new locations so the current settings apply, without a copy to another dataset.

Rewrite a directory tree with the current properties
# zfs set compression=zstd tank/archive# zfs rewrite -rv /tank/archive # -r recurse, -v print each file# zfs rewrite -rP /tank/archive # -P keeps block birth times, so incremental sends do not resend it (needs the physical_rewrite feature)

A rewrite makes the blocks look modified to snapshots and incremental sends unless you use -P. Blocks that are in snapshots or cloned are written as new copies, so the pool uses more space until the old snapshots are gone. recordsize changes have no effect on a rewrite.

Practice on files, not disks

ZFS can build a pool out of ordinary files, so you can rehearse a failure, a replacement or a restore without risking a single real disk. A file-backed pool behaves like a real one for everything in this guide, apart from speed. Do this once before you need it for real. It takes about ten minutes.

These pools are for practice only. Do not leave them running: a file-backed pool depends on the filesystem underneath it and is slow. The cachefile=none setting below stops them from coming back on their own after a reboot.

Make six empty disks

Each file is a “disk”. ZFS needs at least 64 MiB per device, and 1 GiB leaves room to experiment. Use /var/tmp rather than /tmp, which is often a small RAM disk. truncate makes sparse files, so they take no space until ZFS writes to them.

Create six 1 GiB sparse filesRan here

The leading 0 in each line is the number of blocks actually in use. Vdev files must be given as absolute paths to ZFS, which is why every command below spells out /var/tmp/zfslab/.

Create a RAIDZ2 pool and put data in it

Create the pool, a dataset and 200 MiB of random data

Four files in RAIDZ2 give you two files' worth of space and survive any two failures, the same shape as a small real array. The status output looks just like the one in the health section, with file paths where the disk IDs would be.

Drill 2: a disk fails and you replace it

Taking a disk offline is the safe way to pretend it died. The pool continues in the DEGRADED state, and changes you make now are missing from that disk, which is exactly the situation a resilver fixes.

Fail a disk, write more data, replace the disk
# zpool offline labpool /var/tmp/zfslab/d2.img# zpool status labpool # DEGRADED, d2.img is OFFLINE# dd if=/dev/urandom of=/labpool/data/more.bin bs=1M count=100 # written while d2 is gone# zpool replace labpool /var/tmp/zfslab/d2.img /var/tmp/zfslab/d5.img# zpool status labpool # a replacing-1 group, with a resilver in progress# zpool wait -t resilver labpool# zpool status labpool # ONLINE again, d2.img is gone from the list# zpool scrub -w labpool && zpool status labpool # prove it

This is the same sequence as the real replacement walk-through, with d2.img standing in for the failed drive and d5.img for the new one. On a pool this small a resilver is over in seconds, so run zpool status straight after the replace to catch the intermediate state.

Two more experiments are worth a minute. Offline a second file (d3.img) while the first is still out: the pool is DEGRADED and has no redundancy left. Then try to offline a third. ZFS refuses with cannot offline /var/tmp/zfslab/d4.img: no valid replicas, because the pool could no longer be read. zpool online labpool FILE brings a file back, and the pool catches up by resilvering only what changed.

Drill 3: replace small disks with bigger ones

This is how real pools grow. A RAIDZ vdev only gets bigger once every disk in it is bigger, so use a small mirror for this drill. It needs two new 1 GiB files for the mirror and two 2 GiB files to move onto.

Grow a two-way mirror from 1 GiB to 2 GiB per disk
# truncate -s 1G /var/tmp/zfslab/m1.img /var/tmp/zfslab/m2.img# truncate -s 2G /var/tmp/zfslab/big1.img /var/tmp/zfslab/big2.img# zpool create -o cachefile=none -o autoexpand=on labmirror mirror /var/tmp/zfslab/m1.img /var/tmp/zfslab/m2.img# zpool list labmirror # a little under 1G# zpool replace -w labmirror /var/tmp/zfslab/m1.img /var/tmp/zfslab/big1.img # -w waits for the resilver# zpool replace -w labmirror /var/tmp/zfslab/m2.img /var/tmp/zfslab/big2.img# zpool list labmirror # a little under 2G

With autoexpand=on the pool grows as soon as the last small disk is gone. Without it, run zpool online -e labmirror FILE for each disk. The real-world version has the same steps.

Boot from ZFS with ZFSBootMenu

You can keep the operating system itself on ZFS. Then a bad update is a snapshot rollback away, and you can keep several complete systems side by side and pick one at power-on. ZFSBootMenu (ZBM) is the boot loader most people use for this. It is a small Linux system with ZFS built in. The firmware starts it from the EFI system partition, and it imports your pool, shows the boot environments it finds, and starts the one you choose with kexec. Because ZBM carries its own ZFS, it needs no changes when you update the kernel, and a pool feature your distribution's GRUB cannot read is not a problem.

This section follows the project's Debian 13 (Trixie) UEFI guide, using ZFSBootMenu 3.1 (the release in the documentation I read). It assumes a UEFI x86_64 machine and a single disk. A second disk is covered at the end. The same ideas apply to other distributions, whose guides are on the ZFSBootMenu site.

What ends up on the disk

the diskGPT partition table
├─ partition 1, 512 MiB, type EF00EFI system partition (FAT32) with ZFSBootMenu's EFI file in EFI/ZBM
└─ partition 2, the rest, type BF00the ZFS pool, here named zroot

├─ ROOTmountpoint=none, only a container for boot environments
│ └─ debianmountpoint=/, canmount=noauto. The whole operating system, including /boot

A boot environment is one dataset that holds a complete operating system, kernel and initramfs included, in its own /boot directory. Keep the system state that must stay consistent in one dataset, and data that should survive a rollback (/home, mail, databases) in others. ZBM then needs nothing else to boot, and a snapshot of that one dataset is a snapshot of the whole system.

At power-on:

  1. The firmware starts EFI/ZBM/VMLINUZ.EFI from the EFI partition.
  2. ZBM imports your pool (read-only at first) and looks at its bootfs property.
  3. It shows a countdown for the default boot environment. Press a key to open the menu and choose another environment, kernel or snapshot.
  4. It finds the kernel and initramfs in that dataset's /boot and starts them. Your system then mounts its own root.

Install Debian onto a ZFS root

This replaces everything on the target disk. Do it in a live environment, on a machine whose disks you have checked with lsblk. The disk names below are placeholders, so a command pasted without editing fails instead of wiping a disk. Do every step in one root shell, because the variables only exist there.

  1. Start the Debian live image in UEFI mode

    Write the Debian 13 live image to a USB stick and boot it with the firmware in UEFI mode, not legacy or CSM. Open a terminal, confirm that UEFI is in use, become root, and install the tools. zfs-dkms compiles the ZFS module for the live kernel, which takes a few minutes.

    Check UEFI, become root, install ZFS in the live system
    $ dmesg | grep -i efivars # UEFI mode prints: Registered efivars operations$ sudo -i# cat > /etc/apt/sources.list << 'EOF'deb http://deb.debian.org/debian/ trixie main non-free-firmware contribdeb-src http://deb.debian.org/debian/ trixie main non-free-firmware contribEOF# apt update# apt install debootstrap gdisk dkms linux-headers-$(uname -r)# apt install zfsutils-linux zfs-dkms# zgenhostid -f 0x00bab10c # writes /etc/hostid, the machine identity that ZFS records in the pool

    The host ID is the number ZFS stores in a pool when it is imported, to notice if two machines open the same pool. ZFSBootMenu uses this same value when none is configured, which is why the guide picks it. It is copied into the new system below.

  2. Name the disks once

    Use stable names from /dev/disk/by-id/ (see finding your disks). Replace DISK1 with the real ID of the disk. With one disk, the boot and pool partitions are on the same disk. A separate boot device, such as a USB stick, works the same way with different variables.

    Set the variables
    # source /etc/os-release # defines ID=debian, used as the dataset name# export ID# export BOOT_DISK=/dev/disk/by-id/DISK1# export BOOT_PART=1# export BOOT_DEVICE="${BOOT_DISK}-part${BOOT_PART}"# export POOL_DISK=/dev/disk/by-id/DISK1# export POOL_PART=2# export POOL_DEVICE="${POOL_DISK}-part${POOL_PART}"

  3. Wipe and partition the disk

    Remove old labels and signatures, then create the two partitionsDestroys everything on the disk
    # zpool labelclear -f "$POOL_DISK"# wipefs -a "$POOL_DISK"# sgdisk --zap-all "$POOL_DISK"# sgdisk -n "${BOOT_PART}:1m:+512m" -t "${BOOT_PART}:ef00" "$BOOT_DISK" # the EFI system partition# sgdisk -n "${POOL_PART}:0:-10m" -t "${POOL_PART}:bf00" "$POOL_DISK" # the pool, leaving 10 MiB at the end# sgdisk -p "$POOL_DISK"

    If zpool labelclear says there is no label, that is fine. The last command, run on a 20 GiB image file with the same options, shows what to expect:

    The partition table afterwards, on a 20 GiB test imageRan here
    # sgdisk -p DISK1Disk DISK1: 41943040 sectors, 20.0 GiB...Number  Start (sector)    End (sector)  Size       Code  Name   1            2048         1050623   512.0 MiB   EF00   2         1050624        41922526   19.5 GiB    BF00

    If the kernel does not see the new partitions, run partprobe and udevadm trigger. The details of these tools are in the partitioning section.

  4. Create the pool

    One-disk pool for the systemDestroys data on the partition
    # zpool create -o ashift=12 \-O compression=lz4 \-O acltype=posixacl \-O xattr=sa \-O relatime=on \-o autotrim=on \-o compatibility=openzfs-2.3 \-m none zroot "$POOL_DEVICE"

    The ZFSBootMenu guide also passes -f, which forces creation over existing data. The wipe in the previous step should make that unnecessary, so leave it out unless zpool create complains and you are sure of the target. ashift=12 suits 4K-sector disks (see sector size). compatibility=openzfs-2.3 keeps the pool importable by the ZFS inside ZBM and by older rescue media. The guide writes the same file as openzfs-2.3-linux, an alias. Read the ZBM release notes before you use zpool upgrade on this pool or remove the option, because a pool with features ZBM does not know can no longer be booted.

    Encrypt the whole system

    Do these extra steps, in the places named, to encrypt every dataset in the pool. You type the passphrase once in ZFSBootMenu at each boot.

    Before creating the pool: a key file in the live system
    # echo 'SomeKeyphrase' > /etc/zfs/zroot.key # use a passphrase you can type on a bare keyboard# chmod 000 /etc/zfs/zroot.key
    Create the pool with encryptionDestroys data on the partition
    # zpool create -o ashift=12 \-O compression=lz4 -O acltype=posixacl -O xattr=sa -O relatime=on \-O encryption=aes-256-gcm \-O keylocation=file:///etc/zfs/zroot.key \-O keyformat=passphrase \-o autotrim=on -o compatibility=openzfs-2.3 \-m none zroot "$POOL_DEVICE"
    • When you re-import the pool for installation, run zfs load-key -L prompt zroot before mounting anything.
    • Copy the key into the new system: mkdir /mnt/etc/zfs, then cp /etc/zfs/zroot.key /mnt/etc/zfs. It ends up in the initramfs of the encrypted system, readable only once the pool is unlocked.
    • In the chroot, before building the initramfs, run echo "UMASK=0077" > /etc/initramfs-tools/conf.d/umask.conf so the initramfs file is not world-readable.
    • Tell ZFSBootMenu which dataset holds the key, so you only type the passphrase once: zfs set org.zfsbootmenu:keysource="zroot/ROOT/${ID}" zroot.

    See encryption in the dataset section for how native encryption works.

  5. Create the boot environment and home

    Datasets and the default boot environment
    # zfs create -o mountpoint=none zroot/ROOT# zfs create -o mountpoint=/ -o canmount=noauto zroot/ROOT/${ID}# zfs create -o mountpoint=/home zroot/home# zpool set bootfs=zroot/ROOT/${ID} zroot

    Every boot environment needs canmount=noauto. Two datasets with mountpoint=/ cannot both mount automatically, and the system will fail to boot. canmount is not inherited, so setting it on zroot/ROOT does not cover the datasets below. Set it on each one you create, including the clones you make later. ZBM uses bootfs to pick the default, and mounts the root itself.

  6. Re-import under /mnt

    Export, then import with an alternate root and mount the new system
    # zpool export zroot# zpool import -N -R /mnt zroot# zfs mount zroot/ROOT/${ID}# zfs mount zroot/home# mount | grep mnt # both should show type zfs# udevadm trigger

    -N imports without mounting anything. -R /mnt puts every mount point under /mnt for this session only (see export and import).

  7. Install the base system

    Download Debian into the pool and enter it
    # debootstrap trixie /mnt # downloads and unpacks a minimal Debian; takes a while# cp /etc/hostid /mnt/etc# cp /etc/resolv.conf /mnt/etc# mount -t proc proc /mnt/proc# mount -t sysfs sys /mnt/sys# mount -B /dev /mnt/dev# mount -t devpts pts /mnt/dev/pts# chroot /mnt /bin/bash

    From here until you exit the chroot, the commands run inside the new system. The shell variables from earlier are still set.

  8. Basic configuration inside the chroot

    Host name, root password, package sources, locale
    # echo 'YOURHOSTNAME' > /etc/hostname# echo -e '127.0.1.1\tYOURHOSTNAME' >> /etc/hosts# passwd# cat > /etc/apt/sources.list << 'EOF'deb http://deb.debian.org/debian/ trixie main non-free-firmware contribdeb-src http://deb.debian.org/debian/ trixie main non-free-firmware contribdeb http://deb.debian.org/debian-security trixie-security main non-free-firmware contribdeb-src http://deb.debian.org/debian-security/ trixie-security main non-free-firmware contribdeb http://deb.debian.org/debian trixie-updates main non-free-firmware contribdeb-src http://deb.debian.org/debian trixie-updates main non-free-firmware contribEOF# apt update# apt install locales keyboard-configuration console-setup# dpkg-reconfigure locales tzdata keyboard-configuration console-setup

    Enable the en_US.UTF-8 locale as well, even if you use another, because some programs expect it.

  9. Add ZFS to the new system

    Kernel, ZFS initramfs support and boot-time services
    # apt install linux-headers-amd64 linux-image-amd64 zfs-initramfs dosfstools# echo "REMAKE_INITRD=yes" > /etc/dkms/zfs.conf# systemctl enable zfs.target zfs-import-cache zfs-mount zfs-import.target# update-initramfs -c -k all

    This is the point to also install what a real system needs: a network manager, an SSH server, a normal user with sudo. The guide stops at a bootable system.

  10. Tell ZFSBootMenu how to start it

    Kernel arguments for every boot environment
    # zfs set org.zfsbootmenu:commandline="quiet" zroot/ROOT

    Properties are inherited, so this one setting covers every environment under zroot/ROOT. Never put root= in it, because ZBM sets that from the environment you choose.

  11. Format and mount the EFI partition

    FAT32 filesystem and fstab entryDestroys data on the partition
    # mkfs.vfat -F32 "$BOOT_DEVICE"# echo "UUID=$(blkid -s UUID -o value "$BOOT_DEVICE") /boot/efi vfat defaults 0 0" >> /etc/fstab# mkdir -p /boot/efi# mount /boot/efi

    The ZFSBootMenu guide finds the UUID with blkid | grep "$BOOT_DEVICE". That does not work with the long by-id names used here, because blkid prints the short names like /dev/sda1. Asking blkid for the UUID of the device directly works for any name. Run on an image file, it prints just the value:

    UUID of a FAT32 image, reached through a link named like a partitionRan here
    # blkid -s UUID -o value DISK1-part110E5-3A68

  12. Install ZFSBootMenu

    Download the prebuilt EFI file and keep a spare copy
    # apt install curl# mkdir -p /boot/efi/EFI/ZBM# curl -o /boot/efi/EFI/ZBM/VMLINUZ.EFI -L https://get.zfsbootmenu.org/efi# cp /boot/efi/EFI/ZBM/VMLINUZ.EFI /boot/efi/EFI/ZBM/VMLINUZ-BACKUP.EFI

    The prebuilt file is a ready-made image for the latest release. You can build your own with generate-zbm (from the Source tab of the project's guide) if you need custom options, extra hooks or a signed image.

  13. Register it with the firmware

    Boot entries for the main image and the spare
    # mount -t efivarfs efivarfs /sys/firmware/efi/efivars# apt install efibootmgr# efibootmgr -c -d "$(readlink -f "$BOOT_DISK")" -p "$BOOT_PART" -L "ZFSBootMenu (Backup)" -l '\EFI\ZBM\VMLINUZ-BACKUP.EFI'# efibootmgr -c -d "$(readlink -f "$BOOT_DISK")" -p "$BOOT_PART" -L "ZFSBootMenu" -l '\EFI\ZBM\VMLINUZ.EFI'# efibootmgr # lists the boot order; the newest entry is tried first

    efibootmgr wants the disk's real device name, so readlink -f turns the by-id link into /dev/sdX or /dev/nvme0n1. The backup entry exists so that a bad update to the main file does not leave you unable to boot. Some firmware ignores entries it did not create. If yours does, copy the file to the fallback path EFI/BOOT/BOOTX64.EFI on the EFI partition.

  14. Leave the chroot and reboot

    Unmount, export and restart
    # exit# umount -n -R /mnt# zpool export zroot# reboot

    Remove the USB stick when the machine restarts. ZFSBootMenu should appear, count down, and start Debian. If the pool fails to export, something is still mounted under /mnt: check mount | grep /mnt.

Boot environments in daily use

Before a risky upgrade, snapshot the running system. If it goes wrong, reboot into the menu and roll back or boot the snapshot from there. From the running system:

Snapshot, upgrade, and clone a spare environment
# zfs snapshot zroot/ROOT/debian@before-upgrade# apt full-upgrade# zfs clone -o mountpoint=/ -o canmount=noauto zroot/ROOT/debian@before-upgrade zroot/ROOT/debian-old # a bootable copy of the earlier state# zfs list -r -o name,mountpoint,canmount zroot/ROOT

The new debian-old shows up in the menu on the next boot, because it has mountpoint=/ and nothing that hides it. To hide an environment without destroying it, set org.zfsbootmenu:active=off on it. Remove an environment you no longer want with zfs destroy, after any clone that depends on it is promoted or gone (see clones). Because the kernel and initramfs live inside the environment, a normal apt kernel upgrade needs no extra step. ZBM sees the new kernel on the next boot, and MOD+K lets you boot the older one.

To change what every environment is booted with, set org.zfsbootmenu:commandline (see below). To change the pool's default environment, use zpool set bootfs=zroot/ROOT/NAME zroot or MOD+D in the menu.

A few things go wrong often enough to list here:

  • The menu shows no environments. A boot environment needs mountpoint=/ (and not org.zfsbootmenu:active=off), and a kernel with a matching initramfs in its /boot. Check with zfs get mountpoint,org.zfsbootmenu:active zroot/ROOT/debian and ls /boot from zfs-chroot.
  • The system hangs after the kernel starts, or reports more than one filesystem mounted at /. An environment is missing canmount=noauto. Fix it from the recovery shell with zfs set canmount=noauto zroot/ROOT/NAME after set_rw_pool.
  • The booted system says the pool was previously in use from another system. The system's /etc/hostid differs from the host ID the pool was last imported with. ZBM passes the host ID it used on the kernel command line, so this mostly shows up with other rescue media. Give the system the same ID the install used, zgenhostid -f 0x00bab10c, then rebuild the initramfs with update-initramfs -u -k all. The message is in the troubleshooting table.
  • ZBM says the pool is read-only and cannot be written. The pool has features newer than ZBM's ZFS knows, or org.zfsbootmenu:readonly is set. It still boots; you only lose the ability to modify it from the menu. Update the ZFSBootMenu image.

A second disk: mirror the pool and the boot partition

The pool can be mirrored while it is in use, but the EFI partition is not part of the pool, so a second copy has to be made on purpose. Otherwise, losing the first disk leaves you with a healthy mirror and a machine that cannot start.

Copy the partition layout, attach the pool partitionDestroys data on the second disk
# sgdisk -R /dev/disk/by-id/DISK2 /dev/disk/by-id/DISK1 # copy DISK1's partition table onto DISK2# sgdisk -G /dev/disk/by-id/DISK2 # give DISK2 its own unique IDs# zpool attach zroot /dev/disk/by-id/DISK1-part2 /dev/disk/by-id/DISK2-part2# zpool status zroot # resilvering; the mirror is redundant when it finishes

sgdisk -R names the target first and the source last. Getting them the other way round overwrites the good disk's partition table, so read the line twice. See attaching a disk for what the resilver does.

Now the EFI partition. Format the second one, copy ZBM across, and give the firmware a way to start from either disk:

Second EFI partition, a copy of ZFSBootMenu and a boot entry
# mkfs.vfat -F32 /dev/disk/by-id/DISK2-part1# mkdir -p /mnt/esp2# mount /dev/disk/by-id/DISK2-part1 /mnt/esp2# cp -r /boot/efi/EFI /mnt/esp2/# umount /mnt/esp2# efibootmgr -c -d "$(readlink -f /dev/disk/by-id/DISK2)" -p 1 -L "ZFSBootMenu (disk 2)" -l '\EFI\ZBM\VMLINUZ.EFI'

Copy the files again every time you replace the ZBM image on the first disk. There are two ways to avoid doing that by hand:

  • For a new install: make the EFI partition a software RAID 1 across both disks, with the old-style metadata at the end of the partition so firmware can still read each half as a plain FAT filesystem: mdadm --create --level 1 --metadata 1.0 --homehost any --raid-devices 2 /dev/md/esp PART1 PART2, then mkfs.vfat -F32 /dev/md/esp and mount that at /boot/efi. Add a boot entry with efibootmgr for each disk. The project documents this in its mdraid ESP guide.
  • If you build the image yourself: the ZFSBootMenu project ships contrib/esp-sync.sh, a hook for generate-zbm that copies each new image to the other EFI partitions.

Some problems come without a message:

  • “No space left on device” while zpool list shows free space. A quota, a reservation or a volume's refreservation is holding the space, or snapshots do. ZFS also keeps about 3.2% of the pool in reserve. Look at zfs list -o space -r tank.
  • The pool is gone after a reboot. It was not in the cache file, or the boot services are off. See import at boot.
  • Everything is slow after a disk was replaced. A resilver or scrub is running. zpool status shows it, and the scan tunables shift the balance.
  • A disk shows errors but the pool is ONLINE. ZFS repaired what it could. Read the status output, then check the disk with SMART (disk health) before you trust it.

Where to look for more detail: zpool events -v for what the kernel module saw, zpool history tank for what was run, dmesg | grep -i -E 'zfs|zio' for kernel messages, and journalctl -u zfs-import-cache -u zfs-mount -u zfs-zed on systemd machines.

Version pills (2.3+)Compared the 2.2.0, 2.3.0, 2.4.0 and 2.4.4 source tags. A 2.3+ or 2.4+ pill means the feature is missing from the tag before it. A 2.2+ pill could not be checked against an older tag. Block cloning and corrective receive are in the 2.2.0 release announcement, and scrub -e is in the 2.2.0 source; I did not confirm that it is missing from 2.1, so check it on your own system. Features with no pill are older than 2.2 or were not compared. Run zfs version to see what you have, because distributions often ship an older release.
Error and status messagesCopied from the format strings in the 2.4.4 source. The place names, sizes, counts and times in them are made up.
“Example output” blocksReal wording around invented numbers. They show the shape of the output, not what your pool will print.
“Ran here” blocksDisk tools that do not need ZFS, run on image files: truncate, dd, sgdisk, wipefs, blkid, parted and mkfs.vfat. The output is what they printed, with only noise removed. Image files make sgdisk warn about the kernel's partition table, so those warnings are left out.
The shell scriptszfs-snap.sh (11 checks) and zfs-replicate.sh (24 checks) were run against stand-in zfs and ssh commands that keep snapshot lists in files. That tests their logic, argument handling and failure paths. It does not test real ZFS behavior. The use of zfs list -d 1 to list one dataset's own snapshots is an established idiom that I did not confirm on a real pool.
ZFSBootMenuWritten from the project's own documentation, manual pages and source (release 3.1.0 and later commits): its Debian UEFI guide, the zfsbootmenu(7) page, the key bindings and the recovery shell. It was not tried on a real machine or a virtual machine. Two things differ from the project's guide: the disks are named by by-id and the fstab UUID comes from blkid -s UUID -o value.

Things I could not confirm, and so say little about:

  • Whether an unprivileged user can run zfs receive on Linux through zfs allow. The manual says receive needs mount, and Linux cannot delegate mount.
  • Whether zfs rewrite moves existing small files onto a newly added special vdev. The manual lists only checksum, compression, dedup and copies.
  • The defaults of OpenZFS 2.2.x point releases (block cloning in particular changed between them) and of distribution packages, which patch their own behavior.
  • Anything about hardware: drive firmware, controllers, SMR disks, USB bridges. The guide treats a disk as a disk.

Tool names move between releases. Before 2.4 the cache reports were called arcstat and arc_summary. They are zarcstat and zarcsummary in 2.4.
