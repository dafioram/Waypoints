Foundation

01Operating model and safety conventions

Git is a distributed content-addressed database with a mutable index and named references. A working directory is only one view of that database. Most Git mistakes become understandable once you distinguish working tree, index (staging area), current commit, and remote-tracking refs.

Four places a change can live

Place Meaning Inspect it
Working tree Files on disk, including unstaged edits and untracked files git status --short; git diff
Index Snapshot proposed for the next commit git diff --cached; git ls-files -s
HEAD The currently checked-out commit (normally reached through a branch) git show --stat HEAD; git symbolic-ref --short HEAD
Remote-tracking ref Your last fetched view of a remote branch, e.g. origin/main git branch -r -vv; git log origin/main

Fetch does not merge. Committing does not push. Pushing does not create a PR. These are deliberately separate operations.

Conventions used in this guide

  • main is the example default branch; substitute the actual branch name. origin means your normal remote, upstream means the original project you forked.
  • Commands use a POSIX shell and Git CLI. Replace illustrative example-org repositories, branch names and paths.
  • Check git status --short --branch before history edits. A backup branch protects committed history only. Save uncommitted files separately; a new worktree does not copy those edits. Paths following -- are file paths, not revisions.
  • A published commit may be in someone else's clone. Prefer revert over rewriting shared history.
  • Red-labeled commands can discard work or change shared history. Read consequences before pasting them.
terminal
# Always a useful diagnostic starting point
git status --short --branch
git branch -vv
git remote -v
git log --oneline --graph --decorate -12

How to use the recipes

Each copy box is one action or one sequence. Separate boxes may be alternatives or require a review checkpoint between them. Labels identify inspection, mutation, and destructive operations; output panels are examples, not commands. Replace illustrative repository URLs, IDs, and paths before use. If a command fails, stop and diagnose it before proceeding.

Multi-step recipes use shell variables: run their steps in the same terminal session. Unless stated otherwise, commands run at the superproject root. Each chapter remains readable offline; search works entirely in the page.

02Configuration, identity and authentication

Know which config wins

System (--system), user (--global), repository (--local), and worktree config can overlap. Higher-precedence scopes and command-line overrides win; includes and multiple values can complicate the result.

terminal
git --version
git config --list --show-origin --show-scope
git config --show-origin --get user.email
git config --global user.name "Your Name"
git config --global user.email "you@example.net"
git config --global init.defaultBranch main
git config --global fetch.prune true
git config --global rerere.enabled true
# Only choose pull.rebase after deciding your team's policy
git config --global pull.ff only

pull.ff only rejects divergent pulls instead of choosing a merge or rebase automatically. To inspect a single setting, use git config --show-origin --get KEY.

SSH versus HTTPS

SSH typically uses your SSH agent and public key; HTTPS generally uses a credential helper or gh auth login. A GitHub account password is not a supported Git-over-HTTPS credential. Keep private keys and tokens out of the repository.

terminal
ssh -T git@github.com             # Test GitHub SSH authentication
gh auth login                     # GitHub CLI interactive sign-in
gh auth status
git remote set-url origin git@github.com:example-org/app.git

Signing commits and tags

Git supports SSH, GPG, and other signing workflows. Signing authenticates who held a signing key; it does not mean the code is safe. Configure an approved key and check verification on your hosting platform.

terminal
git config --global gpg.format ssh
git config --global user.signingkey "${HOME}/.ssh/id_ed25519.pub"
git config --global commit.gpgsign true
git log --show-signature -1
git tag -s v1.2.0 -m "Release v1.2.0"

03Graph, refs, HEAD and the index

The graph is the history

A commit points to a tree and zero or more parent commits; trees point to blobs or more trees. Branches and tags are names pointing into the graph. Rebasing and amending create new commits with new IDs, even if their visible file content is identical.

diagram
A──B──C──D  main
    └──E──F  feature

HEAD -> refs/heads/feature -> F
origin/main -> D  (the last fetched remote state)

HEAD usually names a branch symbolically. A detached HEAD points directly to a commit; new commits there need a branch name to keep them conveniently reachable.

terminal
git cat-file -t HEAD
git cat-file -p HEAD
git rev-parse --show-toplevel
git rev-parse --git-dir
git symbolic-ref -q --short HEAD || echo "detached HEAD"
git ls-tree HEAD
git ls-files --stage

Revisions and ranges

  • HEAD~3: first parent three commits back; HEAD^2: second parent of a merge commit.
  • A..B: commits reachable from B but not A; A...B is symmetric difference for log; git diff A...B instead compares the merge base with B.
  • git merge-base A B: best shared ancestor for typical branch comparisons.
terminal
git log --graph --oneline --decorate --all --simplify-by-decoration
git log main..feature --oneline
git log --left-right --cherry-pick main...feature --oneline
git merge-base main feature
git diff main...feature --stat

04Investigate changes before acting

Inspect working tree, staged contents, and one commit

terminal
git status --short --branch
git diff --check                    # Whitespace errors
git diff --stat
git diff --word-diff
git diff --cached
git show --format=fuller --stat HEAD
git show HEAD:src/config.py         # File as stored in HEAD
git log --follow --oneline -- src/config.py

git status --short prefixes are two characters: index status then worktree status (M staged; M unstaged; ?? untracked). Use git status --porcelain=v1 -z for robust scripting.

Find the introduction of a bug

investigate file history
git log -S'problematic_symbol' --all --oneline -- src/
git log -G'regex.*pattern' --patch -- src/
git blame -L 40,75 src/file.py

Bisect is a separate session. With a clean checkout, a known bad current commit, and a known good v1.0.0 tag:

start binary-search investigation
git bisect start
git bisect bad
git bisect good v1.0.0

At each selected commit, run the test and mark it with git bisect good, git bisect bad, or git bisect skip. Alternatively, when your script reliably classifies a revision:

automate revision classification
git bisect run ./test.sh

Record the first bad commit and its test evidence. Finish the session separately to return to the original checkout:

finish bisect session
git bisect reset

git bisect run requires a repeatable test: exit 0 good, 1–127 except 125 bad, 125 skip. Make the test self-contained; run against a clean environment.

05Branching strategies and clean commits

A branch is a cheap movable name for a commit. Prefer small, cohesive branches and reviews rather than long-lived integration branches where possible. Name them by intent: feat/parser-cache, fix/timeout, docs/git-guide.

Create, inspect, and clean up branches

Start from a clean checkout. Create the feature branch here; commit and integrate its work before using the separate cleanup step.

create feature branch
git switch main
git fetch origin
git merge --ff-only origin/main
git switch -c feat/fast-index

Clean up after integration

Switch away from the feature branch before deleting it. If a squash merge prevents Git from recognizing it as merged, inspect the PR and compare the changes before deciding whether forced deletion is appropriate.

delete integrated branch
git switch main
git fetch origin
git merge --ff-only origin/main
git branch --merged main
git branch -d feat/fast-index

Only for a branch you have intentionally abandoned; preserve its tip under another name first if it may be needed.

delete unmerged branch
git branch -D abandoned-branch

Stage intentionally

review and commit
git add -p
git diff --cached --check
git diff --cached
git commit -m "fix: avoid duplicate work during retry"

Separate operation: amend only when the last commit is the one you intend to replace. Review staged changes first; amending changes its ID.

replace last commit
git commit --amend

For a conventional commit convention, use type(scope): imperative summary if the project adopts it. It is a team convention, not a built-in Git rule. Keep secret files ignored and excluded from commits; .gitignore cannot retroactively untrack committed secrets.

06Fetch, pull, push, and remote architecture

The remote/ref distinction

origin/main is local remote-tracking state, updated by fetch. main is your local branch. git push requests a remote ref update. A branch upstream (@{upstream}) is the configured integration target, not necessarily a remote named upstream.

terminal
git remote -v
git remote show origin
git fetch --prune origin
git log --oneline --left-right main...origin/main
git branch --set-upstream-to=origin/main main
git push -u origin feat/fast-index

Choose merge, rebase, or fast-forward deliberately

terminal
git switch main
git fetch origin
git merge --ff-only origin/main   # Safe linear synchronization

# On your private feature branch, replay commits on new main:
git switch feat/fast-index
git rebase main
# If branch was already published and you must update it:
git push --force-with-lease origin feat/fast-index

--force-with-lease is safer than --force, but it is not a substitute for coordination: background fetches can affect its expected value. Prefer reviewing the branch's current remote OID and an explicit lease for high-stakes changes.

Fork topology

terminal
gh repo fork example-org/project --clone   # Fork and clone if allowed
git remote -v                           # Usually origin=fork, upstream=original
git fetch upstream
git switch main
git merge --ff-only upstream/main
git push origin main

Use an explicit lease when a private published branch must be rewritten

Coordinate the rewrite first. On your feature branch, fetch and inspect the remote tip before saving the expected value; retain it while you rewrite. An explicit lease rejects the push if the server’s branch has changed since that point.

review and capture remote expectation
git fetch origin
expected_feature=$(git rev-parse refs/remotes/origin/feat/fast-index)
git log --oneline --left-right HEAD..."$expected_feature"

After the agreed rebase and verification, use the captured ID:

replace only the agreed branch
git push --force-with-lease="refs/heads/feat/fast-index:$expected_feature" \
  origin HEAD:refs/heads/feat/fast-index

A rejection is a reason to inspect new remote work, not to refresh the expected value automatically. This protects against an unexpected ref change, not against choosing the wrong branch or rewriting work collaborators already based on.

07Merge, rebase and conflict resolution

Choose the mechanism

Goal Operation Tradeoff
Integrate shared feature history intact git merge Preserves topology; can add a merge commit
Keep an unpublished branch linear git rebase Rewrites its commit IDs
Apply one selected fix git cherry-pick New commit, may need manual conflict handling
Reverse a published change git revert Records inverse change without rewriting history

These are separate choices. Begin on the branch that should receive the change, with a clean working tree.

merge a feature
git merge --no-ff feat/my-feature
edit your private branch history
git rebase -i main
fold fixup commits
git rebase -i --autosquash main
apply one selected commit
git cherry-pick -x abcdef12
reverse one published commit
git revert abcdef12

During a conflict

Conflict markers are just a textual representation of competing changes; they may also appear in rebase or cherry-pick. Understand which side is which before choosing --ours / --theirs: during rebase the meanings often surprise people.

terminal
git status
git diff --name-only --diff-filter=U
git ls-files -u                # Stage 1 base, stage 2 ours, stage 3 theirs
git diff --merge
# Edit files to intended result, then:
git add affected/file.py
git merge --continue            # During merge; or git rebase --continue
# Abandon instead: git merge --abort / git rebase --abort

git rerere can remember previous resolutions of the same conflict shape. Review the resolution after it applies; it is not a semantic merge engine.

08Stash, restore, reset and the danger ladder

Know the smallest operation that works

Intent Prefer Scope
Discard unstaged edits to one tracked file git restore -- file Working tree only
Unstage changes without deleting them git restore --staged -- file Index only
Temporarily set aside edits git stash push -u -m "context" Working tree + index + untracked (not ignored)
Move branch to an earlier commit, retain file changes git reset --mixed COMMIT Branch + index, retains working tree
Abandon a merge/rebase git merge --abort / git rebase --abort In-progress operation
Undo published code without altering history git revert COMMIT New inverse commit

Save work in this repository

stash and inspect
git stash push -u -m "before dependency update"
git stash list
git stash show -p 'stash@{0}'

Ignored files are excluded. A parent stash does not preserve uncommitted work inside submodules: save or commit that work separately in each child. Check that a stash was actually created before referring to stash@{0}.

Recover a stash without immediately deleting it

apply saved work
git stash apply --index 'stash@{0}'

Inspect git status and test the result. --index attempts to restore the staged state as well; conflicts may prevent this. The stash remains available. After confirming recovery, remove that exact stash in a separate action:

drop verified stash
git stash drop 'stash@{0}'

If applying conflicts, resolve and stage the intended files; there is no stash --continue. Keep the stash until the result is verified. To abandon the attempt, first preserve any work that existed before applying it; do not blindly hard-reset a mixed working tree.

Unstage one file, preserving its contents

unstage only
git restore --staged -- src/app.py

Discard unstaged edits to one tracked file

This replaces the working-tree file with the index version. Unsaved edits may be unrecoverable.

discard unstaged edits
git restore -- src/app.py

Destructive reset and clean

Use git clean -nd to preview, always. -x includes ignored files (such as build caches and sometimes local settings) and -fdx can erase valuable untracked work.

First inspect and save tracked edits, untracked files, ignored files, and child-repository work separately. A backup branch only preserves committed history.

discard tracked edits
git reset --hard HEAD

This reset replaces tracked files and may also remove untracked paths that obstruct writing tracked files. It is a separate action from cleaning.

Preview untracked-file deletion

preview only
git clean -nd

Stop and inspect every listed path. If the preview is correct and the working tree has not changed, run the deletion separately:

delete previewed untracked files
git clean -fd

To include ignored files, first preview with git clean -ndx. Only after reviewing that expanded list consider git clean -fdx. This can erase local settings, build output, and other valuable files.

09Reflog and recovering lost work

The reflog tracks local movements of refs and HEAD; it is a powerful short-term safety net, not a permanent backup. It is local to the repository and may expire or be pruned.

terminal
git reflog --date=local --all
git reflog show main
git show HEAD@{2} --stat
git switch -c rescue/recovered HEAD@{2}  # Preserve before resetting anything
git fsck --full --no-reflogs --unreachable # Last-resort unreachable objects

Incident recipes

Deleted a branch: find its tip in reflog, create rescue/<name> there. Bad hard reset: find pre-reset HEAD@{N} and create a rescue branch. Accidental amend/rebase: find old tip in reflog, inspect both versions before any force-push. Deleted an untracked file: Git generally cannot recover it; use backups or filesystem recovery.

Already pushed a secret? Remove access, rotate the credential immediately, then coordinate history cleanup and provider-side secret revocation. Deleting the local file alone does not remove it from old commits, forks, or caches.

10Worktrees: parallel work without extra clones

A linked worktree gives one repository multiple checked-out working directories, usually with different branches, and shares its Git object database. Good for reviewing a PR while developing another feature, release hotfixes, or bisecting without disrupting the primary directory.

terminal
git worktree add -b hotfix/urgent ../app-hotfix main
git worktree add ../app-review origin/main   # Detached worktree for inspection
git worktree list --porcelain
git -C ../app-hotfix status
git worktree remove ../app-review           # Refuses dirty worktree by default
git worktree prune                         # Clean stale administrative metadata

Do not manually delete active worktree folders. Git normally prevents the same local branch being checked out in two worktrees. Submodule setup is per worktree and has operational limitations; do not assume submodules are populated or safely shared between linked worktrees. For many complex submodule builds, separate clones may be simpler.

11Tags, releases and version conventions

Annotated tags are immutable in intent and contain tagger/message metadata. Lightweight tags are just refs. Avoid moving published release tags; automation and downstream users may have cached them.

terminal
git tag -a v2.4.0 -m "Release 2.4.0"
git show v2.4.0
git push origin v2.4.0
git ls-remote --tags origin
gh release create v2.4.0 --generate-notes

A tag does not tag nested submodule histories: the superproject's tagged commit pins gitlinks, and each submodule commit must still be fetchable from its own configured source. Use signed tags for provenance when appropriate and record reproducible build inputs.

12Git attributes, ignore rules and line endings

.gitignore controls untracked candidates; .gitattributes controls content treatment: text normalization, diff, merge drivers, and LFS filters. Patterns in .gitignore cannot remove a file already tracked in Git.

inspect ignore and attribute policy
git check-ignore -v build/cache.bin
git ls-files --cached -- .env
git check-attr -a -- assets/scene.psd

Separate operation: stop tracking a file while keeping its working-tree copy. Add the corresponding ignore rule and review the staged deletion before committing.

untrack local configuration
git rm --cached -- .env

Optional POSIX user-level convention; review existing repository attributes before changing it:

set user line-ending policy
git config --global core.autocrlf input
.gitattributes
# Example .gitattributes: commit consistent LF line endings
* text=auto
*.sh text eol=lf
*.bat text eol=crlf
*.png binary

Introduce normalization in a dedicated commit, separate from feature work, and review git diff --check to avoid mass line-ending conflicts.

Submodules

13Submodules: the mental model (read first)

A submodule is a separate Git repository, not a regular directory whose files the parent tracks. The superproject records a gitlink (tree entry mode 160000) pointing to one exact submodule commit. .gitmodules records the path and clone URL, plus optional hints such as a branch to use with update --remote.

diagram
Superproject (app)                    Submodule (engine)
┌────────────────────────────┐       ┌────────────────────────────┐
│ app commit 9d8c...         │       │ engine commits: a1 → b2 → c3│
│   src/...                  │       │                            │
│   .gitmodules              │       │ main → c3                  │
│   engine/ 160000 → b2 ───────────→ │ commit b2 (PINNED)         │
└────────────────────────────┘       └────────────────────────────┘

Important consequences:

  • Cloning the parent without recursive options often leaves submodule working directories unpopulated.
  • git submodule update --init normally checks out the pinned commit in detached HEAD, whether or not it is the latest on a branch. This is correct and reproducible.
  • Committing inside the submodule changes its own repository, not the parent's recorded gitlink. Commit the updated gitlink in the parent separately.
  • The parent does not store the child repository's objects or LFS content. The pinned commit must be obtainable from the child's remote for teammates and CI.
  • .gitmodules and submodule.* values in local .git/config are related but distinct. git submodule init copies configuration when first registering; git submodule sync updates changed URLs for initialized modules.
terminal
git ls-tree HEAD libs/engine               # 160000 commit <sha>
git submodule status --recursive
git diff --submodule=log
git submodule summary --cached
git -C libs/engine rev-parse HEAD
Submodules

14Submodule architecture: own it or depend on it?

Decision You manage the child repo Someone else manages it
Update authority You can commit and push upstream You generally cannot push to its upstream
Default intent Develop child and parent together Adopt a tested upstream release or commit
Typical workflow Child feature branch → push child → parent pin → push parent Fetch upstream → inspect changes → select commit → parent pin
Local modification Make a normal child branch and PR Contribute upstream, or maintain a clearly named fork
Critical check Push child commit before publishing parent pointer Pinned commit exists in an accessible upstream or fork
Maintenance Coordinated test/version/release policy Watch compatibility, licensing, security, and upstream availability

Core recommendation: treat both situations as pinned dependencies in released/CI builds. --remote is an explicit upgrade operation, not what a normal checkout should do. Do not make builds silently chase main or the default upstream branch.

When not to use submodules

Use a package manager for published libraries with release/version resolution; a monorepo for code that needs atomic commits and one review process; git subtree or vendoring if consumers must receive source in one clone and accept copying upstream code. Submodules excel when repositories have independent lifecycles, security boundaries, or reuse and you need exact commit pins.

15Submodules: add, clone, inspect and initialize

Add a child repository

terminal
# Commands run from superproject root; sample URLs are illustrative.
git submodule add -b main https://github.com/example-org/engine.git libs/engine
git diff -- .gitmodules
git diff --cached --submodule=log
git commit -m "build: pin engine as submodule"

-b main records a branch hint for git submodule update --remote; it does not replace the recorded commit pin. Prefer relative submodule URLs (../engine.git) only when the projects genuinely share a stable host/organization relationship and forks can resolve them correctly.

Clone a parent containing submodules

For a new clone:

clone pinned dependencies
git clone --recurse-submodules https://github.com/example-org/app.git
cd app
git submodule status --recursive

For an existing parent checkout instead:

initialize existing checkout
git submodule update --init --recursive

To initialize only one selected module instead:

initialize one module
git submodule update --init -- libs/engine

After switching parent branches, run git submodule update --init --recursive to move children to the commits recorded by the new parent commit. This may detach a child's HEAD; that is normal for dependency consumption.

Status symbols and changed pointers

git submodule status uses - for uninitialized, + when the child HEAD differs from the parent's recorded pin, and U for an unresolved gitlink merge conflict. A modified submodule working tree is a distinct condition from a different gitlink commit.

terminal
git status --short
git diff --submodule=log
# Inspect what parent expects vs what is actually checked out:
git rev-parse HEAD:libs/engine
git -C libs/engine rev-parse HEAD

16Self-managed submodule: the full two-repo workflow

Scenario: your application uses libs/engine, and you have push access to both repositories. You are modifying the engine API and the application in the same feature. The unit of publication is two Git commits and two pushes, not a single atomic commit.

1. Create a branch and change the child

terminal
# In the parent:
git switch -c feat/new-parser
# In the child (often detached after initialization):
git -C libs/engine switch -c feat/new-parser
# Edit child files, run its tests...
git -C libs/engine status --short
git -C libs/engine add -p
git -C libs/engine commit -m "feat: expose parser streaming API"
git -C libs/engine push -u origin feat/new-parser

If the child branch already exists locally, use git -C libs/engine switch feat/new-parser rather than creating it again. Review what it branched from; after a normal submodule checkout, it may start at an older pinned commit.

2. Commit and publish the parent pin

terminal
# Change parent application code to use the API, then:
git status --short
git diff --submodule=log
git add src/ libs/engine
git commit -m "feat: use streaming parser from engine"
# Local guard; follow with the fresh-clone verification below.
git push --recurse-submodules=check origin feat/new-parser

If the remote child commit is on a feature branch, teammates need permission to fetch it and that branch must not be deleted before merging/retaining the commit. Preferred release practice: merge the child's PR into a durable branch or tag first, then pin the resulting reachable commit in the parent.

3. Optional push automation

Choose automatic child pushing only when every relevant child has an appropriate push remote and branch configuration:

attempt child pushes before parent
git push --recurse-submodules=on-demand origin feat/new-parser

Alternatively, configure this parent repository to check child publication on future pushes:

enable local publication guard
git config --local push.recurseSubmodules check

check uses child remote-tracking reachability to detect unpublished commits; on-demand attempts child pushes. Neither proves that the recorded clone URL, current server state, and a teammate’s credentials can supply the pin. Use the fresh-clone verification below.

Typical traps

  • You committed in the child but didn't stage libs/engine in the parent: the parent still points to the old commit.
  • You committed a new gitlink in the parent but never pushed the child: fresh clones cannot fetch the pin.
  • You ran git submodule update while developing on a child branch: default checkout may detach HEAD at the parent pin. Preserve child work in a branch before running it.
  • You changed parent and child in separate PRs: coordinate merge order so the parent never points at an unavailable child commit.

When the child PR is squash-merged

Starting state: child PR 42 was merged into example-org/engine with squash, and the parent feature branch still pins the original child feature tip. Squashing creates a different commit. Obtain the merged PR’s actual commit, fetch it, and repin before the old branch is retired.

inspect merged child commit
child_release=$(gh pr view 42 --repo example-org/engine --json mergeCommit --jq '.mergeCommit.oid')
test -n "$child_release" && test "$child_release" != null
git -C libs/engine fetch origin main
git -C libs/engine show --stat "$child_release"
git -C libs/engine merge-base --is-ancestor "$child_release" origin/main

Stop if any check fails, or the child contains local edits. Once the commit and compatibility are confirmed:

select durable child commit
git -C libs/engine switch --detach "$child_release"
git -C libs/engine submodule sync --recursive
git -C libs/engine submodule update --init --recursive
git diff --submodule=log

Run the child tests and the application’s integration tests before recording the pin.

publish revised parent pin
git add libs/engine
git commit -m "deps: pin merged engine change"
git push --recurse-submodules=check origin HEAD
Expected result
The parent now records the merged child commit, not the pre-squash feature tip.

Verify publication from a fresh clone

Use a new directory and the same access model as CI. This checks the actual recorded clone URLs rather than your existing child remotes or object cache. The branch must already be published.

verify clean consumer checkout
git clone --branch feat/new-parser --recurse-submodules \
  https://github.com/example-org/app.git ../app-pin-check
git -C ../app-pin-check submodule status --recursive
git -C ../app-pin-check status --short

Expect no -, +, or U prefix in submodule status and a clean parent status. If LFS is used, pull and verify those payloads in each relevant repository, then run the build. Failure here blocks parent integration. To roll back a published parent change, use a reviewed revert and update the child worktrees to the restored pins.

17Externally managed submodule: upgrade without ownership

Scenario: your application embeds an upstream codec repository (vendor/codec) that you do not control. Treat it like a release-managed dependency. The safest update is a deliberate commit selection, not an unreviewed move to the tip of the upstream branch.

1. Inspect upstream and pick a version

terminal
git -C vendor/codec remote -v
git -C vendor/codec fetch --tags origin
git -C vendor/codec log --oneline --decorate -15 origin/main
git -C vendor/codec tag --sort=-version:refname | head
# Inspect between old pin and proposed release:
git -C vendor/codec log --oneline HEAD..v2.3.1
git -C vendor/codec diff --stat HEAD v2.3.1

2. Move to the tested version and record it in the parent

terminal
git -C vendor/codec switch --detach v2.3.1
git -C vendor/codec submodule sync --recursive
git -C vendor/codec submodule update --init --recursive
git -C vendor/codec rev-parse HEAD
git diff --submodule=log
# Run tests in the superproject now
git add vendor/codec
git commit -m "deps: update codec to v2.3.1"
git push origin HEAD

The superproject stores the commit ID, not the tag name. Tags can be moved or removed upstream; record the selected version and reason in the commit/PR. Verify licenses and changelog, test consumers, and keep a rollback path to the previous parent commit.

Explicit branch-following update (not a checkout default)

terminal
# Configure the branch hint in the tracked .gitmodules:
git submodule set-branch --branch main vendor/codec
git add .gitmodules && git commit -m "build: track codec main for manual upgrades"
# This fetches and checks out the remote tracking branch's target (normally detached):
git submodule update --remote vendor/codec
# Review and test, then stage/commit the new gitlink only if approved.
git diff --submodule=log
git add vendor/codec && git commit -m "deps: advance codec pin"

git submodule update --remote --merge and --rebase can integrate new upstream commits into an existing child branch instead of detached-checkout behavior; they are for active child development, not passive consumption. git pull inside the child follows its own branch tracking config, not necessarily the .gitmodules branch hint.

Nested dependencies after selecting a release

The release-selection recipe above also updates nested dependencies. Check their pins before staging the parent pointer; switching the top-level child alone does not populate those worktrees.

verify nested release pins
git -C vendor/codec submodule status --recursive

Do this before staging the parent pointer. For rollback, restore the previously selected parent commit through your normal branch/revert workflow, then run git submodule update --init --recursive.

18External child with local patches: fork or contribute

If upstream needs a patch, choose intentionally:

  1. Contribute upstream: fork the child, make a PR; once merged to upstream and available there, select the upstream commit and pin it in the parent. Best long-term maintenance.
  2. Maintain a fork: if upstream cannot accept the change in time, point the parent's .gitmodules URL at your fork and pin a commit available from that fork. Now you own updating and securing that fork.
  3. Avoid an unpushed detached commit: a parent cannot reliably clone a child commit that exists only on your machine.

A maintainable fork workflow

terminal
# In the child, keep official upstream separate from your fork:
git -C vendor/codec remote rename origin upstream
git -C vendor/codec remote add origin git@github.com:your-org/codec-fork.git
git -C vendor/codec fetch upstream
git -C vendor/codec switch -c patches/app-compat upstream/main
# Edit; commit; test, then publish to your fork:
git -C vendor/codec push -u origin patches/app-compat
# In parent, RECORD your fork URL for future clean clones:
git submodule set-url vendor/codec https://github.com/your-org/codec-fork.git
git add .gitmodules vendor/codec
git commit -m "deps: use patched codec fork"

Caution: git submodule set-url updates .gitmodules and synchronizes this checkout; teammates with old initialized URL settings should run git submodule sync --recursive after pulling. Confirm all relevant CI deploy keys or tokens can read the fork. A private fork embedded into a public parent can make fresh clones fail.

Bring upstream fixes into your fork

terminal
git -C vendor/codec fetch upstream
git -C vendor/codec switch patches/app-compat
git -C vendor/codec merge upstream/main
# Resolve/test/commit as necessary, then:
git -C vendor/codec push origin patches/app-compat
git add vendor/codec
git commit -m "deps: refresh patched codec against upstream"

Decide whether to merge or rebase local patch history based on whether the fork branch is shared. Never rewrite a branch other consumers depend on without coordinating.

20Submodule conflict resolution and recovery

A gitlink conflict represents competing child commit IDs. Resolve the child history first, then stage the chosen child commit in the parent. The following recipe is for an ordinary parent merge stopped on libs/engine, with two divergent child commits and push access to the child. For a rebase, inspect the reversed side meanings and use git rebase --continue at the final parent step.

1. Capture both pins and inspect the child

Do not start with dirty child worktrees. Save child edits and detached commits before switching branches. Keep this terminal open so the captured variables remain available.

inspect unmerged gitlink stages
ours=$(git rev-parse :2:libs/engine)
theirs=$(git rev-parse :3:libs/engine)
git -C libs/engine fetch origin
git -C libs/engine cat-file -e "$ours^{commit}"
git -C libs/engine cat-file -e "$theirs^{commit}"
git -C libs/engine log --graph --oneline --left-right "$ours...$theirs"

Stop if either object is missing. Fetch the child branches that contain those commits from an authorized source; do not replace a missing pin arbitrarily. Use git merge-base --is-ancestor in both directions to check whether choosing a descendant is sufficient. Exit 0 means ancestor; 1 means not ancestor; other nonzero results are errors.

2. Merge the child commits

integrate child histories
git -C libs/engine switch -c integrate/parent-merge "$ours"
git -C libs/engine merge --no-ff "$theirs"

If this produces a child file conflict, edit that file to the intended result, then stage it explicitly. Here the conflicting file is src/parser.py; substitute the paths Git reports.

finish child conflict resolution
git -C libs/engine diff --name-only --diff-filter=U
git -C libs/engine add -- src/parser.py
git -C libs/engine diff --cached
git -C libs/engine merge --continue

Skip that conflict block if the child merge completed automatically. Run the child’s tests and the parent’s integration tests. Then verify both input tips are ancestors of the selected child result:

verify child integration
git -C libs/engine merge-base --is-ancestor "$ours" HEAD
git -C libs/engine merge-base --is-ancestor "$theirs" HEAD
git -C libs/engine status --short
Expected result
Both ancestry checks exit 0. The child status is clean; HEAD is the integration commit.

3. Publish the child, then finish the parent

publish child integration
git -C libs/engine push -u origin integrate/parent-merge

Retain this child commit on a durable branch or tag under the recorded child URL. After a successful child push:

stage parent resolution
git add libs/engine
git diff --cached --submodule=log
git diff --name-only --diff-filter=U

The last command must produce no paths before continuing; resolve any other parent conflicts first.

finish parent merge
git merge --continue

Publish the parent through its normal reviewed workflow, then use the fresh-clone check.

Recovery at either layer

While the child merge is in progress, git -C libs/engine merge --abort abandons that merge. While the parent merge is in progress, git merge --abort abandons the parent merge. These are separate operations. A completed child integration commit stays on its child branch even if the parent merge is aborted. Save edits before repopulating the parent’s old pin with git submodule update --init --recursive. After publication, use coordinated revert commits rather than deleting reachable history.

Common submodule errors

Symptom Likely cause Safe next step
not our ref <sha> Child remote cannot supply parent's pinned commit Confirm commit exists on an accessible branch/tag or correct remote; push child or repin parent
Child looks empty after clone Submodules not initialized git submodule update --init --recursive
Child says detached HEAD Normal pinned checkout Make a branch in child before editing
Parent says modified: child Child HEAD changed or child has modified/untracked content Inspect git -C child status; compare git diff --submodule=log

Large files & LFS

21Git LFS: how large files actually work

Git stores ordinary file versions as Git blob objects. Large binaries that change frequently can bloat every clone because the history retains their prior versions. Git Large File Storage (LFS) puts a small text pointer in ordinary Git history and stores the large payload in a separate LFS object store. LFS is an extension with its own lifecycle, permissions, retention and storage/bandwidth quotas.

diagram
Git history:                 LFS store:
assets/scene.psd             oid sha256:abcdef... ──> actual 180 MB file
  ↳ pointer file (< 1 KB)

A pointer contains a version declaration, SHA-256 object ID, and size, not the binary content. Normal working trees usually contain the real file because the LFS smudge/filter process downloads it.

When LFS helps—and when it does not

Material Recommended location Why
Source code, small text configs Ordinary Git Great textual deltas and history
Large frequently edited PSD, CAD, datasets, binaries Git LFS Avoids repeated large Git blobs
Generated build artifacts Release/package registry/artifact storage Usually shouldn't be versioned at all
Dependency source Package manager, submodule, or vendoring Depends on release and ownership model
Secrets / passwords Secret manager, never Git or LFS LFS is not an encryption mechanism
Huge reproducible data archive Object storage/data versioning system LFS quotas and download patterns may be unsuitable

On GitHub, ordinary Git warns above 50 MiB and blocks individual files above 100 MiB; LFS per-file limits depend on plan. GitHub Pages does not support Git LFS, so do not use LFS for assets that your Waypoints static site itself needs to serve. Store page media as normal files (if suitably small), or use external hosting when appropriate.

Large files & LFS

22Git LFS: install, track, inspect and download

Track new large binaries

terminal
# Install git-lfs using the OS package manager first (package name: git-lfs)
git lfs version
git lfs install
git lfs track '*.psd'
git lfs track '*.blend'
git add .gitattributes assets/scene.psd
git commit -m "assets: track design source in Git LFS"
git push origin HEAD

Commit .gitattributes: this is the policy that tells other clones to use LFS for matching paths. Quote patterns so the shell doesn't expand them before git lfs track receives them. Use specific extensions rather than indiscriminately sending all binary files to LFS.

Inspect LFS versus normal Git

terminal
git lfs ls-files
git lfs status
git lfs env
git check-attr filter -- assets/scene.psd
git show HEAD:assets/scene.psd  # Git stores a textual pointer
# Avoid accidentally printing a binary from the working tree to the terminal.

Download or selectively skip large payloads

download current checkout payloads
git lfs pull

Separate backup/migration operation; it can download a large amount of history:

fetch historical payloads
git lfs fetch --all

Inspect local cache pruning before deleting anything:

preview local LFS cache pruning
git lfs prune --dry-run

After checking the preview and verifying remote copies/backups, prune eligible local objects separately:

prune local LFS cache
git lfs prune --verify-remote

To start a new clone without downloading asset payloads:

clone with pointers initially
GIT_LFS_SKIP_SMUDGE=1 git clone https://github.com/example-org/artwork.git
cd artwork
git lfs install --local

Run git lfs pull inside that clone when you need the real files.

git lfs prune cannot replace a verified remote backup. Offline operations and old releases can require payloads you no longer have locally.

23Git LFS: migrate existing files and clean history

Already tracked binaries, but history may stay as-is

terminal
git lfs track '*.psd'
git add .gitattributes
git add --renormalize .
git diff --cached --stat
git commit -m "assets: convert current PSD files to LFS"

This converts current matching tracked content to pointers in new commits, without removing the old large blobs from past commits. It is appropriate when you cannot rewrite shared history and old repository size is acceptable.

Worked migration: rewrite one agreed branch

Starting state: a coordinated freeze, a remote with one branch to migrate (main), no release tags requiring rewriting, sufficient LFS quota, and permission to replace the branch. This example converts PSD and Blender history. Other branches, tags, PR refs, and provider retention can still keep old blobs reachable. A migration is not automatic server-side storage reclamation.

1. Clone, record the lease, and back up

prepare migration and backup
GIT_LFS_SKIP_SMUDGE=1 git clone --single-branch --branch main \
  https://github.com/example-org/artwork.git artwork-migration
cd artwork-migration
git lfs install --local
git fetch origin main
old_main=$(git rev-parse refs/remotes/origin/main)
printf '%s\n' "$old_main" > ../artwork-main-before.txt
git bundle create ../artwork-before.bundle --all
git bundle verify ../artwork-before.bundle
git lfs fetch --all origin
git rev-parse --git-path lfs/objects

Copy the LFS objects directory printed above to a separate backup location if it exists. The bundle does not contain those payloads. Confirm a restore from the bundle and LFS backup before continuing. Keep the recorded old ID unchanged; it is the expected remote value for the later lease.

2. Inspect and transform

inspect candidate history
git status --short
git lfs migrate info --include-ref=refs/heads/main

Stop if the working tree is not clean or the inventory does not match the agreed scope. Then rewrite the selected branch:

rewrite main history
git lfs migrate import --include-ref=refs/heads/main --include='*.psd,*.blend'

The explicit include ref selects the reachable history of local main. The original remote-tracking ref and external backup remain useful for comparison; they may still retain old blobs locally.

verify pointers and policy
git lfs checkout
git lfs ls-files
git lfs fsck
git log --oneline -8 main
git show main:.gitattributes
git show main:assets/scene.psd
Expected result
assets/scene.psd in Git is a pointer containing version, oid sha256:…, and size.
The working-tree file should still contain the real asset.

Use an asset path that actually exists. git lfs checkout materializes payloads already in the local LFS cache; it does not download missing ones. Open representative assets, run project tests, and compare payload checksums against the original versions. Check attributes across relevant historical revisions when old releases matter.

3. Upload payloads, then replace exactly one ref

upload migrated LFS payloads
git lfs push --all origin main

Stop on any upload failure. After review and any required branch-protection exception, replace only main using the previously recorded expected ID. Do not substitute a new expected ID merely to bypass a rejected lease.

publish agreed history rewrite
git push --force-with-lease="refs/heads/main:$old_main" \
  origin refs/heads/main:refs/heads/main

4. Verify as a new consumer

verify remote Git and LFS together
cd ..
GIT_LFS_SKIP_SMUDGE=1 git clone --single-branch --branch main \
  https://github.com/example-org/artwork.git artwork-verify
cd artwork-verify
git lfs install --local
git lfs pull
git lfs fsck
git lfs ls-files
git status --short

Open the actual assets and run the build in this new clone. Expect a clean status and valid LFS payloads. Only then end the freeze and instruct collaborators to re-clone or carefully transplant their unpushed work. Never merge the old branch wholesale into the rewritten history.

Recovery and wider migrations

Before publication, abandon the migration clone and restore from the verified backups. After publication, freeze writes again, inspect the current remote ID, and coordinate any restoration of the original branch using an explicit lease; account for new work first. Keep the Git bundle and LFS backup until the migration has been accepted.

For several branches or tags, inventory every ref, map old to new IDs, and publish an explicitly reviewed list. git lfs migrate import --everything considers commits reachable from local and remote refs but updates local refs; it does not automatically rewrite remote-tracking refs or publish anything. Signed tags and signed rewritten commits require renewed provenance. Avoid an indiscriminate mirror push. See the migration manual.

Remove a large file committed by mistake

If the bad file is only in an unpublished last commit, remove it from the index and amend. If already shared, avoid casual rewrite; choose git filter-repo in a fresh clone with organizational coordination when rewriting history is genuinely necessary. Removing a file in a new commit does not remove old blobs.

terminal
# Only for an unpublished last commit:
git rm --cached assets/huge.dump
printf '\nassets/*.dump\n' >> .gitignore
git add .gitignore
git commit --amend
# For large history cleanup, evaluate git-filter-repo in a fresh clone.

26GitHub Actions: reproducible checkouts

Treat CI as a clean consumer of the repository. GitHub-hosted jobs normally get fresh environments; self-hosted runners may retain state. Do not assume .git/modules, LFS caches, SSH agent or credentials from your laptop exist. GitHub's checkout action can initialize submodules. GitHub Actions
# Example job steps within an existing GitHub Actions workflow.
# Use the current supported checkout release in your repository.
steps:
  - uses: actions/checkout@v7
    with:
      fetch-depth: 0
      submodules: recursive

27Advanced history editing

History editing replaces commits. Start with a clean working tree, preserve the old tip, and use these recipes on a private branch or under an agreed rewrite policy. A backup branch preserves committed states, not unstaged edits. The examples below are separate workflows.

Fixup and autosquash

Stage only the correction for the chosen earlier commit; replace abc1234 with that commit ID.

fold a focused correction
git add -p
git diff --cached
git commit --fixup=abc1234
git branch backup/before-autosquash
git rebase -i --autosquash main

Review the generated todo list before accepting it. Resolve conflicts, stage the intended files, and run git rebase --continue. During an unfinished rebase, git rebase --abort returns to the starting branch state. Compare the resulting patch series with the backup and rerun tests.

Split one private commit into two

Starting state: branch feat/parser has a non-root commit touching both src/parser.py and docs/parser.md, followed by other commits. Both files were already tracked in the preceding commit. You want the implementation and documentation as separate commits. Save unrelated work first.

start commit split
git switch feat/parser
git branch backup/before-split
git rebase -i main

In the editor, change pick to edit for the combined commit, save, and exit. Wait for Git to stop at that commit. Then move HEAD back one commit while leaving its file changes unstaged:

uncommit the stopped change
git reset --mixed HEAD^

This reset is intentional inside the stopped rebase; do not use --hard. The combined change is now in the working tree.

record implementation part
git add -- src/parser.py
git diff --cached
git commit -m "feat: add parser mode"

Review what remains before creating the second commit. Use git add -p instead when splitting hunks in the same file.

record documentation part
git add -- docs/parser.md
git diff --cached
git commit -m "docs: explain parser mode"
git status --short

The working tree must now be clean. If the original commit added other paths, include them deliberately before continuing.

replay later commits
git rebase --continue
verify split result
git diff --exit-code backup/before-split HEAD
git range-diff main..backup/before-split main..HEAD
git log --oneline main..HEAD
Expected result
The final tree diff is empty; the original combined change is now two commits.
Later commits may have new IDs. Run tests even when the final tree matches.

If the rebase is still in progress, abort it to return to the original tip. If it already finished, inspect backup/before-split and create a rescue branch there; do not overwrite new work with a blind reset.

Move a stacked branch with rebase --onto

Starting state: feature-a contains A1 and A2 on top of main; feature-b contains B1 and B2 on top of A2. A was squash-merged into the current main, so replaying A1 and A2 is unwanted. Preserve the old A2 boundary before moving or deleting feature-a.

inspect commits to transplant
git switch feature-b
git branch backup/before-onto
git branch backup/a-boundary feature-a
git log --oneline backup/a-boundary..feature-b
Expected result
Only B1 and B2 should be listed. Stop if the range includes unrelated work.
transplant B onto main
git rebase --onto main backup/a-boundary feature-b

The arguments mean: new base main, exclude commits reachable from the old boundary, rewrite feature-b. The result is main → B1′ → B2′. Conflict resolution may still be needed even though A’s changes are already present.

review transplanted patch series
git range-diff backup/a-boundary..backup/before-onto main..feature-b
git log --oneline --graph --decorate -12

Run the feature’s tests. During a stopped rebase use continue/abort as above. If the old boundary was lost or rewritten, recover it from reflog before guessing a range. --rebase-merges can recreate merge topology, but prior manual merge resolutions may need to be reapplied and tested.

Revert a merge, then reintroduce its corrected feature

Starting state: published main contains a true merge commit M whose first parent is the previous main tip. The feature contains a defect. Inspect M’s parents before choosing the mainline; -m 1 means preserve the first-parent side, not “revert one commit.” Work through review branches.

inspect merge parents
git switch -c revert/parser origin/main
git show --no-patch --pretty=raw MERGE_COMMIT

After confirming the first parent is the intended mainline, substitute the inspected merge ID:

reverse merge changes
git revert -m 1 MERGE_COMMIT

Resolve any conflicts, stage the result, and use git revert --continue; use git revert --abort to abandon an unfinished revert. Test and merge the revert through a PR. Record the resulting revert commit ID on main, especially if your PR itself is squash-merged.

A revert leaves M in the ancestry. Merging the old feature branch again will not simply restore all its old changes. If the team fixes the original feature by adding commits to that same branch, a common reintegration path is to revert the revert, then merge the corrected feature on a new review branch:

restore previously reverted change
git fetch origin
git switch -c reintroduce/parser origin/main
git revert REVERT_COMMIT_ON_MAIN

Complete and inspect this revert before integrating the corrected feature:

integrate follow-up fixes
git merge --no-ff origin/feature-parser

Test the full restored feature before publication. This recipe assumes the corrected branch extends the original history. If the feature was rebuilt as a new patch series, analyze that history separately rather than automatically reverting the revert. See git-revert and git-rebase.

29Plumbing: inspect objects, trees and gitlinks

The porcelain commands (status, switch, commit) are human-facing. Plumbing (cat-file, hash-object, rev-list, update-ref) exposes Git's underlying model. Use these for diagnostics or carefully reviewed scripts, not routine manual ref editing.

terminal
git rev-parse HEAD
git cat-file -t HEAD
git cat-file -p HEAD
git cat-file -p HEAD^{tree}
git ls-tree -r HEAD | head -30
git ls-tree HEAD vendor/codec   # '160000 commit' for submodule
git rev-list --objects --all | head
git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads/

Index entries and hash algorithms

git ls-files --stage prints modes, object IDs and index stages. Modes include 100644 regular file, 100755 executable, 120000 symlink, and 160000 gitlink. SHA-1 repository formats remain common; Git also supports SHA-256-format repositories, but hosting/tool support must be checked before creating one. Never assume an object ID is always 40 hexadecimal digits in programmatic tools.

Atomic reference changes

git update-ref is for scripts and experts; it can verify an expected old OID to guard against races. Prefer git branch, git tag, and git push for normal use. A ref update does not rewrite underlying objects.

Lab: trace one file from working tree to branch ref

Run this in a disposable directory outside any existing repository. It creates only a new git-object-lab folder and configures identity locally. If that name already exists, choose a fresh one; do not reuse a real project.

create and stage a file
mkdir git-object-lab
cd git-object-lab
git init -b main
git config user.name "Git Lab"
git config user.email "git-lab@example.invalid"
printf 'hello\n' > hello.txt
git hash-object hello.txt
git add hello.txt
git ls-files --stage
Expected result
The index shows: 100644 <blob-id> 0 hello.txt
The object ID matches hash-object; stage 0 means a normal, resolved entry.

hash-object computes an ID here without writing an object; staging writes the blob and records its ID in the index. This new repo has no attributes affecting this file. In other repositories, clean filters and normalization can change the stored bytes.

inspect blob, tree, commit, and ref
git cat-file -p :hello.txt
tree_id=$(git write-tree)
git cat-file -p "$tree_id"
git commit -m "Add greeting"
git cat-file -p HEAD
git rev-parse HEAD^{tree}
git symbolic-ref HEAD
git rev-parse refs/heads/main
Expected result
Blob content: hello
Tree entry: 100644 blob <blob-id> hello.txt
Root commit: tree <tree-id>, author, committer, message (no parent)
HEAD symbolically names refs/heads/main; that ref resolves to the commit ID.

The tree printed by rev-parse HEAD^{tree} matches tree_id. write-tree serializes the index without moving a branch. The commit refers to that tree and identity/message metadata; the branch names the commit.

Lab: change the working tree without changing the index

compare all three file states
printf 'hello again\n' > hello.txt
git diff -- hello.txt
git diff --cached -- hello.txt
git cat-file -p :hello.txt
git show HEAD:hello.txt
Expected result
Working-tree diff shows the edit. Cached diff is empty.
The index and HEAD still contain hello; the working tree contains hello again.

Now stage and commit the new version:

store a second snapshot
git add hello.txt
git diff --cached -- hello.txt
git commit -m "Extend greeting"
git cat-file -p HEAD
git show HEAD^:hello.txt

The new commit has a parent pointing to the first commit and a new tree pointing to a new blob. The old commit and blob still exist. Rename detection and patch output are comparisons Git computes; commits fundamentally name snapshots. In a superproject tree, a gitlink uses mode 160000 and identifies a child commit whose objects live in the child repository.

30Hooks, aliases and automation safety

Local hooks live in the repository's hooks directory (or configured core.hooksPath) and are not generally versioned and auto-installed from a remote clone. Tools such as pre-commit can manage shared hook policy. Server-side protections are needed because users can bypass local hooks.

terminal
git config --global alias.lg 'log --oneline --graph --decorate --all'
git config --global alias.unstage 'restore --staged --'
git config --get core.hooksPath
git help hooks

Shell scripting conventions

  • Inspect git rev-parse --show-toplevel instead of assuming the current directory is the root.
  • Quote paths and use NUL-delimited output (-z) when processing arbitrary filenames.
  • Prefer git status --porcelain=v1 -z and git diff --name-only -z to human-readable output.
  • Treat a detached HEAD in CI as normal. Do not assume git branch --show-current yields a name.
  • Before scripted destructive changes, validate repo identity, current branch, clean state and expected remote OIDs.

A status-command failure must stop the script. This example checks the exit status before checking whether the output is empty; it includes untracked files and overrides submodule-ignore settings. It does not protect ignored files or detached child commits.

fail-closed status guard
# POSIX shell script; exit terminates the script.
repo_status=$(git status --porcelain=v1 --untracked-files=all --ignore-submodules=none) || {
  printf '%s\n' 'Refusing operation: unable to inspect repository' >&2
  exit 1
}
if [ -n "$repo_status" ]; then
  printf '%s\n' 'Refusing operation: working tree or index not clean' >&2
  exit 1
fi

33Recommended conventions and anti-patterns

  • Atomic by intent: one logical change per commit; keep generated artifacts out of commits unless intentionally required.
  • No magic pull behavior: team chooses ff-only/rebase/merge policy; the default should not rewrite shared work accidentally.
  • Pinned dependencies: commit versions or SHAs, including submodules; don't chase upstream in releases and CI.
  • Durable child pointers: never publish parent gitlinks before child objects are reachable by reviewers and CI.
  • Minimal force: avoid rewriting protected/shared branches; when essential use explicit leases and announce coordination.
  • Auditable large files: track LFS policy in .gitattributes; distinguish code history from downloaded payloads and billing.
  • Secrets are special: rotate exposed tokens; .gitignore and history rewrites alone cannot un-expose a leaked secret.
  • Separate working contexts: use worktrees for parallel branches, dedicated fresh clones for risky history migrations.
  • Backups matter: mirrored hosting and reflog are not full backups; consider a tested git bundle plus LFS backups.

Back up Git history in a portable bundle

terminal
git bundle create repo-backup.bundle --all
git bundle verify repo-backup.bundle
git clone repo-backup.bundle recovered-repo

A bundle contains Git refs and objects selected by the bundle command, not LFS payloads, hosting metadata (PRs, issues, permissions), remote secrets, or uncommitted working-tree/index changes. Back up these separately when necessary. Submodules are separate repositories: back them up individually.
